# 523 未完了の案件を除いてリードタイムの中央値を出すと、本当より何日短く出るのか？（実務の型）

架空の案件（2024年1月〜2025年12月に受注）を作り、2025年12月31日で締めて、2025年に受注した案件のリードタイム（受注から完了までの日数）の中央値を、未完了の案件の扱い方を変えて出し、全部が終わった後に分かる「本当の中央値」と比べたフォルダです。受注件数が増えている時期・横ばい・減っている時期の3通りで比べました。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A523 | 締めの日に終わっていない案件を除くと、リードタイムの中央値は本当より何日短く出るか。カプラン・マイヤー、締めを後ろにずらす、「期間中に完了した案件」で数える、ではどうか | 受注から完了までの日数は時期によらず同じ分布（対数正規、中央値60日）。締めの日時点で見える情報だけで中央値を出し、全部終わった後の値と比べる。完了分だけの中央値と未完了の件数は SQL（DuckDB）でも出し、Python と一致するか確かめる | `src/a523_lead_time.py`、`src/02_lead_time_duckdb.sql`、`src/01_lead_time_tsql.sql`（T-SQL 版、未検証） |

## 主な結果（2025年受注の案件、2025/12/31 締め）
- **横ばい（2,901件、締めの日に未完了23.2%）**：本当の中央値61日、完了分だけ49日（−12日）、カプラン・マイヤー61日（0日）、2025年に完了した案件60.5日（−0.5日）
- **増えている（2年で3倍、3,913件、未完了27.7%）**：本当60日、完了分だけ47日（−13日）、カプラン・マイヤー60日、2025年に完了した案件54日（−6日）
- **減っている（2年で3分の1、2,239件、未完了21.3%）**：本当61日、完了分だけ49日（−12日）、カプラン・マイヤー61日、2025年に完了した案件63日（+2日）
- **受注月ごと（横ばい）**：完了分だけの中央値は、1月受注 62日（本当62日）から、9月 41日（本当65日）、11月 24日（本当51.5日）、12月 16.5日（本当61日、未完了92.5%）へ下がる
- **締めを後ろにずらすと（横ばい）**：30日後 −11日、90日後 −6日、180日後 −2日、360日後 −1日。長い案件が残るうちは0にならない
- 「完了分だけ」の短く出る分は件数の増減でほとんど変わらない（−12〜−13日）。「期間中に完了した案件」で数えるやり方は、件数が増えている時期に短く、減っている時期に長く出る
- SQL（DuckDB）で出した完了分だけの中央値と未完了の件数は、Python と一致

## データ
- `data/fictional_cases_flat_cut20251231.csv`：架空の案件（seed 523、横ばいの場合）を、締めの日に見える形にしたもの。列は received（受注日）・done_observed（締めの日までに終わっていれば完了日、終わっていなければ空）・lead_days_observed（同じく日数）。ほかの場合はスクリプトを動かすと作られる

## 注意（言えないこと）
- 架空のデータ。リードタイムの分布（対数正規、中央値60日、σ0.9）と件数の増え方は作成者が置いたもので、実際の会社の値ではない
- リードタイムの分布は時期によらず同じと置いた。実際に時期によって長さが変わる場合、どのやり方でもその変化と締めの影響が混ざる
- カプラン・マイヤーが本当の値とそろったのは、「終わるかどうかは締めの日と関係ない」という前提をこのデータが満たしているから。途中で取り消される案件や、締めの前に急いで終わらせる案件があると、この前提は崩れる
- 日数は整数の日で数えたので、中央値は0.5日きざみ
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。カプラン・マイヤーは Python で計算した
