# F162 公的データは「API で取れる」のか？ 記事の取得記録で作る、取り方の地図

note の記事「公的データは『API で取れる』のか？」（下書き）の分析コード・データ・図です。

## 問い
このリポジトリには、公的データを使った分析が377本あります（看板記事 F 158本、番号つきの通常記事 219本。コミット 8090888 時点）。各記事は、データを次のどれで取ってきたのでしょうか。
- API
- Excel・CSV・ZIP などのファイル
- 画面の操作
- PDF
- 手作業での書き写し

この記事では、それを統計の作り手（府省・機関）ごとに整理し、「取りやすさの地図」を作ります。

F69（データの欠点の点検）・F93（PDF の表の読み取り精度）とは重ならないよう、**取得の経路**に絞りました。記事の間でのデータの使い回しは F124 で扱ったので、ここでは「新しく取ったデータ」を選ぶために使うだけです。

## データ
- このリポジトリ（takayuki-0127/japan-open-data-notes、コミット 8090888）の `articles/*/` 377フォルダ
  - README の見出しに「データ」「取得」「出典」「再現」「動かし方」を含む節と、「出典」で始まる行
  - `src/` の取得用ファイル（`01_*`・`fetch*`・`*.md`）
  - `data/` の説明（`*.md`）
- これらを1行ずつ取り出しました（12,175行、`data/source_lines.csv.gz`）。
- `data/` に同梱したファイルの一覧も使います（`data/tree_data_files.csv`）。
- 新しく外部から取ったデータはありません。

## 手法
1. **作り手を決める**：行ごとに、府省・機関の名前、統計の名前、ドメインから、統計の作り手を決めます（21区分、`src/common.py` の `OWNERS`）。
   - e-Stat は「置き場所」として扱い、作り手には入れません。
   - 例：「厚生労働省『人口動態統計』（e-Stat）」は、作り手を厚生労働省とし、「e-Stat 経由」の印をつけます。
2. **経路を決める**：同じ行の URL、`data/raw/` のファイル名、言葉から、経路を決めます（`routes_of`）。1行に複数の経路があってもかまいません。

| 経路 | 判定の手がかり |
|---|---|
| API | URL に `/api`、`api.`、`datamapper/api` など。「API」という言葉（「使わない」「登録が要る」と書かれた行は除く） |
| 表ファイル | `.xlsx` `.xls` `.csv`、e-Stat の `file-download`・`statInfId`・`stat-search/files`、「Excel」「SheetJS」 |
| 一括ファイル | `.zip`、シェープ・GML・TopoJSON、国土数値情報、「全件データ」 |
| Webページの表 | パラメータつきのページ（`.php?` など）、`read_html`、「ページの表」 |
| 画面操作 | 開発者ツール・コンソール、画面での条件の指定、「ブラウザで実行・取得」、`api_get_result`、e-Stat の `dbview` |
| PDF | `.pdf`、「PDF」 |
| 手で転記 | 「書き写し」「転記」など |
| ページURLのみ | 案内ページの URL だけ（ファイルの形が書かれていない） |
| 記録なし | 経路の手がかりなし |

3. **記事×作り手の「組」にまとめる**：581組を作り、次の2つの経路を持たせます。
   - いちばん機械向きの経路（基本）
   - いちばん手間のかかる経路
4. **新しく取った組を選ぶ**：「F○○ で取得」「と同じ」のように他の記事を指す行と、出典の定型文（「〜を加工して作成」）を除きます。そのうえで、取得の手がかりがある行が残る組を「新規」とします（428組・314記事）。記事全体で「新しいデータは取っていない」と書かれた24記事は、すべて再利用とします。
5. **手作業で確かめる**：分類の規則を決めたあと、新しく40組を無作為に選びました。本文の行を読んで手で判定し、自動の判定と比べています（`data/validation_labels.csv`）。規則を決めるのに使った別の120組は含めていません。

## 頑健性（`results/robustness.csv`、図5）
分類の仕方を8通り変えると、各割合は次の範囲に収まりました。

| 割合 | 範囲 |
|---|---|
| ファイル | 56〜80% |
| API | 0〜4% |
| 画面・PDF・手で転記 | 2〜18% |
| 経路の記録なし | 17〜33% |

8通りの内訳：
- 手間のかかる経路で数える
- 再利用の組も含める
- 記事単位で数える
- F だけ
- 通常記事だけ
- e-Stat 経由だけ
- e-Stat 経由でないものだけ
- 基本

どの数え方でも、「ファイルが中心」「API はわずか」「4組に1組前後は経路の記録がない」は変わりませんでした。

**手作業の確認（40組）**：自動の判定との一致は85%（34組）でした。食い違いの6組は次のとおりです。
- 同じ行に2つの作り手が出て、経路が混ざった：2組
- ファイル名の `.pdf` を拾えなかった：1組
- HTML をたどった取得を「画面操作」とした：1組
- 統計地理情報システムからの取得を「記録なし」とした：1組
- 再利用を新規とした：1組

## 言えないこと
- これは「この記事群が実際にどう取ったか」の記録です。各統計に API があるかどうかの調べではありません。e-Stat API は、アプリケーションIDを登録すれば多くの表（データベース形式のもの）を取れますが、このシリーズでは登録しない方針だったため使っていません。「API がない」とは言えません。
- 経路は README とコードの文字から機械的に判定したもので、手作業の確認で約15%の食い違いがありました。作り手ごとの数が少ない行（日本銀行・警察庁・社人研など、5〜7組）の割合は大きくぶれます。
- 「経路の記録なし」は、取り方が書かれていないことを示すだけです。取り方が難しかったという意味ではありません。
- 作業の環境（コンテナから官公庁のサイトに直接つながらず、ブラウザ経由で取った回が多い）が、経路の選び方に影響しています。同じ統計でも、別の環境なら別の経路で取れた可能性があります。
- 作り手の区分は作成者が決めたものです。統計の実施府省と公表サイトが違う場合（例：社人研の資料集に載った国勢調査の値）、行の書き方によって作り手が変わることがあります。
