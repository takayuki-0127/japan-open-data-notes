# 492 Excel の日付のシリアル値を読み替えるとき、何日ずれるのか（実務の型）

Excel が日付を数字（シリアル値）で持つ決まりを Python で再現し、架空の日付1万行をシリアル値にしてから、よく見る5通りの読み替え方で日付に戻して、ずれた行と日数を数えたフォルダです。1904年基準のファイルが混ざった場合と、時刻つきの値から日付を取り出す場合も試しました。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A492 | シリアル値の読み替え方・基準の取り違え・時刻の丸めで、日付は何日・何行ずれるか | 1900年基準（1900/1/1 = 1、存在しない 1900/2/29 = 60 を数える）と1904年基準（1904/1/1 = 0）でシリアル値を作り、openpyxl の変換と一致を確認。5通りで日付に戻して元と比べる | `src/a492_serial_dates.py`、`src/01_serial_to_date_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
- **データ**：架空の日付1万行。9,800行は2015〜2026年、200行は1900年1〜2月（うち120行は「日付不明」の代わりの 1900/1/1）
- **①1899/12/30 起点**（pandas の origin='1899-12-30' など、よく使われる方法）：2015〜2026年の行は0日のずれ。1900年1〜2月の200行だけ1日早くなる
- **②1899/12/31 起点**（1 = 1900/1/1 をそのまま足す）：1900年3月以降の9,800行すべてが1日遅くなる
- **③1900/1/1 起点**（s 日後と読む）：1万行すべてずれる。3月以降は2日、1〜2月は1日遅い
- **④UNIX 時刻に直す**（(s−25569)×86400 秒）：①と同じ（1900年1〜2月の200行だけ1日早い）
- **⑤openpyxl の from_excel**：0行。存在しない 1900/2/29（60）は 1900/2/28 として返す
- **1904年基準のファイルを1900年基準として読む**：全行が1,462日（4年と1日）早くなる。2割が1904年基準のファイルから来た表では、2015〜2026年の1,984行がずれ、2011〜2014年に行が現れ、2023年以降の件数が2割前後少なく見える
- **時刻つきの値から日付だけを取る**（2万行、1割は23:59台）：切り捨ては0行。分に丸めてから取ると959行（4.8%）、四捨五入すると正午以降の10,963行（54.8%）が翌日になる

## 注意（言えないこと）
- Excel 本体では試していない（未検証）。シリアル値の決まりは公開されている説明と openpyxl の実装に合わせて Python で再現した
- LibreOffice・Google スプレッドシートの起点の扱いは試していない
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。SQL Server の datetime の起点（1900/1/1 = 0）は Excel と2日ずれる、という前提で書いた
- 書き方の混ざった日付の文字列は 427、CSV を Excel で開いたときの変化は 372 で扱った
