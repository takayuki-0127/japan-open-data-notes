# F247 データを集めて、使える形に整える ― 架空のスーパー「サンプルマート（架空）」で staging から mart まで

看板記事 F247（③ 業務の再現：架空の会社で、F246〜F255 の2本目）。F246 で KPI を決めた架空の食品スーパーのチェーンで、次の仕事として **現場から届くファイルを集め、分析に使える形（mart）に整える**ところを再現した。POS・勤怠・廃棄登録・会計の4つの元から届くファイルに、現場でよくある8種類の汚れを入れて合成し、SQL で staging → mart を作り、9つのテストで汚れを見つけ、F246 の KPI の数字と照合した。

- **会社・数字は架空（合成データ）。実在の会社とは関係がない。顧客（クライアント）のデータは使っていない。**

- 成果物：SQL `sql/10_staging.sql`・`sql/20_mart.sql`・`sql/30_tests.sql`、補正表 `sql/ref_fix_*.csv`、mart `mart/`、データ辞書 `docs/data_dictionary.md`

## 問い
現場から届くファイルは、そのままでは KPI の計算に使えない。どんな汚れがあり、どう整え、どうやって「整え終わった」と確かめるか。整える手当てを1つ抜くと、F246 で決めた KPI はどれだけ狂い、テストで気づけるか。

## 手法
- **SQL**：staging（`10_staging.sql`）→ mart（`20_mart.sql`）→ テスト（`30_tests.sql`）。書き方は SQL Server 互換（CTE・ROW_NUMBER・CASE・COALESCE・BETWEEN・SUBSTRING・YEAR/MONTH）にそろえたが、**この記事では DuckDB 1.5（Python から）で実行した。SQL Server そのものでは動かしていない。**
  - 再送：店コード×営業日ごとに送信日時の新しい1行だけ（ROW_NUMBER）
  - 遅れ：`run_param.cutoff` までに届いた行だけを使う（締めの再現）
  - 店コード：有効期間つきの対応表 ＋ 補正表（`ref_fix_store_code`）で店番に置き換える。置き換えられない行は捨てずに `q_pos_unmapped` に残す
  - 部門：有効期間つきの部門の対応表で元の7部門に戻す
  - 人時の空：同じ店・同じ月・同じ曜日の平均で埋め、`labor_imputed` の印をつける。人件費は 埋めた人時 × その店・月の時給
  - 廃棄の単位：補正表（`ref_fix_waste_unit`）の期間だけ ×1000
- **テスト**（どれも「問題の行の数」を返し、0 なら合格）：T01 キーの重複、T02 対応表にない店コード、T03 部門の参照、T04 店の参照、T05 欠けた日、T06 空の値、T07 部門の合計と店の合計、T08 会計との照合（店×月 0.1%）、T09 値の範囲（廃棄率 0.5〜6%、人時 > 0）。
- **流れ**：1回目は補正表なしで流し、テストの結果から補正表を2つ（3行）足して2回目を流す。
- **手当てを1つずつ抜く**：同じ処理を pandas でも書き（`src/03_整える.py` の `build_mart_pd`）、手当てを1つ抜いた10通り（＋全部抜いた素朴なもの）で mart を作り、FY2025 の KPI の正解とのずれと、どのテストが落ちるかを見た。
- **月次の締め**：営業日の翌月 1・3・5・10・20日までに届いた分だけで既存店の前年比を出し、確定（すべて届いたあと）とどれだけ違うかを見た。前年同月は確定の値を使う。

## 結果（seed 0）
- **1回目（補正表なし）**：T02 391 行（コード 1020 が 2025-04-01〜 366 日・7.45億円、9999 が 25 日・672万円）、T05 365 店×日、T08 12 店×月、T09 3 店×月（19店の 2025-06〜08 の廃棄率 0.004%）。**2回目（補正表あり）はすべて 0。**
- **正解との照合**：既存店売上 FY2025 25,817,692,832円（F246 は 25,817,692,839円、差は円の丸めの 7円）、既存店営業利益の前年比 −3.22%（正解 −3.20%、差 −0.02pt は人時を埋めた分）。全店売上 FY2025 270.38億円も一致。
- **SQL と pandas**：3つの mart で行数が一致し、値の差は最大 3.7×10⁻⁹。
- **手当てを1つ抜いたときの FY2025 の KPI のずれ**（正解との差）：

| 抜いた手当て | 既存店売上 | 既存店営業利益の前年比 | 全店売上 | その他 | 落ちたテスト |
|---|---|---|---|---|---|
| 再送を除かない | +0.67% | +1.24pt | +0.66% | 営業利益の水準 +15.7% | T01・T07・T08 |
| 締め5日の時点 | −0.55% | −0.10pt | −0.54% | | T05・T08 |
| 店コードを期間を見ずに結合 | **+95.9%** | −46.9pt | **+100%** | 廃棄率 +18.5pt | 5つ |
| 店コードを古い対応表だけで | −4.1% | **−463pt（営業利益が赤字に）** | ±0 | 廃棄率 +16.5pt | 4つ |
| 16店の新コードを補わない | ±0 | ±0 | **−2.7%** | | T02・T05・T08 |
| 9999 を除かない | ±0 | ±0 | +0.006% | | 5つ |
| 部門の付け替えを戻さない | ±0 | ±0 | ±0 | **惣菜の前年比 −41.2pt** | T03 のみ |
| 空の人時を0のまま | ±0 | −0.27pt | ±0 | 人時売上 +1.3%、営業利益の水準 +4.4% | T09 のみ |

- **どの汚れも少なくとも1つのテストで見つかった**。会計との照合（T08）が1つずつ抜いた9通りのうち6つを拾うが、部門の付け替え（T03）・人時の空と廃棄の単位（T09）は別のテストでしか見つからない。
- **月次の締め**：既存店売上の前年比があとで直る幅（12か月の絶対値の平均・最大）は、翌月1日 0.78pt・1.95pt、3日 0.64・1.70、5日 0.54・1.56、10日 0.26・0.71、20日 0。締めの時点の数字はいつも低めに出る（前年同月は確定しているため）。5日の締めで、その月の売上の届いた割合は平均 99.5%（最小 98.5%）。

## 頑健性
1. **乱数の種**：seed 0〜19 の20通りで届いたファイルを作り直しても、正しく整えたものは不合格のテスト 0、既存店売上の前年比と全店売上のずれ 0、営業利益の前年比のずれは最大 0.07pt（人時を埋めた分）。素朴なものはどれも9つすべて不合格、全店売上 +97.5%（最大 +97.8%）。
2. **汚れの割合 ×0.5・×2**（再送・遅れ・9999・人時の空、各5通り）：正しく整えたものは不合格 0・ずれ同じ。素朴なものの全店売上のずれは平均 +97.5〜97.6%、営業利益の前年比は平均 +8.3〜8.5pt で、割合を変えてもほぼ同じ（ずれの大部分は店コードの結合の誤りで、割合を変えた汚れとは関係がないため）。
3. **人時の埋め方**：同じ店・月・曜日の平均（採用）は埋めた日の人時の誤差 2.9%、中央値 3.0%、0 のままは人時売上 +1.29%・営業利益の前年比 −0.27pt、その日ごと落とすと既存店売上 −1.28%・営業利益の前年比 +0.62pt。
4. **SQL と pandas の照合**：seed 0 で一致（差 3.7×10⁻⁹）。seed 1〜4 でも SQL の流れで1回目は4つ不合格（約760行）、2回目はすべて 0。
5. **締めの日**：1・3・5・10・20日で比べた（上の結果）。

## 言えないこと
- **数字は架空の会社の合成データ**。汚れの種類と割合は筆者が置いたもので、実在のスーパーの POS・勤怠の品質を示すものではない。
- **ずれの大きさは、この会社の店コードの振り直し方などの設定しだい**。振り直しで店の大きさの順にコードを並べ替えたので、期間を見ない結合のずれが大きく出ている。
- **テストで見つけられるのは、テストを書いた汚れだけ**。ここでは汚れを知っていてテストを書いたので、9つで全部見つかるのは当たり前の面がある。知らない汚れ（売上の計上の仕方が途中で変わるなど）は、会計との照合（T08）で大きくずれたときにしか気づけない。
- 補正表の中身（16店の新コード、9999 がトレーニング用、19店の千円入力）は、実務では情報システム部や店に確認して決めるもの。ここでは確認できた前提で足した。
- 人時の埋め方は推測で、埋めた 460 店×日の人時は正解と平均 2.9% 違う。
- 廃棄登録には送信日時がないので、締めの再現は POS だけ。会員とネットスーパーのデータは F246 のものをそのまま渡し、この回では整えていない。
- SQL は SQL Server 互換の書き方にしたが、SQL Server では動かしていない。
