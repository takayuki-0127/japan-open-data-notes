# 762 申込率を小数の桁の少ない DECIMAL に入れると、率はどれだけ丸まり、店の順位はどれだけ入れ替わるのか（実務の型・SQL の数の型）

率を表に保存するとき、`DECIMAL(5,2)` のように小数の桁を決めた列に入れることがあります。率を「比」（0.0347 など）で持つと、小数2桁では0.01きざみ、つまり1ポイントきざみにしかなりません。申込率が数%の世界では、これは大きな丸めです。**ここでは、架空の80店の1か月の来店数と申込み数（申込率は0.8〜5.5%）で、申込率を桁の違う4つの DECIMAL の列に入れ、丸まり方と、店を申込率で並べたときの同点・順位の入れ替わりを数えました。** 申込率のばらつきは作成者が置いたもので、数字はその置き方で決まります。

|---|---|---|---|
| A762 | 率を小数の桁の少ない DECIMAL に入れると、どれだけ丸まり、順位はどう変わるか | 浮動小数（本当の値）、比で小数2桁 DECIMAL(5,2)・3桁 DECIMAL(6,3)・4桁 DECIMAL(7,4)、%で小数1桁 DECIMAL(5,1)。DuckDB（1スレッド）の CAST の結果を Python の四捨五入（ROUND_HALF_UP）と照らし合わせて一致を確認。seed 762 | `src/a762_decimal.py`、`src/02_decimal_duckdb.sql`、`src/01_decimal_tsql.sql`（未検証） |

## 主な結果
- **比を小数2桁で持つ**：80店の申込率が6つの値（1%・2%・…・6%）にまとまり、79店がほかの店と同じ値になった。いちばん多い値（3%）には26店が並ぶ。ずれは平均0.29ポイント、最大0.50ポイント（本当の率の32.7%）
- **上位10店が選べない**：小数2桁の値で並べると、同点のため「10位以内」に13店が入る
- **小数3桁（＝%で小数1桁）**：35の値、ずれは最大0.05ポイント（本当の率の4.3%）。それでも67店がほかの店と同じ値
- **小数4桁**：74の値、ずれは最大0.005ポイント（0.5%）、同じ値の店は12店
- **平均への影響は小さい**：丸めた値の平均と本当の平均の差は、小数2桁でも0.05ポイント。困るのは店ごとの比べ方

## 動かし方
```
pip install -r requirements.txt
cd src && python a762_decimal.py
```
数秒で終わります。`data/stores.csv` に来店数と申込み数を、`results/stored_rates.csv` に4つの型に入れた申込率を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- DuckDB の CAST の結果が、Python の Decimal で四捨五入した値と一致した
- DuckDB では DECIMAL どうしの割り算の結果は浮動小数（DOUBLE）になるので、桁が落ちるのは決まった桁の DECIMAL に入れるときだと確かめた
- T-SQL 版（`01_decimal_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）。SQL Server の decimal どうしの割り算の結果の桁の決まりは、ここでは試していない

## データ
- `data/stores.csv`：store_id・visitors・applications
- 仮定：来店数は2,000〜20,000、申込率は平均3.2%・標準偏差1.1%（0.8〜7%に収める）。申込み数は二項分布

## 注意（言えないこと）
- 架空のデータ。同点の多さは、率の大きさとばらつきで決まる
- ここで試した丸めは「入れるときに四捨五入」。切り捨てになる道具や設定では、ずれはもっと大きくなる（推測）
- 実在の店の数字ではない
