# 342 締めたあとに訂正されたデータで、先月のレポートの数字を再現できるか（実務の型）

架空の取引12か月分（約4万8千件）に、遅れて登録される行・金額の訂正・取消を入れ、3つの持ち方（上書き／今の値＋更新の履歴／いつ時点の値かを持つ）で、過去のレポートの数字を出し直せるかを数えたフォルダです。SQL は DuckDB で動かしました。T-SQL 版は `src/01_asof_tsql.sql` に置きましたが、**SQL Server 本体では動かしていません（未検証）**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A342 | レポートを出したあとに動いたデータから、当時の数字を再現できるか | 取引の4%が遅れて登録、4.9%が訂正、1.6%が取消。レポートは翌月の第5営業日に出したとし、2026-03-31 に12か月分を出し直す。A 上書き、B 今の値＋更新の履歴（訂正の時刻と前の値だけ）、B＋（登録時刻と取消の記録を足す）、C 行ごとに有効な期間を持つ | `src/a342_restate.py`、`src/01_asof_tsql.sql` |

## 主な結果
- **当時と同じ数字を再現できた月数（12か月中）：A 上書き 0、B 今の値＋更新の履歴 0、B＋ 12、C 12**
- 当時の数字とのずれ：A は平均1.1%・最大2.7%、B は平均0.8%・最大1.5%、C は0
- B で戻せなかったのは、遅れて登録された行（登録した時刻が残っていない）と、取消（行が消えている）
- レポートのあとに動いた金額は、増減を別々に足して当時の数字の平均2.8%、差し引きでは+1.1%
- 動いた金額の内訳：遅れて登録された行 60%、取消 23%、訂正（差し引き）18%。1か月あたりの行数は、遅れ 約56行、訂正 約85行、取消 約19行
- C の行数は、上書きの表の1.09倍

## 動かし方
```
pip install -r requirements.txt
cd src && python a342_restate.py
```
乱数の種を固定してあるので、実行のたびに同じ `results/`・`figures/` を出します。

## 確かめたこと
- 空のフォルダで流し直し、results・figures が一致した
- 「当時の数字」は、持ち方とは別に、できごとの記録（登録・訂正・取消の時刻つき）から直接計算した

## 注意（言えないこと）
- すべて架空のデータです。結果は、置いた訂正・取消・遅れの割合で決まります
- どの月にも訂正や遅れがあるように作ったので、上書きの表は0か月になりました。何も動かなかった月があれば、その月は再現できます
- マスタがあとから変わる場合は扱っていません（期間つきのマスタは 270 で扱いました）
- 行が増えることによる速さ・容量への影響は測っていません
- T-SQL 版と、SQL Server のシステムバージョン管理テーブル（`FOR SYSTEM_TIME AS OF`）は試していません
