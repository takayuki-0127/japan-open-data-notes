# 313 月の集計で、月末の最終日はどれだけ落ちているのか（実務の型）

架空の時刻つき取引（12か月）に、「ある月の売上」を出す9つの書き方を当て、落ちる行と余分に入る行を数えたフォルダです。SQL は T-SQL の書き方で `sql/month_filters.sql` に置き、DuckDB で実行して確かめました。**SQL Server 本体では試していません（未検証）**。`EOMONTH` と `DATEADD(hour, …)` は DuckDB の `last_day` と `+ INTERVAL` に書き換えて実行しています。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A313 | 月を絞る書き方ごとに、何%の行が落ち、何%が余分に入るか | 架空の取引30.7万件（2025年4月〜2026年3月、ミリ秒つきの日時、seed 313）。毎月1日 0:00:00 ちょうどの定期課金600件を含む。最終日の取引はふつうの日の2倍。9つの書き方を12か月に当て、正解（日本時間の半開区間を pandas で計算）と行単位で比べる | `src/a313_run.py`・`a313_figs.py`、`sql/month_filters.sql` |

## 主な結果
| 書き方 | 落ちた行（12か月平均） | 余分な行 | 正しかった月 |
|---|---|---|---|
| W1 `BETWEEN 初日 AND 最終日` | **6.2%** | 0 | 0/12 |
| W2 `BETWEEN 初日 AND 最終日 23:59:59` | 12か月で1行 | 0 | 11/12 |
| W3 `BETWEEN 初日 AND 翌月の初日` | 0 | **2.1%**（翌月1日 0:00:00 の定期課金600件） | 1/12 |
| W4 `<= EOMONTH(初日)` | 6.2% | 0 | 0/12 |
| W5 半開区間（`>= 初日 AND < 翌月の初日`） | 0 | 0 | 12/12 |
| W6 日付に直してから BETWEEN | 0 | 0 | 12/12 |
| W7 YEAR と MONTH で絞る | 0 | 0 | 12/12 |
| W8 半開区間を UTC の列にそのまま当てる | **2.8%** | **2.6%** | 0/12 |
| W9 UTC の列を日本時間に直してから半開区間 | 0 | 0 | 12/12 |

- W1・W4 は、最終日の 0:00:00 より後を全部落とす。月の合計は −5.9〜−6.8%。12か月を足すと年の合計の93.7%
- W3 は、翌月1日 0:00:00 ちょうどの行を今月にも入れる。月の合計は +1.1〜+1.2%（データの最後の月を除く）、12か月を足すと年の合計の101.05%（同じ行が2つの月に入る）
- W8 は、月初の0〜9時を落とし、翌月の0〜9時を入れる。毎月2.8%の行が隣の月と入れ替わるが、**月の合計の差は0.16%以内**（データの最後の月を除く）、12か月を足すと年の合計の99.88%で、ほぼ合って見える
- W2 が落とした1行は、最終日 23:59:59 のあとの1秒未満（ミリ秒）に入った取引
- 最終日の取引がふつうの日の1倍・2倍・3倍・5倍のとき、W1 が落とす行は 3.3%・6.2%・9.0%・14.2%

## 確かめたこと
- 空のフォルダで流し直し、results と figures の7ファイルがバイト単位で一致した
- 落ちた行・余分な行は、取引番号を1件ずつ正解と突き合わせて数えた

## 注意（言えないこと）
- 取引の時刻の分布、最終日の重み（2倍）、定期課金の件数は架空の置き方です。「6.2%」「2.8%」はこの置き方での数字です
- SQL Server の `datetime` 型は約3ミリ秒の刻みで値を持つため、`'… 23:59:59.999'` と書くと翌日の 0:00:00 に丸められると説明されています。これは試していません（未検証）
- W6・W7 は答えは合いますが、列に関数をかけるので索引が使われにくくなります（294 で扱いました）。速さはここでは測っていません
- 日本時間と UTC の差は9時間で固定です。夏時間のある地域の扱いは見ていません
- 233（合計が合わないとき）の「期間の端」を1本に広げた記事です
