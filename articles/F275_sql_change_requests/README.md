# F275 集計の SQL は、どう書けば直しやすく、直し忘れに気づけるか？（求人票の業務、精選モード）

架空の小売「みどりマート（架空）」の2年分の合成データで、月次の報告パッケージ8本（全社・店舗別・部門別・既存店前年比・客数と客単価・店舗×部門・KPI まとめ・直近月の日別）を、3つの書き方の SQL で作った。そこに、実務でよく来る8つの「定義の変更依頼」を当て、直す場所の数と、直し忘れたときにどのテストで気づけるかを数えた。
結果を見る前に計画（[PLAN.md](PLAN.md)、コミット 5beb93c）を置いた。

F244（よくある21の誤りとテスト）は「1本のクエリの書き間違い」を扱った。今回は「定義の変更と直し忘れ」を扱う。

## 問い

- 書き方によって、1つの変更依頼で直す場所の数はどれだけ違うか
- 直し忘れたとき、どのテストなら気づけるか
- 問い直し：定義を1か所にまとめると、そこを書き間違えたときの誤りは見つかるのか（計画には書いていない、あとから足した問い）

## データ

- 合成データ（`src/zz_f275_01_データ生成.py`、乱数の種 2751〜2755）。13店（うち1店はテスト店、3店は期間の途中で開店）、2024-04〜2026-03、レシート約13万件・明細約26万行・返品約5千行。ステータスに cancel（2%）と void（1%）、会員 ID は約4割が NULL
- 答え合わせ用の小さなデータ（`data/fixture_*`）：4店・レシート約350件。既存店の境目に当たる開店日の店、月末に売って翌月に返品、20日と21日の売上、void だけのレシート、同じ会員の同じ日の2回の来店、部門5・8、テスト店の売上を入れた。比べるため、境目のケースを入れない版（`fixture_plain_*`）も作った
- 実在の会社のデータは使っていない

## 3つの書き方（`sql/` に基準の SQL、`sql/*_changes.diff` に変更依頼ごとの差分）

| 書き方 | 中身 | 基準の行数 |
|---|---|---|
| S1 コピペ型 | 8本がそれぞれ、キャンセル除外・税・返品・既存店・月・テスト店・部門・客数の定義を式の中に直接書く | 248 |
| S2 CTE 型 | 各レポートの中を CTE で段に分けるが、定義のかたまりは各ファイルに書く（共有しない） | 270 |
| S3 共通ビュー型 | 定義を6つのビュー（line_ok・net・mon・comp_store・dept_grp・cust）に1回だけ書き、レポートはビューから読む | 114 |

S2 の CTE と S3 のビューは同じ文で、違いは「共有するかどうか」だけにした。SQL は日付関数を使わず（月はカレンダー表から引く）、整数の割り算と文字列の連結を使わない書き方で、DuckDB と SQLite で同じものが動く。sqlglot（T-SQL 方言）で270ファイルすべて解析エラーなし。ただし互換の保証ではない（sqlglot の T-SQL 方言は LIMIT・::・QUALIFY・ILIKE なども通す）。T-SQL にない構文は目で見て使っていない。SQL Server での実行はしていない。

## 変更依頼（8つ）

CR1 返品を元の売上日に計上 / CR2 既存店を13か月→12か月以上 / CR3 月を21日締めの会計月に / CR4 税込み→税抜き / CR5 テスト店を除外 / CR6 除外するステータスに void を追加 / CR7 部門のまとめ方の変更 / CR8 客数をレシート数→日ごとの会員の人数（会員 ID がないレシートは1枚を1人）

## テスト

- T1 レポート間の照合：R1 の月合計＝R2・R3・R6 の合計＝R5・R7 の売上、R8 の日別合計＝R1 の直近月
- T2 中の整合：既存店の売上 ≦ 全店、客単価×客数＝売上
- 本文の「照合」は T1＋T2 のこと。2年分の本番データで、ほぼ完全一致（相対誤差 1e-9）で比べた
- T3 R1 だけの答え合わせ（小さなデータで、pandas で別に計算した期待値と比べる）
- T4 全レポートの答え合わせ（同じ小さなデータで8本すべて）

期待値は SQL とは別に pandas で計算した（`src/zz_f275_spec.py`）。正しい版の SQL は、3様式×9版×8本のすべてで pandas と一致した（計1,824比較、不一致0。種 2751 は DuckDB と SQLite の両方で全版を本番・答え合わせ用データで、残りの種4通りは DuckDB で全版を答え合わせ用データで、基準の版だけを本番データでも比べた）。

## 手法

- 直す場所：変更前後の SQL の差分から、直したファイル数と行数（difflib）を数えた
- 直し忘れの変異：S1・S2 は、変更依頼が触るレポートのうち1本だけ古い定義のまま残した変異（46個）と、全部直し忘れた変異（8個）。S3 は直す場所が1つなので、全部直し忘れた変異（8個）だけ
- 変異の出力は、正しい版と基準の版の出力を組み合わせて作った（S1・S2 の各ファイルは単独で動くので、実行し直した場合と同じになる）
- ずれの大きさ：影響を受けたレポートで、正しい値との差 ÷ その列の正しい値の平均の大きさ（％）。前年比の列は差のポイント。キーが食い違う行は 0 との差として数えるので、100% を超えることがある

## 結果

| 仮説 | 基準 | 結果 | 判定 |
|---|---|---|---|
| H1 直すファイル数の中央値：S1 が S3 の3倍以上 | 3倍 | 8 対 1（8倍） | 支持（構造からほぼ決まる） |
| H2 S2 の直すファイル数は S1 の0.8倍以上 | 0.8倍 | 8 対 8（1.0倍）。行数は中央値 8 対 18 | 支持 |
| H3 S1 の1つだけ直し忘れのうち、T1＋T2 で見つかるのは70%未満 | 70% | 80.4%（46個中37個） | 外れ |
| H4 T4 は全様式の直し忘れの90%以上を見つける | 90% | 94.8%（116個中110個） | 支持 |

- 直す行の数（S1／S2／S3）：CR5 テスト店の除外 52／16／3、CR3 会計月 30／8／1、CR6 void 26／8／1、CR4 税抜き 24／8／1
- T1＋T2 をすり抜けた S1 の直し忘れ9個（T1 だけなら見つかったのは 76%）：既存店前年比（R4）の直し忘れ4つ（CR1・CR2・CR5・CR6）、KPI まとめの既存店（CR2 の R7）、部門のまとめ方（CR7 の R3・R6）、客数（CR8 の R5・R7）。合計を変えない変更や、どこにも突き合わせていないレポートの直し忘れは、照合ではつかまらない
- すり抜けたときのずれ：前年比で最大 7.3 ポイント（CR2）、部門別の売上は部門の行そのものが入れ替わる（CR7）、客数は 0.9%
- T4 が見逃した6個は、どれも R8（直近月の日別）の直し忘れ（CR1・CR5・CR6 の S1・S2）。答え合わせ用のデータの直近月に、返品・テスト店・void の行がなかった
- 注：S2 の結果は S1 とすべて同じで、S3 の全部直し忘れも出力は S1 と同じ。重なりを除くと54通りで、T4 は51通り（94.4%）
- T3（R1 だけの答え合わせ）は、全部直し忘れの 62.5% を見つけたが、1つだけ直し忘れでは 10.9%

## 頑健性

- 乱数の種5通り：T1＋T2 はどれも 80.4%、T4 は 93.5〜95.7%
- SQLite：結果は DuckDB と同じ（正しい版の不一致0、検出率も同じ）
- 照合の許容を 0.5% にすると、T1＋T2 は 65.2% に下がる（返品の計上月がずれても月の合計のずれは最大 0.49% で、CR1 の直し忘れ7個がすべて許容の内に入る）
- レポートを5本（R1〜R5）にすると、T1＋T2 は 28個中22個（78.6%）、T4 は28個すべて
- 各場所を20%ずつ独立に直し忘れる（変更依頼ごとに200回、S1・S2）：直し忘れがあった S1 の1,040回で T1＋T2 は 77.1%、T4 は 98.4%
- 計画になかった確かめ：境目のケースを入れない答え合わせ用データでは、T4 は 74%（S1・S2 の1つだけ直し忘れ）〜75% に下がる。テスト店の除外（CR5）と客数の数え方（CR8）の直し忘れは1つも見つからなかった（ふつうのデータにはテスト店も、同じ会員の同じ日の2回の来店もほとんど入らないため）

## 問い直し：定義を1か所にまとめると、そこを書き間違えたときに気づけるか

基準の SQL に4種類の書き間違い（B1 キャンセルの除外漏れ、B2 返品の結合キー不足、B3 既存店の境目 <= を <、B4 客数で明細のないレシートも数える）を入れた。S1・S2 は1ファイルずつ（20通り）、S3 は共通のビューに（4通り）。

| | T1＋T2 で見つかった | T4 で見つかった | 数字が変わったレポートの数（平均） |
|---|---|---|---|
| S1（1ファイル） | 14/20（70%） | 18/20（90%） | 1 |
| S2（1ファイル） | 14/20（70%） | 18/20（90%） | 1 |
| S3（共通ビュー） | 0/4（0%） | 4/4（100%） | 5（B1・B2 は8本すべて） |

共通ビューの書き間違いは全レポートにそろって入るので、レポートどうしを突き合わせても食い違いが出ない（4種と少なく、構造からほぼ決まる結果）。見つけられるのは、正しい答えと比べる答え合わせだけだった。コピペ型でも、同じ誤りを全ファイルに写せば同じく照合では見つからない。違いは、誤りがそろって入りやすいかどうか。S1・S2 で照合が見逃した6通り（B1・B2 の R4、B3、B4）は、本題と同じ「突き合わせていない」「合計を変えない」場所だった。S1・S2 で T4 が見逃した2つは、どちらも R8 の書き間違い（上と同じく、答え合わせ用データの直近月にキャンセル・返品の行がない）。

## 計画からのずれ

- ずれの大きさの測り方を、計画では決めていなかった。「その列の正しい値の平均の大きさに対する％」にした（キーが食い違う行があると 100% を超える）
- 境目のケースを入れない答え合わせ用データでの確かめ（上の頑健性の最後）と、問い直しの書き間違いの実験は、計画にない追加
- 図は5枚（計画では枚数を決めていない）


確かめ：src だけを別のフォルダに写して全部を流し直すと、data・sql・results・figures の150ファイルのうち149がバイト単位で一致した。違ったのは results/B_mutants.csv のずれの大きさの列の小数13桁目だけ（DuckDB が並列で足し算するため）で、判定の列はすべて同じ。

リポジトリには答え合わせ用データ（`data/fixture_2751/`）だけを置いた。本番用データは 01 で作り直せる。

## 言えないこと

- 架空のデータと、作者が決めた8本のレポート・8つの変更依頼・4つの書き間違いでの結果。実務の SQL の書き方や変更依頼の分布は測っていない
- H1・H2 の「直すファイル数」は、書き方の構造からほぼ決まる。数えて確かめたのは、行数と、直し忘れたときの気づきやすさ
- 答え合わせ（T4）の強さは、答え合わせ用データに境目のケースをどれだけ入れたかで決まる。今回は直近月のケースが足りず、R8 の直し忘れを見逃した
- 境目のケースは今回の8つの変更依頼を知ったうえで入れた。事前に知らない変更では、境目なしの74%のほうが近い可能性がある（推測）
- T4 は正しい答えの計算（pandas）も新しい定義に直す前提で、その手間と直し忘れは測っていない
- 変異はファイル単位だけ。コピペ型でいちばん起きやすいと思われる「1ファイルの中の一部だけの直し忘れ」は試しておらず、もっと見つけにくい可能性がある（推測）
- SQL と変更依頼はスクリプト（sqlgen.py）で作ったので、直す行の数は整形に左右される
- 「直しやすさ」のうち、読みやすさ・実行の速さ・権限の管理・ビューを変えたときの影響の確認（どのレポートが使っているか）は測っていない
- SQL Server では実行していない（構文解析のみ）。部門名などの日本語の文字列は、SQL Server では N'...' で書く必要がある。0で割ったとき DuckDB・SQLite は NULL を返すが、SQL Server はエラーになる（R4 の前年比、R5 の客単価）
