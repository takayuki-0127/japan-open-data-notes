# PLAN：F275 集計の SQL を、直しやすく・直し忘れに気づける形にするには？

（精選モード D. 求人票の業務 Q35。結果を出す前に書いた計画。2026-11-11）

## 問い

月次の報告パッケージ（全社・店舗別・部門別・既存店前年比・客数と客単価など）を SQL で作っていると、
「返品の計上日を変える」「既存店の定義を12か月にする」「会計月を21日締めにする」といった**定義の変更依頼**が何度も来る。
同じ定義が何本ものクエリに書かれていると、1か所だけ直し忘れて、レポートどうしで数字が食い違ったまま出てしまう。

- 書き方（構造）によって、1つの変更依頼で直す場所の数はどれだけ違うか？
- 直し忘れたとき、どのテストなら気づけるか？

F244（よくある21の誤りとテスト）は「1本のクエリの書き間違い」を扱った。今回は**定義の変更と直し忘れ**、つまり「直しやすさ」を扱う。F247 のマートは作り方の例で、変更の受け止め方は測っていない。

## データ

架空の小売「みどりマート（架空）」の2年分（2024-04〜2026-03）の合成データ（乱数の種を固定）。
レシート明細・返品・レシート（会員ID、NULL あり）・店舗（開店日、テスト店フラグ）・商品・部門・カレンダー。
カレンダー表に暦月と21日締めの会計月を持たせ、SQL では日付関数を使わない（SQL Server・DuckDB・SQLite で同じ SQL が動くようにするため）。

## 比べる書き方（3つ）

- **S1 コピペ型**：8本のレポートが、それぞれ定義（キャンセル除外、税の扱い、返品、既存店、月の切り方、テスト店除外、部門のまとめ方、客数の数え方）を式の中に直接書く
- **S2 CTE 型**：各レポートの中を CTE で段に分けて読みやすくするが、定義は各ファイルに書く（共有しない）
- **S3 共通ビュー型**：定義を共通のビュー（明細の正味、月、既存店、部門の対応、客数）に1回だけ書き、レポートはビューから読む

レポートは8本：R1 全社月次、R2 店舗別月次、R3 部門別月次、R4 既存店前年比、R5 客数・客単価、R6 店舗×部門、R7 KPI まとめ、R8 直近月の日別。

## 変更依頼（8つ）

CR1 返品を元の売上日に計上 / CR2 既存店を13か月→12か月以上 / CR3 月を21日締めの会計月に / CR4 税込み→税抜き /
CR5 テスト店を除外 / CR6 除外するステータスに 'void' を追加 / CR7 部門のまとめ方の変更 / CR8 客数をレシート数→会員の延べ人数（日ごとの会員ID、NULL はレシート）

## 測るもの

1. **直す場所の数**：各変更依頼を各様式で実際に SQL に当て、変更前後の差分から「直したファイル数」と「直した行数」を数える
2. **直し忘れの変異**：S1・S2 では、変更依頼が触るファイルのうち1つだけ古い定義のまま残した変異を全部作る（全部直し忘れた変異も作る）。S3 は直す場所が1つなので「全部直し忘れ」だけ
3. **テスト**（すべて自動）
   - T1 レポート間の照合：R1 の月合計＝R2・R3・R6 の合計＝R7・R5 の売上、R8 の日別合計＝R1 の直近月
   - T2 中の整合：既存店の売上 ≤ 全店、客単価×客数＝売上
   - T3 R1 だけの答え合わせ：小さなデータ（境目のケース入り）で R1 の期待値と比べる
   - T4 全レポートの答え合わせ：同じ小さなデータで8本すべての期待値と比べる
   - 期待値は SQL とは別に pandas で作る（新しい定義で）
4. 変異で数字がどれだけずれるか（本番の2年分のデータで、影響を受けたレポートの最大のずれ％）

## 仮説と「外れ」の基準

- **H1**：変更依頼1つあたりの「直すファイル数」の中央値は、S1 が S3 の3倍以上。→ 3倍未満なら外れ
- **H2**：S2（CTE で整理しただけ）の「直すファイル数」の中央値は、S1 の0.8倍以上（CTE だけでは直しやすさは変わらない）。→ 0.8倍未満なら外れ
- **H3**：S1 の「1つだけ直し忘れ」の変異のうち、T1＋T2（レポート間の照合と中の整合）で見つかるのは70%未満。→ 70%以上なら外れ
- **H4**：T4（全レポートの答え合わせ）は、全様式の直し忘れの変異の90%以上を見つける。→ 90%未満なら外れ

## 頑健性（少なくとも3つ）

1. データの乱数の種を5通り
2. エンジンを DuckDB と SQLite の両方で（同じ SQL）
3. 照合の許容誤差：完全一致 と 0.5%
4. レポートを5本に減らす（R1〜R5）
5. 直し忘れの作り方：「1つだけ」ではなく、各場所を20%ずつ独立に直し忘れる（種を変えて200回）

SQL Server：同じ SQL を sqlglot で T-SQL として構文解析できるかを確かめる（SQL Server での実行はしない）。

## 言えないことの予定

- 架空のデータと、作者が決めた8本のレポート・8つの変更依頼での結果。実務の書き方の分布は測っていない
- S3 の「直す場所が1つ」は構造からほぼ決まる。測る価値があるのは、直し忘れたときの気づきやすさのほう
