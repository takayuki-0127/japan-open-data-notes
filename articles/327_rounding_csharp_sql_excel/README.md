# 327 C# の Math.Round と SQL Server の ROUND と Excel の ROUND は、同じ答えを返すのか（実務の型）

3つの丸め方（四捨五入＝0から遠いほうへ／偶数丸め／切り捨て）を Python の10進数で再現し、架空の金額10万件に当てて、答えが違う件数と合計の偏りを数えたフォルダです。**C#・SQL Server・Excel の本体では動かしていません（未検証）。公開されている仕様を再現したものです。**

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A327 | 同じ金額を丸めたとき、丸め方によって何件の答えが違い、合計はどれだけ偏るか | 単価×数量×掛け率（0.5〜1.1、返品5%）の架空の金額10万件を、円未満で丸める。SQL Server の `ROUND`（DECIMAL）と Excel の `ROUND` は「0から遠いほうへ」、C# の `Math.Round`（既定）は偶数丸め、SQL Server の `ROUND(x,0,1)` と Excel の `ROUNDDOWN` は切り捨てとして再現。別に、小数第3位が5の値10万件を小数第2位に丸め、10進の型と2進の小数（double）の違いを見る | `src/a327_rounding.py`、`sql/01_round_tsql.sql` |

## 主な結果
- 10万件のうち、円未満の端数がある行は18.5%、ちょうど0.5で終わる行は3.2%（掛け率0.85と0.95の行だけ）
- 答えが違う件数：四捨五入と偶数丸め 1,508件（1.5%）、四捨五入と切り捨て 10,174件（10.2%）、偶数丸めと切り捨て 8,666件（8.7%）
- 丸める前の合計（279,482,971.36円）との差：四捨五入 +1,211円、偶数丸め −133円、切り捨て −7,971円
- 負の金額（返品）で、「0から遠いほうへ」と「0.5を足して切り下げ」（JavaScript の `Math.round` の形）が違ったのは154件
- 小数第2位への丸め（小数第3位が5の値10万件）：10進の型どうしでも、偶数丸め（C# の decimal）と四捨五入（SQL Server の DECIMAL）は50.2%で違う。合計は四捨五入が+500.00、偶数丸めが−1.91
- 2進の小数（double）に100を掛けると、13.4%の値で「ちょうど .5」にならなかった。C# の `Math.Round(double, 2)` の形（掛けて偶数丸めして割る）は、C# の decimal の偶数丸めと6.7%で違う答えになった
- 例：1.005 → SQL Server・Excel は 1.01、C#（decimal・double とも）は 1.00。−2.5 → SQL Server・Excel は −3、C# は −2

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- 金額は Python の `decimal` で持ち、丸める前の値に小数の誤差が入らないようにした

## 注意（言えないこと）
- **C#・SQL Server・Excel の本体では1回も動かしていません。** 各製品の丸めは、次の理解にもとづく再現です：SQL Server の `ROUND`（DECIMAL）は0から遠いほうへ、第3引数が0以外なら切り捨て。C# の `Math.Round` は既定が偶数丸め（`MidpointRounding.ToEven`）。Excel の `ROUND` は0から遠いほうへ
- C# の `Math.Round(double, 桁)` は「10の桁乗を掛け、丸め、割る」形で再現しました。.NET の版によって中の計算が違う可能性があります
- Excel は「有効15桁の10進に直してから四捨五入」と置きました。この置き方のため、Excel の列は SQL Server の DECIMAL と必ず同じになります。実際の Excel の動きは確かめていません
- SQL Server の `ROUND` に FLOAT を渡したときの動きは扱っていません
- 件数と偏りの大きさは、掛け率の置き方で決まります（ちょうど0.5が出るのは0.85と0.95の行だけ）。割合そのものは一般の数字ではありません
- どの丸め方を使うべきかは、取引の決まりや社内の決まりによります。ここでは助言しません
