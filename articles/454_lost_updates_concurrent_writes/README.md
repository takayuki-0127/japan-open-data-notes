# 454 2つの処理が同時に同じ行を書き換えると、何件の更新が消えるのか（実務の型）

架空の在庫の表（500行）に更新2万件を流し、「読んでから書く」「1文の UPDATE で足し引きする」「版番号を確かめてから書く」の3つの書き方で、消えた更新の数・最後の在庫のずれ・やり直しの回数を数えたフォルダです。330（2回取り込んでも二重にならない形）・359（累計）とは別に、同時の書き換えだけを扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A454 | 同時に動く処理があるとき、書き方によって更新は何件消えるか | 処理の重なりを乱数で作るシミュレーション（到着はポアソン、読んでから書くまでの時間は指数分布、20回の平均）。同時に動く数・処理の時間・行の数と集まり方を変える。SQLite の2つの接続で「読む→読む→書く→書く」の順を実際に流して確かめる | `src/a454_lost_updates.py`、`src/01_three_ways_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
基本の場面：更新2万件、500行（一部の行に集まる）、毎秒50件、読んでから書くまで平均0.05秒（同時に動く処理は平均2.5本）

| 書き方 | 消えた更新 | 最後の在庫が合わない行 | やり直し（更新1件あたり） |
|---|---|---|---|
| 読んでから書く | 7.1%（20回で6.7〜7.4%） | 10.8% | 0 |
| 1文の UPDATE で足し引きする | 0% | 0% | 0 |
| 版番号を確かめてから書く | 0% | 0% | 0.095回 |

- **同時に動く処理の数（読んでから書く）**：平均0.1本で0.4%、0.5本で1.7%、1本で3.3%、2.5本で7.1%、5本で12.0%、10本で18.6%、20本で26.6%
- **版番号のやり直し**：同じ順に、更新1件あたり 0.004・0.018・0.037・0.095・0.199・0.427・0.923回
- **処理の時間（毎秒50件のまま）**：0.005秒で0.9%、0.02秒で3.3%、0.05秒で7.1%、0.2秒で18.6%、1秒で38.6%
- **行の数と集まり方（読んでから書く、消えた更新）**：

| 行の数 | どの行も同じ割合で更新 | 一部の行に集まる |
|---|---|---|
| 50 | 4.8% | 14.6% |
| 500 | 0.5% | 7.1% |
| 5,000 | 0.06% | 4.2% |
| 50,000 | 0.007% | 2.8% |

- **SQLite で実際に流す**：在庫100から、A が −3、B が −5 を「読む→読む→書く→書く」の順で流すと、読んでから書く形は 95（A の −3 が消える）、1文の UPDATE は 92、版番号を確かめる形は B の1回目が0行になり、読み直して 92

## 確かめたこと
- 空のフォルダで流し直し、results・figures が一致した
- SQLite の結果が 95・92・92 になること（コード内の assert）

## データ
- データのファイルはない。シミュレーションの設定と乱数の種はコードの中にある（seed 454）

## 注意（言えないこと）
- シミュレーションは、読むときにも書くときにも待たされない（ロックで止まらない）という前提。実際のデータベースでは、分離レベルやロックの設定で、待たされたりエラーになったりする
- 「一部の行に集まる」は、行の番号 k が選ばれる割合を 1/k に比例させたもの
- 「消えた更新」は、最後の値に入っていない更新の数。足し引きが打ち消し合うと、更新が消えていても最後の在庫は合うことがある
- 版番号のやり直しは、やり直しのたびに読み直し、同じ分布の時間をかけて書き直す形。やり直しの回数に上限は置いていない
- SQLite での確認は、2つの接続を順番に動かしたもの。本当に同時に動かした試験ではない
- SQL Server のロック・分離レベル・ROWVERSION は試していない（未検証）。T-SQL 版も SQL Server 本体では動かしていない
