# 663 ウィンドウ関数の PARTITION BY を書き忘れると、店ごとの累計や順位はどれだけ狂うのか（実務の型・SQL の落とし穴）

SQL のウィンドウ関数（`SUM() OVER`・`AVG() OVER`・`LAG()`・`RANK()`）は、`PARTITION BY` で「どの単位ごとに計算するか」を決めます。書き忘れると、表全体がひとつの単位として計算されます。エラーは出ず、もっともらしい数字が返ってきます。**ここでは、架空の20店の日別売上（2025年1〜3月の90日、1,800行）で、4つのウィンドウ関数を PARTITION BY あり・なしで出し、ずれた行の数とずれの大きさを数えました。** 店の売上の大きさは作成者が置いたもので、ずれの大きさはその仮定で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A663 | PARTITION BY を書き忘れると、どの関数で何行ずれるか | 店ごとの累計（SUM OVER）、7日の移動平均（AVG OVER ROWS 6 PRECEDING）、前日の売上（LAG）、その日の店の順位（RANK）を、PARTITION BY あり・なしで比べる。GROUP BY（自己結合）で出した累計とも比べる。DuckDB（1スレッド）と pandas で一致を確認。seed 663 | `src/a663_window.py`、`src/02_window_duckdb.sql`、`src/01_window_tsql.sql`（未検証） |

## 主な結果
- **累計は1,800行すべてがずれた**：`ORDER BY 日付` だけだと、その日までの全店の合計になる。1店の累計の何倍かは中央値21.4倍、最大70.9倍（売上の大きい S05 でも、3月末で11.7倍）
- **その日の順位は1,799行がずれた**：日ごとの1〜20位ではなく、1,800行の中の1〜1,800位になる
- **7日の移動平均は114行（6.3%）がずれた**：`ORDER BY 店, 日付` で並べていると、各店の最初の6日だけに前の店の売上が混ざる。ずれは最大310%、1日目で中央値43%
- **前日の売上は19行（1.1%）がずれた**：各店の1日目に、前の店の最終日の売上が入る（本当は空）。その行の前日比は-76%〜+211%
- **GROUP BY（自己結合）で出した累計は、PARTITION BY ありと一致した**
- 全行がずれるものは見て気づきやすいが、店の境目だけがずれるもの（移動平均・前日）は、合計や平均ではほとんど目立たない

## 動かし方
```
pip install -r requirements.txt
cd src && python a663_window.py
```
数秒で終わります。`data/daily.csv`（store_id・sale_date・sales）を書き出し、`results/window_compare.csv.gz` に全行の比較を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 4つの関数のあり・なしと、GROUP BY の累計が、DuckDB と pandas で一致した
- T-SQL 版（`01_window_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- 仮定：20店の1日の売上の水準は対数正規（中央値30万円、店ごとに11万〜61万円）。曜日の波（土曜が1.2倍）と、日ごとの誤差（12%）を置いた

## 注意（言えないこと）
- 架空のデータ。実際の店の数字ではない
- ずれの大きさは、店の数と、隣り合う店の売上の差で決まる。ずれる行の数は、PARTITION BY がないときの並べ方（ORDER BY）で変わる
- `ORDER BY 日付` だけで同じ日の行が並ぶと、SUM の既定の枠（RANGE）は同じ日の全行をまとめて足す。LAG や ROWS の枠では、同じ日の中の順番が決まらず、流すたびに結果が変わることがある（ここでは使っていない）
