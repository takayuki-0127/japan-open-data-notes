# 280 週次の数字を毎週メールで自動配信するとき、いつ送るか（実務の型）

週次 KPI のメール（HTML＋テキスト、推移の小さな図を埋め込み）を Python で作り、**送る前に集計がそろったかを確かめる**形を試したフォルダです。メールはファイル（`.eml`）に書き出すだけで、**送信はしていません**。あわせて、送る時刻の決め方3つで「先週の数字がそろう前に送ってしまう週」の割合を、集計の終わる時刻の架空の前提で数えました。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A280 | 週次メールを自動で送るとき、決まった時刻に送るのと、そろったか確かめてから送るのとで何が違うか | 送る前の確認の SQL（最新の週と行数）、集計の終わる時刻の想定（架空）と 2,000年ぶんのシミュレーション、`email.message` で HTML メールを作って読み戻して確認 | `sql/01_freshness.sql`、`src/a280_make_data.py`・`a280_send_rules.py`・`a280_email.py`・`a280_preview.py` |

## 主な結果
- 集計はふだん月曜の6:30前後に終わり、10%の週は前のシステムの遅れで1〜5時間ずれる、と置いた（架空の前提）
- **A：毎週7:00に決め打ちで送る** → 14.3%の週で、先週の数字がそろう前に送ってしまう（遅れる週が5%なら9.5%、20%なら23.7%）
- **B：毎週9:00に送る** → 6.2%に減るが、毎週2時間遅く届く
- **C：7:00に確かめ、そろっていなければ30分おきに確かめ直す** → そろう前に送る週は0。届く時刻の平均は7:18、9割の週は7:30までに届く。12:00 までにそろわない週（0.01%）は「遅れています」の知らせだけを送る
- 送る前の確認の SQL は、最後の週の行が4つそろうと `OK`、最後の週が入っていないと `WAIT` を返すことを確かめた（DuckDB で実行）
- 書き出したメール（15.1KB）を読み戻すと、テキストと HTML の2つの形と PNG 1枚。HTML の中の画像の参照（cid）は添付と一致し、テキストと HTML に出てくる13個の数字はすべて同じ。`<style>` は使わず、見た目はすべて要素ごとの style で付けた（メールソフトは `<style>` を消すことがあるため）

## 動かし方
```
pip install -r requirements.txt
cd src && python a280_make_data.py && python a280_send_rules.py && python a280_email.py && python a280_preview.py
```
`a280_email.py` の `send()` は、既定（`dry_run=True`）ではファイルに書くだけです。送信のコードはこのフォルダにはありません。

## データ
- `data/weekly_kpi.csv`：架空の会社の週次 KPI（4つ × 2025年の52週）。作成者が乱数で作成（seed 280）
- `data/ready_time.csv`：各週の集計が終わった時刻（架空）
- `output/weekly_2025-12-29.eml`：書き出したメール（宛先・差出人は `example.invalid`）
- `results/send_rules.json`・`send_rules_sensitivity.csv`・`email_checks.json`

## 注意
- 14%・18分という数は、集計が終わる時刻の置き方（ふだんの時刻・ばらつき・遅れる週の割合と長さ）で決まります。遅れる週の割合は 5%・10%・20% で試しました。言えるのは「決め打ちの時刻は、遅れる週の分だけ古い数字を送る。確かめてから送れば、遅れはその週だけで済む」という向きまでです
- この記事の1年（52週）では遅れた週が1回だけで、7:00 に送ると2週、9:00 なら1週で古い数字を送っていました
- メールの見た目は Chromium で HTML を開いた画像です。メールソフトごとの表示は確かめていません
- 送信の部分（SMTP の設定・認証）は扱っていません
