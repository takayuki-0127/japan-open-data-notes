# 715 取り込み元に同じキーが2行ある状態で MERGE（UPSERT）すると、何件の値が意図と違う行で上書きされるのか（実務の型・SQL の取り込み）

更新ファイルを顧客表に取り込むとき、ファイルに同じ顧客が2行あると、どちらの値が残るかは書き方とファイルの並びで決まります。エラーで止まる書き方もあれば、黙ってどちらかを残す書き方もあります。**ここでは、架空の顧客表5,000人と更新ファイル1,500行（うち250人は古い変更と新しい変更の2行）で、ファイルの並びを3通りに変え、DuckDB の3つの書き方で取り込んで、最新でない値が残った人数を数えました。** 重複の数と並びは作成者が置いたもので、数字はその置き方で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A715 | 重複のある更新ファイルで、どの書き方が何人の値を古いまま残すか | A そのまま INSERT … ON CONFLICT DO UPDATE、B ROW_NUMBER で最新の1行に絞ってから同じ更新、C MERGE INTO。並びはばらばら・時刻の古い順・新しい順。DuckDB 2.0（1スレッド）。seed 715 | `src/a715_upsert.py`、`src/02_upsert_duckdb.sql`、`src/01_merge_tsql.sql`（未検証） |

## 主な結果
- **そのまま ON CONFLICT DO UPDATE（A）**：エラーにならず、ファイルで **先に出た行** が残った。2行ある250人のうち、ばらばらの並びで **126人**、時刻の古い順で **250人全員**、新しい順で0人が古いランクのまま
- **最新の1行に絞ってから（B）**：どの並びでも0人
- **MERGE INTO（C）**：「同じ行を2回以上更新しようとした」というエラーで止まり、何も更新されない
- **先に重複を調べる SQL**（GROUP BY … HAVING COUNT(*) > 1）で、250人を見つけられた

## 動かし方
```
pip install -r requirements.txt
cd src && python a715_upsert.py
```
数秒で終わります。`data/customers.csv`（顧客表）と `data/updates.csv`（ばらばらの並びの更新ファイル）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- A の結果が「ファイルで先に出た行の値」と一致することを pandas で確かめた。これは DuckDB 2.0.0・1スレッドで見た動きで、決まりとして保証されたものではない。版やスレッド数で変わることがある
- B の結果が、すべての顧客で最新の値になっていることを確かめた
- T-SQL 版（`01_merge_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）。SQL Server の MERGE も重複でエラーになるとされるが、確かめていない

## データ
- `data/customers.csv`：customer_id・rank_code・updated_at
- `data/updates.csv`：customer_id・rank_code・updated_at・file_row
- 仮定：更新ファイルの1,250人（うち67人は新規）。250人は2行目を持ち、2行目は1行目より5分〜3日後で、ランクが違う

## 注意（言えないこと）
- 架空のデータ。古い値が残る人数は、重複の数とファイルの並びで決まる
- 「最新の1行」は updated_at で決めた。時刻が同じ行は file_row の後ろを最新とした。何を最新とするかは、データの作り方で決める
- 実在の会員制度の数字ではない
