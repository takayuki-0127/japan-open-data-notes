# 465 サーバーごとに時計がずれていると、ログの出来事の順番は何件逆になるのか（実務の型）

架空のアクセスログ（5,000人、約4万件の出来事、サーバー4台）で、サーバーごとに時計がずれているとき、記録された時刻で並べると出来事の順番がどれだけ入れ替わるかを数えたフォルダです。313（月末・UTC）・403（並びの指定なし）とは別に、時計のずれによる順番の入れ替わりだけを扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A465 | 時計のずれの大きさごとに、順番が逆になる割合、「最初の出来事」「購入の直前の出来事」が変わる人の割合、間隔がマイナスになる件数。並べ方・記録のしかたで変わるか | 本当の時刻が分かるログを乱数で作り、サーバーごとのずれを足して記録の時刻にする。①記録された時刻で並べる ②受け取った順の通し番号で並べる ③同じ人は1台で記録する、の3つを比べる（各10〜30回の平均） | `src/a465_clock.py`、`src/01_event_order_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
基本の場面：1人4〜12件の出来事、出来事の間隔は35%が1秒未満（中央値4秒）、サーバー4台。出来事ごとに、4台のどれかがくじで記録する

| 時計のずれ（標準偏差） | となりの出来事の順が逆 | 最初の出来事が変わった人 | 購入の直前が変わった人 | 並びが1か所でも変わった人 | 間隔がマイナスの件数 |
|---|---|---|---|---|---|
| 0秒 | 0% | 0% | 0% | 0% | 0 |
| 0.1秒 | 1.3% | 1.3% | 2.6% | 8.9% | 469 |
| 0.5秒 | 7.5% | 8.2% | 15.0% | 41.6% | 2,629 |
| 1秒 | 10.3% | 11.7% | 20.1% | 53.2% | 3,611 |
| 2秒 | 13.4% | 16.0% | 26.4% | 63.8% | 4,711 |
| 5秒 | 19.1% | 24.7% | 37.6% | 77.6% | 6,703 |

- 30回の平均。件数は、出来事約4万件（となりの組は約3.5万組）のうち
- **間隔の長さ**：ページを読む間隔の中央値を2秒・8秒・40秒に変えると、ずれ1秒で順が逆になる割合は14.0%・10.3%・8.9%。間隔が長くても、1秒未満の続けての操作が35%あるので、あまり下がらない
- **並べ方・記録のしかた**（ずれ1秒、30回の平均）：

| 指標 | ①記録された時刻で並べる | ②通し番号で並べる | ③同じ人は1台で記録する |
|---|---|---|---|
| となりの出来事の順が逆 | 10.2% | 0% | 0% |
| 最初の出来事が変わった人 | 11.7% | 0% | 0% |
| 購入の直前が変わった人 | 19.9% | 0% | 0% |
| 所要時間が1秒以上ずれた人 | 28.4% | 28.4% | 0% |
| 人をまたいだ全体の順が逆 | 35.1% | 0% | 34.0% |

- ②は順番は直るが、時刻そのものは直らないので、所要時間のずれは残る。③は1人の中の順番と所要時間は正しいが、人をまたいだ順番は直らない
- **台数**（ずれ1秒）：2台で7.0%、3台で10.4%、5台で12.0%、10台で13.3%

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- 間隔がマイナスの件数と「最初の出来事が変わった人」の割合は、SQL（DuckDB の LAG・ROW_NUMBER）で出した値と一致する（コード内の assert）

## データ
- `data/access_log_sample.csv`：架空のアクセスログの最初の3,000行（全体はコードで作り直す。seed 465）

## 注意（言えないこと）
- 架空のログ。割合は、出来事の間隔の分布、サーバーの台数、時計のずれの大きさ、どのサーバーが記録するかの置き方で決まる
- 時計のずれは、サーバーごとに一定と置いた。時間とともにずれが動く場合や、時刻合わせで時計が戻る場合は扱っていない
- 通信の遅れ（出来事が起きてから記録されるまでの時間）は入れていない
- 通し番号は、入口の1台が受け取った順に正しく振れると置いた。入口が複数ある場合は扱っていない
- 実際のサーバーの時計がどれくらいずれるかは調べていない。ずれの大きさは置いた値
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。SQL は DuckDB で実行した
