# 1060 平均が速くなっても、遅い側の数%は遅くなっていることはあるのか？（処理の速さ）

処理の速さを変える変更を入れたあと、「平均の応答時間が何%速くなった」と報告することがよくあります。けれども、変更で速くなる処理と遅くなる処理がまざっていると、平均は速くなっても、遅い側の数%（99パーセンタイルなど）は遅くなっていることがあります。**ここでは、作成者が置いた分布からの乱数で作った架空のアプリ（軽い処理95%・重い処理5%）に、よく使う結果を手元に置いておく仕組み（キャッシュ）を入れる変更を置き、平均・中央値・90%点・95%点・99%点・99.9%点がそれぞれどう動くか、どのパーセンタイルから遅くなるか、200件・2,000件ずつ測って比べると遅くなったことを何回見落とすかを数えました。置き方を変えた27通りでも確かめました。処理時間はすべて作成者が置いた分布からの乱数で、実機の計測はしていません。**

パーセンタイル（速い順に並べて何%の位置の値か）の言葉は、99%点なら「100件のうち99件はそれより速く終わる時間」のことです。同じ企画の1059はサーバーごとの99%点を平均するずれ、1058は99%点が何件測れば落ち着くか、1055は平均・中央値・最小値のどれで比べるかで速い方が入れかわるか、1064は時間切れで打ち切った処理を除くと平均がどう見えるかという問いです。全便の平均の遅れと遅れた便の平均の違いは 1031、平均の待ち時間と長く待つ人の割合の違いは 873 で扱っています。この記事は、同じ変更で平均と遅い側が逆に動く場合に絞ります。

## 主な結果

### 変更の前後（基本、各200万件、`results/before_after.csv`）
| 物差し | 変更の前 | 変更のあと | 変化 |
|---|---|---|---|
| 平均 | 78.72ms | 45.341ms | **−42.4%** |
| 中央値 | 61.605ms | 16.952ms | −72.48% |
| 90%点 | 114.043ms | 81.046ms | −28.93% |
| 95%点 | 163.61ms | 154.871ms | −5.34% |
| 99%点 | 456.431ms | 550.721ms | **+20.66%** |
| 99.9%点 | 839.085ms | 1009.105ms | +20.26% |

- **平均は42.4%速くなったのに、99%点は20.66%遅くなった**。パーセンタイルごとに見ると、96%点から遅い側が遅くなっていた（`results/percentile_curve.csv`）
- 変更の前も後も、99%点より遅い処理はすべて（100%）重い処理だった。99%点の変化は、重い処理に置いた遅くなり方（+20%）のほぼ写し（式どおり）。新しく分かるのは、その遅くなりが平均・中央値・95%点にはまったく出てこないこと
- 1件ずつ見て遅くなった処理は、重い処理と手元にない軽い処理で24%（置いた割合からの式どおり：5%＋95%×20%）。平均だけを見ると、4件に1件ほどが遅くなったことは分からない

### 少ない件数で比べると（1,000回）
| 前後それぞれの件数 | 平均で速くなった回 | 中央値で速くなった回 | 99%点で遅くなったと出た回 | 99%点の遅くなりを見落とした回 |
|---|---|---|---|---|
| 200件 | 100.0% | 100.0% | 70.1% | **29.9%** |
| 2,000件 | 100.0% | 100.0% | 93.9% | 6.1% |

- 前後200件ずつの比べでは、99%点が本当は遅くなっているのに、29.9%の回で「遅くなっていない」と出た。200件の99%点は上から2件ほどで決まるので揺れが大きい（何件で落ち着くかは同じ企画の1058の問い）
- 平均と中央値は、どちらの件数でも100.0%の回で速くなったと出た

### 置き方を変えた27通り（各40万件、`results/grid.csv`）
- 平均は27通りすべてで速くなった（−65.04〜−15.17%）
- 99%点が1%より大きく遅くなったのは18通りで、重い処理が遅くなると置いた18通りと同じだった。99%点の変化は、重い処理の遅くなり方が+10%の通りで+7.04〜+11.0%、+20%の通りで+18.45〜+21.72%、0%の通りで−1.53〜+0.7%
- 遅くなり始めるパーセンタイルは、重い処理が遅くなる18通りで90〜99%点だった。重い処理の割合が多いほど低い位置から遅くなる（重い処理10%の通りで90〜91%点）
- 重い処理を遅くしない9通りでも、2通りで1%より大きく遅くなったパーセンタイルがあった。99.9%点などの端は件数が少なく揺れるためで、遅くなったわけではない
- つまり、遅い側が遅くなるかどうかとその大きさは、作成者が置いた「重い処理の遅くなり方」でほぼ決まる。この記事が示せるのは、そうした変更でも平均・中央値はそろって速く見えることと、遅い側の変化がどの物差しに出るか・出ないか

## 注意（言えないこと）
- 架空のデータです。軽い処理と重い処理の分布、割合、手元にある割合、遅くなり方は作成者が置いたもので、結果はこれで決まります。とくに99%点の変化の大きさは、置いた重い処理の遅くなり方の写しです。実在のソフトやサーバーの速さを表すものではありません
- 変更で重い処理が遅くなるしくみ（手元の結果を作り直す手間など）は、作成者がそう置いただけです。実際の変更で遅い側が遅くなるかは、測ってみないと分かりません
- 混み具合で遅くなる効果（待ち行列）は入れていません。速くなった処理の分だけ空きが増えて、ほかの処理も速くなることがあります（推測）
- どの変更を入れるべきかの助言ではなく、平均と遅い側が逆に動くときの見え方を数えただけです
