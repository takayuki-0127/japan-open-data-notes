# 311 表をつなぐと、合計はなぜ増えたり減ったりするのか（実務の型）

架空の注文・明細・支払・店マスタで、素朴な結合7つの合計を正解と比べ、5つの照合クエリが見つけるかを数えたフォルダです。SQL は T-SQL の書き方で `sql/` に置き、DuckDB で実行して確かめました。**SQL Server 本体では試していません（未検証）**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A311 | 表をつなぐと、合計は何倍になり、何%が黙って落ちるか。照合で見つかるか | 架空の注文4万件・明細10万行・支払4.3万行・店50（seed 311）。素朴な結合7つと直した書き方7つ、照合5つ（ぴったり比べる／0.5%以内は通す） | `src/a311_run.py`・`a311_figs.py`、`sql/naive.sql`・`fixed.sql`・`checks.sql` |

## 主な結果
- データの置き方：1注文あたりの明細は平均2.52行。注文の8.0%（3,219件）は支払が2行。0.47%（189件）は支払の行がない。3.0%（1,187件）は店マスタにない店コード（新しい店・小文字・末尾の空白）。履歴つきの店マスタでは10店に古い行と今の行の2行がある
- 素朴な結合の合計と正解の差

| 場面 | 差 | 起きたこと |
|---|---|---|
| S1 明細をつないで注文の送料を足す | **+151.8%**（2.52倍） | 注文の列が明細の行数だけくり返される |
| S2 支払をつないで注文の金額を足す | +7.7% | 2回払いの注文が2回数えられ、支払のない注文189件は消える |
| S3 明細と支払を両方つなぐ | +7.7% | 明細の行が支払の行数だけ増える |
| S4 店マスタを内部結合 | **−3.1%** | マスタにない店コードの1,187件が消える |
| S5 履歴つきマスタを外部結合 | +15.6% | 履歴が2行ある店の注文6,323件が2回数えられる |
| S6 履歴つきマスタを内部結合 | +12.5% | 増える分と消える分の両方 |
| S7 履歴が3店だけにあるマスタを内部結合 | **−0.39%** | 1,088行が増え、1,187行が消えて、ほぼ打ち消し合う（行数の差は −0.25%） |

- 照合が見つけた数（7場面中）：行数をぴったり比べる 7、合計をぴったり比べる 7、注文番号の重なり 6、相手のキーの重なり 6、注文番号の欠け 5
- 「0.5% 以内の差は通す」にすると、行数の照合も合計の照合も **S7 を通した**（6/7）。S7 では注文の5.7%（2,275件）が誤って数えられているのに、合計の差は 0.39%
- 直した書き方（結合の前に相手を注文単位に集計する／EXISTS／今の行だけをつなぐ／LEFT JOIN）は、7つとも正解と一致した

## 動かし方

```
pip install -r requirements.txt
cd src && python a311_run.py && python a311_figs.py
```

## 確かめたこと
- 空のフォルダで流し直し、results と figures の7ファイルがバイト単位で一致した
- 直した書き方の合計は、pandas で別に計算した正解と一致する（コード内の assert）

## 注意（言えないこと）
- 明細の行数、2回払いの割合、マスタにない店コードの割合は架空の置き方です。「何倍になるか」「何%落ちるか」はこの置き方での数字で、言えるのは向きと仕組みまでです
- 7つの場面は作成者が選んだもので、実際の業務で起きる結合の誤りを網羅していません
- S7 は、増える行と消える行がいちばん近くなる店の数（3店）を探して作りました。いつも打ち消し合うわけではありません
- 233（合計が合わないとき、SQL のどこから疑うか）・F244（間違えにくい SQL）と近い題材です。ここでは「結合で行が増減する場面」だけに絞りました
