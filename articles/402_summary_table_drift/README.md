# 402 速くするために作った集計済みの表は、元の表とどれくらいずれていくのか（実務の型）

レポートを速くするために、日別の集計済みの表を作っておくことがあります。元の表に、あとから遅れて届く行・金額の訂正・行の削除があると、集計済みの表は少しずつ元の表と合わなくなります。架空の売上（1日400行×365日）で、集計済みの表を6通りの更新の仕方で1年間保ち、ずれの大きさと、照合のクエリが気づくまでの日数を数えたフォルダです。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A402 | 更新の仕方ごとに、1年後に何日・何%ずれるか。照合のクエリは、最初のずれから何日で気づくか | 行の6%が遅れて届き、3%で金額が訂正され、1%が消える（遅れは70%が1〜3日、25%が4〜30日、5%が31〜90日）。毎晩、6通りの更新と5通りの照合を行う。売上の最後の日のあとも120日続ける | `src/a402_summary_drift.py`、`src/sql_update_and_check.sql` |

## 主な結果（最後の時点）
| 更新の仕方 | ずれた日 | 合計の差 | 読んだ行（毎晩ぜんぶ＝1） |
|---|---|---|---|
| A 当日分だけ足す | 365日すべて | −4.99% | 0.003 |
| B 直近7日を作り直す | 365日すべて | −1.41% | 0.023 |
| B' 直近35日を作り直す | 303日（83%） | −0.27% | 0.114 |
| C 更新日時で変わった日を作り直す | 35日（9.6%） | +0.02% | 0.045 |
| C' 更新日時＋削除の記録 | 0日 | 0 | 0.048 |
| D 毎晩ぜんぶ作り直す | 0日 | 0 | 1 |

- **C は、消えた行を拾えない**：消えた行は元の表に残らないので、「きょう変わった日」に入らない。削除をなくすと、C のずれは0になる（`results/sensitivity.csv`）
- **照合が気づくまで**（最初のずれからの日数）：
  - 取り込んだ当日分の合計だけを比べる照合は、どの更新の仕方でも気づかない
  - 直近7日を日ごとに比べる照合は、A にはその日に気づくが、B と B' には気づかない（その7日は作り直したばかり）
  - 全期間の合計を0.1%まで許して比べる照合は、A に1日後、B に2日後、B' に49日後に気づき、C には最後まで気づかない
  - 全期間を日ごとに比べる照合は、どれもその日に気づく
- 乱数の種を変えた20回でも、ずれた日の割合は A・B が100%、B' が81〜88%、C が6〜13%
- 遅れ・訂正・削除をどれも2倍にすると、A の差は−10.2%、B は−2.8%。半分にすると−2.5%、−0.7%

## 動かし方
```
pip install -r requirements.txt
cd src && python a402_summary_drift.py     # 10秒ほど
```

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- 最後の時点の元の表を DuckDB で日別に集計し直すと、シミュレーションの「元の表の合計」と365日とも一致する（assert）
- 全期間を日ごとに比べる照合の SQL を DuckDB で流すと、A のずれた日数（365日）を返す（assert）

## 未検証
- `src/sql_update_and_check.sql` は T-SQL で書きましたが、SQL Server では動かしていません。更新の仕方は Python で再現しました

## データ
- すべて架空（作成者が乱数で作成、seed 402）。`data/sales_events_sample5000.csv` は14.6万行のうち5,000行の抜き出し（sale＝売上の日、created＝届いた日、upd＝訂正の日、dele＝消えた日。全体はコードが作る）

## 注意（言えないこと）
- 遅れ・訂正・削除の割合と遅れの長さは、作成者が置いた数字です。ずれの大きさは、この置き方で決まります
- 「読んだ行」は、作り直した日の行数の合計で、手間の目安です。実際の時間は、索引や表の分け方で変わります
- 遅れて届く行が多いので、ずれは「少なく出る」向きに偏りました。訂正だけなら、多くも少なくも出ます
- 毎晩ぜんぶ作り直せる大きさなら、それがいちばん確かです。この記事は、更新の仕方を勧めるものではありません
