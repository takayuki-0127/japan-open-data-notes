# 652 採番の連番の最大値で件数を見ると、欠番のせいで何%多く数えるのか（実務の型・件数の数え方）

申込みや注文に振る連番（データベースの自動採番）は、件数と同じではありません。登録の途中で失敗した分、削除した分、サーバーの再起動で先読みしていた番号が飛んだ分だけ、番号は進みます。**ここでは、架空の申込みシステム（2025年、残っている申込み6.6万件）で、件数を COUNT(*) と「MAX(ID) − MIN(ID) + 1」で数えた場合を、月ごとと年間で比べました。** 失敗・削除の割合と再起動の日は作成者が置いたもので、数字はその仮定で決まります。

## 主な結果
- **年間では、最大の番号 72,458 に対して残っている件数は 66,100**：番号で数えると **9.6%** 多い
- **欠番 6,358 個の内訳**：取消で削除 2,764（43.5%）、再起動で飛んだ番号 2,551（40.1%）、登録の途中で失敗 1,043（16.4%）
- **月ごと**：ふだんの月は 5.3〜6.1% 多い（中央値 5.9%）。再起動で番号が大きく飛んだ月は 2月 18.0%、5月 11.2%、8月 **36.0%**（2日続けて再起動）
- **欠番の形**：3,604 か所のうち 3,402 か所は1つだけの欠番、100 個を超える欠番は4か所（再起動）

## 動かし方
```
pip install -r requirements.txt
cd src && python a652_max_id.py
```
数秒で終わります。`data/applications.csv` に残っている申込み（app_id・created_at）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 月ごとの件数と番号の幅が DuckDB と pandas で一致し、LAG で見つけた欠番の合計が「番号の幅 − 件数」と一致した
- T-SQL 版（`01_id_gaps_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）。再起動で番号が飛ぶ動きは、SQL Server の IDENTITY の先読みを1,000件として作成者が置いた

## データ
- `data/applications.csv`：app_id・created_at（削除した行は入っていない）
- 仮定：1日の申込みは平日約225件・休日約108件（季節の波あり）、登録の途中で失敗1.5%、取消で削除4%、再起動5回

## 注意（言えないこと）
- 架空のデータ。実際のシステムの数字ではない
- 番号の飛び方はデータベースの種類・設定で違う。ここは「番号は件数ではない」ことを数で見る例
- 件数は COUNT(*) で数え、削除した件数が必要なら削除の記録（論理削除のフラグなど）から数えるのが安全
