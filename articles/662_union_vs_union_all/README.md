# 662 UNION と UNION ALL を取り違えると、何件の行が消えたり残ったりするのか（実務の型・SQL の落とし穴）

2つの表を縦につなぐとき、SQL の `UNION` は同じ内容の行を1行にまとめ、`UNION ALL` はそのまま全部残します。売上の明細では、同じ時刻に同じ品を同じ数だけ売った別々の明細が、ふつうにあります。逆に、取り込みのやり直しで同じ明細が二重に入っていることもあります。**ここでは、架空の2店（A・B）の半年分の売上明細（6万6,344行）を、店ごとの2つの表に分け、B の表には3日分を二重に入れて、4通りのつなぎ方で行の数と売上を比べました。** 品の売れ方と二重に入った日数は作成者が置いたもので、数字はその仮定で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A662 | UNION・UNION ALL・キーで1行に絞る方法で、行と売上はどれだけ変わるか | U1 店とレシートの列を落として UNION、U2 店の列は残して UNION、U3 UNION ALL、U4 UNION ALL のあと明細のキー（店・レシート番号・行番号）で1行に絞る。DuckDB（1スレッド）と pandas で一致を確認。seed 662 | `src/a662_union.py`、`src/02_union_duckdb.sql`、`src/01_union_tsql.sql`（未検証） |

## 主な結果
- **U1（店とレシートの列を落として UNION）は671行少なく**、売上は0.51%少ない。二重に入った479行も消えるが、本当の明細も671行消える
- **U2（店の列は残して UNION）は360行少なく**、売上は0.27%少ない。店をまたいだ同じ内容の明細は残るが、同じ店の中のものは消える
- **U3（UNION ALL）は479行多く**、売上は0.74%多い。二重に入った3日は、その日の売上が41〜46%多く出る
- **U4（UNION ALL のあとキーで1行に）は本当の明細と一致した**
- U1 で消えた明細の割合は、100円の品で1.8%、900円以上の品では0.3%未満。安くてよく売れる品ほど、同じ内容の明細が重なる
- U1 の日ごとの売上は、98%の日で本当より少なく、差は0〜-1.7%。小さくて毎日続くので、気づきにくい

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 4通りの行の数と売上の合計が、DuckDB と pandas で一致した
- T-SQL 版（`01_union_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- 仮定：品は30品（100〜3,000円）。よく売れる度合いは値段に反比例。レシートは1日に A で約90枚、B で約70枚（土日は15%多い）。1枚の品の数は平均2.2。500円未満の品は2個以上買うこともある
- 売った時刻は9時〜21時の分まで。2025-03-10〜12の B の明細を二重に入れた

## 注意（言えないこと）
- 架空のデータ。実際の店の数字ではない
- 消える行の数は、品の数・時刻の細かさ・客の数で大きく変わる。日付だけで時刻がない表なら、UNION で消える行はずっと多くなる
- 二重の取り込みを UNION で消すと、本当の明細も一緒に消える。重複はキーで確かめて消すのが安全
