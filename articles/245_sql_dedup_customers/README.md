# 245 SQL で重複データを見つけて片づける（実務の型）

顧客の表に同じ人が2行以上入っているとき、SQL のどのキーで「同じ人」とみなし、どの行を残すかを、正解（人ID）の分かる架空の顧客表（6,900行、6,000人、重複900行）で試したフォルダです。5つの照合ルールで、正しく消せた重複・見落とした重複・別人をまとめてしまった行を数えました。SQL は T-SQL の書き方で書き、DuckDB で動かしました。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A245 | 重複をどのキーで見つけ、どの行を残すか | 照合用の列（`REPLACE`・`LOWER`）、`MIN() OVER (PARTITION BY …)` によるグループ番号、`ROW_NUMBER()` と `FIRST_VALUE()` で1行残す | `sql/02`〜`04`、`src/a245_make_data.py`・`a245_dedup.py` |

## 主な結果
- R1 完全一致（名前・生年月日・電話・メールがすべて同じ）：900行のうち129行しか見つからなかった。誤りは0
- R2 名前（空白を取る）＋生年月日：839行見つけたが、**別人を42行まとめて消した**（名前と生年月日が同じ別人。試しに40組入れ、ほかに偶然2組）
- R3 R2＋電話（ハイフンを取る）：別人の誤りは0になったが、522行に減った。新しい行の電話が空の場合と、電話番号が変わった人を拾えない
- R4 名前＋生年月日＋（電話 または メール）：801行、誤り0
- R5 R4＋（生年月日＋メール）：856行、誤り0。姓が変わった人も、メールが同じなら拾えた（93%）。残りの44行は、電話もメールも変わったか空だった行で、SQL の照合だけでは見つけられない
- 「または」のつながりは、`MIN() OVER` を2回かけると、グラフの連結成分（Python の networkx）と完全に一致した（このデータでは。つながりが長い表では回数が足りないことがある）
- 新しい行だけを残すと、R5 でまとめた6,044グループのうち224グループで電話が空になった。`FIRST_VALUE` で同じグループの古い行から埋めると、空は31グループ（グループのどの行にも電話がない）まで減った

## 動かし方
```
pip install -r requirements.txt
cd src && python a245_make_data.py && python a245_dedup.py
```
`src/common.py` の `tsql_to_duckdb()` が T-SQL の `N'…'` などを置き換え、`a245_dedup.py` の中で `SELECT … INTO` を `CREATE TABLE … AS` に、文字列をつなぐ `+` を `||` に置き換えて DuckDB で動かします。

## データ
- `data/customers.csv`：架空の顧客表。作成者が乱数で作成（seed 245）。名前はよくある姓・名の組み合わせ、電話・メールは架空（example.com／example.net）で、実在の人ではありません。`person_id`（正解の人ID）と `dup_type`（重複の種類）は説明用の列で、実務の表にはありません
- `results/rules_summary.csv`：ルールごとの、正しく消せた・見落とした・誤ってまとめた行数
- `results/found_pct_by_type.csv`：重複の種類ごとに見つけられた割合
- `results/checks.json`：照合の結果

## 注意
- 架空のデータの重複の割合や種類は、作成者が決めたものです。ルールの順位の向きは参考になりますが、何%見つかるかは実際の表で変わります
- 実際の名寄せでは、正解の人IDはありません。R2 のように別人をまとめるルールは、グループの中身を目で確かめる手順（手順3）を入れてから使います
- `sql/01_create_load.sql` の `BULK INSERT` は SQL Server 専用のため未検証です。`02`・`03` は上の置き換えをして DuckDB で、`04` は同じ文を DuckDB で動かしました
- 半角カナと全角カナ、旧字体などの違いは、この表には入れていません（`REPLACE` だけでは拾えません）
