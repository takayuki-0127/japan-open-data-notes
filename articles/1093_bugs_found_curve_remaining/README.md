# 1093 バグの見つかり方の曲線から、残りのバグの数はどこまで読めるのか？（テストとバグ）

テストを続けると、週ごとに見つかるバグは少しずつ減り、見つかったバグの累計は頭打ちの形になります。この曲線に「いずれここで止まる」という形を当てはめ、止まる高さから今までに見つかった数を引いて「残りは◯件」と読むことがあります。もう1つ、2つのグループが別々に探し、両方が見つけたバグの重なりが大きいほど「もうあまり残っていない」と読む方法もあります。どちらも、すべてのバグが同じように見つかりやすいときに合う読み方です。実際には、すぐ見つかるバグと、なかなか見つからないバグがあります。見つかりにくいバグは、曲線にも重なりにもほとんど顔を出さないまま残ります。**ここでは、作成者が乱数で作った架空のアプリ（作りこまれたバグ300件と、1件ずつの見つかりやすさを作成者が置いたもの）で、10週目までの見つかり方から2つの読み方で残りを見込み、作成者が置いた本当の残りの何倍になるかを300回数えました。見つかりやすさの散らばり・見た週・テストの量の減り方を変えた18通りの確かめも行いました。**

例のアプリは架空のもので、実在のソフトウェアやテストの道具は使っていません。

関連する記事：914「全数検査なら、不良はゼロになるのか？」は、工場の外観検査をくり返すとき、不良1個ごとの見つけやすさが違うと2回目の検査で見つかった数から残りを素直に読めないことを扱います。855「「9割終わった」から残りが長いのはなぜか？」は、終わり近くに長い作業が残ることを扱います。同じ企画の 1099「自動テストで見つかるバグと、人が触って見つかるバグは、同じ種類なのか？」は、得意な種類の違う2つの見つけ方の重なりから全体の数を見積もると、多めにも少なめにも外れることを扱っていて、この記事の②と同じ見積もりの形です。1089「見つかったバグが減ったのは、品質が上がったからか、テストが減ったからか？」は、見つけやすさがバグごとに違うとテストの時間と見つかる数が比例しないことを扱っていて、この記事と同じしくみです。この記事は、ソフトウェアのテストで週ごとに見つかったバグの累計と、2つのグループの重なりから残りを見込む読み方に絞ります。

## 主な結果

### 1回分（`data/weekly_one_draw.csv`、`data/bugs_one_draw.csv`）
- 10週目までに157件見つかり、本当の残りは143件だった。①の曲線は止まる高さを219.19件と読み、残りを62.19件と見込んだ
- この曲線は、当てはめに使っていない11〜20週目の累計もよく当てた（20週目の累計：実際211件、曲線202.58件）。**先の見つかり方をよく当てる曲線でも、止まる高さ（全体の件数）は300件を大きく下回った**
- 10週目までに見つかったバグの見つかりやすさは平均1.5211、見つかっていないバグは平均0.5584だった。残っているのは見つかりにくいバグだった

### 基本の置き方（散らばり1・10週目・テストの量一定、300回、`results/methods_base.csv`）
| 読み方 | 見込んだ残り÷本当の残り（中央値） | 10〜90%の範囲 | ±25%に入った回 | 半分未満だった回 |
|---|---|---|---|---|
| ① 頭打ちの曲線 | **0.29倍** | 0.16〜0.56倍 | 3.33% | 86.33% |
| ② 2つのグループの重なり | **0.33倍** | 0.24〜0.48倍 | 0% | 91% |

- 10週目までに見つかったのは平均150.85件、本当の残りは平均149.15件だった。どちらの読み方も、残りを本当の0.29倍・0.33倍（中央値）と少なく見込んだ
- ①と②は形の違う読み方だが、どちらも「見つかりにくいバグも同じように見つかる」と見る点が同じで、同じ向きに外れた

### 確かめ：置き方18通り（各300回、`results/grid.csv`）
| | ① 曲線（中央値） | ② 重なり（中央値） |
|---|---|---|
| 散らばり0・テストの量一定（3通り） | 1.01〜1.05倍 | 1.0〜1.02倍 |
| 散らばり0・テストの量が後半に減る（3通り） | 0.32〜0.59倍 | 0.99〜1.03倍 |
| 散らばり1・2（12通り） | **0.03〜0.38倍** | **0.07〜0.4倍** |

- **散らばりを置いた12通りすべてで、①も②も中央値が1倍を下回った**。散らばり2では0.03〜0.1倍（①）だった
- 散らばり0（どのバグも同じ見つかりやすさ）でテストの量が一定なら、①はほぼ1倍になる。①の曲線の形が、置いた見つかり方の形と同じなので、作りどおりの結果。それでも1回ごとの幅は広く、10週目で0.57〜1.95倍（10〜90%）だった
- 散らばりを置くと、見た週を伸ばすほど①の中央値は下がった（散らばり1・テストの量一定で、6週目0.38倍→10週目0.31倍→14週目0.23倍）。週を重ねるほど、残っているのが見つかりにくいバグばかりになるため
- 後半3割の週のテストの量を半分にすると、散らばり0でも、週を横軸にした①は0.32〜0.59倍に下がった。見つかる数が減ったのを「頭打ちに近づいた」と読むため。横軸をテストの量の累計にした①'では1.04〜1.11倍に戻った。テストの量が減ったときに①が下がったのは、9通りのうち8通り（残る1通りは散らばり2・14週目で、どちらも0.03倍）
- ②は見つけた週を使わないので、テストの量が減っても散らばり0なら0.99〜1.03倍のままだった

## 注意（言えないこと）
- 架空のデータです。バグの数、見つかりやすさの散らばり、テストの量は作成者が置いたもので、結果はこれで決まります。とくに外れの大きさは散らばりの置き方で0.03〜0.38倍（①）と大きく動きました
- 見つかりやすさは、バグごとにずっと変わらないと置きました。テストのやり方を変えて、見つかりにくかったバグが見つかりやすくなることは入れていません
- テストの途中でバグを直すときに新しいバグが入ること、見つかったバグの重さの違いは入れていません
- ②は、2つのグループの見つけやすさが同じバグについてそろう（同じバグを見つけやすい）と置きました。グループごとに得意なバグが違うときの外れ方は数えていません（得意な種類の違う2つの見つけ方は 1099 で数えた）
- 実在のアプリ・開発の数字を表すものではありません。この記事は、見つかり方から残りを読む2つの読み方が、見つかりやすさの違いでどれだけ外れるかを数えただけです
