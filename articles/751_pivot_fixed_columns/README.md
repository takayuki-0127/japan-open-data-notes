# 751 PIVOT の列を固定で書いておくと、あとから増えた区分の売上は何%消えるのか（実務の型・SQL の PIVOT）

区分別の売上を横に並べる表は、`PIVOT ... IN ('食品', '飲料', ...)` のように列を固定して書くことが多いです。あとで区分が増えても、IN に書いていない区分は列にならず、エラーも出ずに表から消えます。**ここでは、架空の区分別の月次売上（2024年1月〜2025年12月、作った時点の6区分に、途中で「定期便」「ギフト」「まとめ買い」が増える）で、固定した PIVOT の列の合計が本当の合計からどれだけ欠けるかを数えました。** 新しい区分の大きさと伸びは作成者が置いたもので、数字はその置き方で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A751 | 列を固定した PIVOT で、増えた区分の売上は何%消えるか | A 列を固定した PIVOT、B CASE WHEN で「その他」「合計」の列も出す、C 縦持ちのまま合計、D 固定の列にない区分を探す SQL。DuckDB（1スレッド）と pandas で一致を確認。seed 751 | `src/a751_pivot.py`、`src/02_pivot_duckdb.sql`、`src/01_pivot_tsql.sql`（未検証） |

## 主な結果
- **2年間で5.2%が表から消えた**：2024年は1.3%、2025年は8.5%。2025年12月だけなら14.3%
- **伸びも小さく見える**：2025年の前年比は本当は+13.9%、固定した6列の合計では+5.6%。12月の前年同月比は+20.8%に対し+6.7%
- **エラーは出ない**：固定した PIVOT は、IN にない区分を黙って捨てる。D の SQL で「固定の列にない区分」を探すと、定期便・ギフト・まとめ買いの3つが見つかった
- **B の形なら気づける**：「その他」と「合計」の列を足しておくと、6列＋その他＝合計になり、その他が0でない月から区分が増えたと分かる

## 動かし方
```
pip install -r requirements.txt
cd src && python a751_pivot.py
```
数秒で終わります。`data/sales.csv` に区分別の月次売上を、`results/monthly_lost.csv` に月ごとの消えた売上を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- DuckDB の PIVOT（A）が pandas の pivot_table と一致し、B の「6列＋その他」と C の縦持ちの合計が一致した
- T-SQL 版（`01_pivot_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- `data/sales.csv`：ym（月初の日付）・category・amount（円）
- 仮定：作った時点の6区分は月0.4%ずつ伸びる。季節の波と12月の山。定期便は2024年7月から月9%、ギフトは2025年4月から月5%、まとめ買いは2025年10月から月4%伸びる

## 注意（言えないこと）
- 架空のデータ。消える割合は、新しい区分の大きさと伸びで決まる
- 列を自動で作る PIVOT（DuckDB の IN を書かない形や、T-SQL の動的 SQL）は列が増えるが、表を受け取る側（Excel やグラフ）の列の位置がずれるので、それはそれで確かめが要る
- 実在の店の数字ではない
