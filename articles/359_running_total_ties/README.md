# 359 累計を出すウィンドウ関数は、同じ日付の行があると何がずれるのか（実務の型）

`SUM(...) OVER (ORDER BY 日付)` で残高の累計を出すとき、同じ日に複数の行があると何が起きるかを、架空の入出金明細（2,000口座・90日・約12.7万行）で数えたフォルダです。枠を書かない場合（既定の RANGE）、ROWS と書くが並びが日付だけの場合、並びを一意にした場合の3つを比べました。SQL は DuckDB で動かしました。T-SQL 版は `src/01_running_total_tsql.sql` に置きましたが、**SQL Server 本体では動かしていません（未検証）**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A359 | 同じ日付の行があると、累計はどうずれるか | ① 枠を書かない、② ROWS＋ORDER BY 日付、③ ROWS＋ORDER BY 日付, その日の順番 の3つで残高を出す。②は表に入っている行の順だけを変えて20回実行する。「残高がマイナスになった口座」の数を、並び方ごとに数える | `src/a359_running_total.py`、`src/*.sql` |

## 主な結果
- 127,067行のうち、同じ口座・同じ日に2行以上ある日の行は58%
- **① 枠を書かない**：ORDER BY があるときの既定の枠は RANGE … CURRENT ROW で、同じ日の行はどれも「その日の最後の残高」になる。行ごとの正しい残高と違った行は全体の35%（同じ日に2行なら50%、3行なら67%、4行なら75%、5行以上で82%）。その日の最後の行は100%一致
- **② ROWS＋日付だけ**：単独で実行し、表に入っている行の順を変えて20回くり返すと、同じ日に複数行ある日の行は100%、どこかの回で違う値になった。1回ごとに見ると、正しい残高と違う行は36%前後
  - ただし、③と同じ SELECT に並べて書くと100%正しい値になり、表がたまたま順番どおりに入っているときも100%正しかった。**正しく見えるのは偶然**で、試したときに合っていても当てにできない
- **残高がマイナスになった口座**（2,000口座中）：正しい順で782口座。同じ日は出金を先に並べると818口座（36口座を余分に数える）、入金を先に並べると743口座（39口座を見逃す）、①（その日の最後の残高だけ）でも743口座。②の20回では765〜783口座
- 最低残高が正しい順と違った口座は、どの並べ方でも21〜22%

## 動かし方
```
pip install -r requirements.txt
cd src && python a359_running_total.py
```
- `results/a359_main.json`・CSV・図は、実行のたびに同じ値になります
- `results/a359_runs_vary_each_time.json`（②の20回の結果）だけは、**流し直すと数字が少し変わります**。同点の並びが実行のたびに変わること自体が、この記事の結果だからです（違う行の割合は36%前後、マイナスの口座は765〜783の近くで動く）

## 確かめたこと
- 空のフォルダで流し直し、上の1ファイルを除く results・figures が一致した
- ③の残高は、pandas で別に計算した累計と一致した。①は「その日の最後の残高」と全行で一致した（コード内の assert）

## 注意（言えないこと）
- すべて架空のデータです。違う行の割合は、同じ日に何行あるかで決まります
- ②の並びが変わるかどうかは、データベースの製品・版・実行計画によります。DuckDB 1.5 で確かめた結果で、SQL Server での動きは試していません。「順番は決まっていない」ことは SQL の決まりとして共通です
- その日の中の順番（seq）が記録されていることを前提にしています。時刻や連番がない明細では、行ごとの残高は出せません
- 232（ウィンドウ関数で前年同月比）とは別の落とし穴として書きました
