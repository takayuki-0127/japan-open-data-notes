# F253 データの品質を毎月チェックする ― 架空のスーパー「サンプルマート（架空）」で、汚れを知らなくても鳴るチェック8つ

看板記事 F253（③ 業務の再現：架空の会社で、F246〜F255 の8本目）。F247 で整えた mart に、毎月の数字を出す前にかける品質チェックを作った。F247 では入っている汚れを知ったうえでテストを書いたが、毎月の仕事では**どんな汚れが来るかは前もって分からない**。そこでチェックを「汚れの種類」ではなく「ありえない形」（キーの重複・行の欠け・空・ゼロ・ほかの日と同じ値・ふだんとの比・列どうしの関係・部門の合計）で書き、知らない汚れ10種類を入れて、どれだけ見つけ、汚れのない月にどれだけ誤って鳴るかを測った。F69（公的データの欠測・桁ずれの点検）の、会社の中の毎月の仕事の版。

- **会社・数字は架空（合成データ）。実在の会社とは関係がない。顧客（クライアント）のデータは使っていない。汚れは筆者が入れたもの。**
- note：（公開後に記入）
- 成果物：チェックのスクリプト `src/dq_check.py`（1か月分の mart に流して、引っかかった店×日の一覧と判定を出す）、SQL 版 `sql/dq_checks.sql`、毎月のチェック表の見本 `reports/dq_2025-12_{確定,速報}_見本.{md,html}`

## 問い
毎月の数字を出す前に、データが壊れていないかを自動で確かめたい。どんな汚れが来るか分からないとき、どんなチェックを置けば、どの汚れをどれだけ見つけられるか。汚れのない月に誤って鳴る回数を、1人が数分で確かめられる量（1か月に数件）に抑えられるか。速報（締めの時点）では、まだ届いていないだけの行と、本当に欠けた行をどう扱うか。

## データ

- **乱数を変えたデータ**：F246 の合成のコード `gen(seed)`（コミット 3006b82）で、設定を変えずに乱数の種 0〜19 の20通りを作り直す（`data/f246/`）。
- **速報の mart**：F247 の `build_mart_pd(raw, close_day=k)` で、営業日の翌月 k 日（1・3・5・10日）までに届いた POS だけで作った FY2025 の店×日・店×日×部門（`src/02_整形.py` → `data/versions/`、F248 と同じ作り方）。

## チェック（`src/dq_check.py`）

| ID | チェック | 何を見るか | 重さ |
|---|---|---|---|
| Q01 | キーの重複 | 店×日が2行以上ある | A |
| Q02 | 行の欠け | 営業しているはずの店×日の行がない（開店日・閉店日は dim_store から）。営業日の外の行 | A（速報では「未着」として保留） |
| Q03 | 空の値 | 必須の8列が空 | A |
| Q04 | 営業日のゼロ | 営業しているはずの日に、売上・客数・点数・人時が0以下 | A |
| Q05 | ほかの日と同じ値 | 客数・点数・売上が、同じ店のほかの日（その月と前の7日）と1円まで同じ | A |
| Q06 | ふだんとの比 | 売上・客数・点数・人時・廃棄が、その店のふだんの値の T 倍より大きいか 1/T より小さい（T：売上・客数・点数・人時 1.5、廃棄 2.0） | B（5倍以上・5分の1以下は A） |
| Q07 | 中の関係 | 一品単価・1回の買上点数・時給が 1.5 倍、廃棄率が 2 倍、ふだんから外れる。会員の客数＞客数 | B（5倍以上・5分の1以下は A） |
| Q08 | 部門の合計 | 部門の売上の合計が店の売上と 0.5% 以上違う。片方にしか行がない | A |

- **重さ**：A＝数字が確実に壊れている。直すまで、その店×日を月の数字から外す（F248 の月次レポートの「載せなかったもの」に書く）。B＝ふだんと大きく違う。店に確かめてから出す。
- **「その店のふだんの値」**（Q06・Q07）は、チェックする月より前の確定の数字だけから作る。
  - 参照 a：月初の前の8週の、同じ曜日の中央値
  - 参照 b：364日前（同じ曜日）の値 × その店の伸び（月初の前の8週の合計 ÷ その1年前の8週の合計）
  - 参照 c：1年前の同じ日付の値 × 同じ伸び（年末のように日付で動くもの）
  - 使える参照のうち「ずれのいちばん小さいもの」で判定する（どの参照から見てもおかしいときだけ鳴らす）。1年前の参照がない店（開店1年未満）は a だけ、a もない店（開店8週未満）は判定せず、チェック表に「判定しなかったもの」として書く。
- 線（T＝1.5・2.0）と参照の組み合わせ（a・b・c）は、下の A の結果を見てから決めた。
- 使い方：`python src/dq_check.py --month 2025-12 --mart data/in --out reports`（`--mode 速報` で行の欠けを保留にする）

## 手法
- **A. 汚れのない月の誤報と、線の決め方**：乱数の種 20通り × FY2024・FY2025 の24か月 ＝ 480か月分で、Q06 の比（値 ÷ 参照）をすべての店×日で計算した。線 T（1.2〜5倍）と参照の組み合わせ（a・b・c・ab・abc）ごとに、1か月に何店×日が鳴るかを数えた。売上・客数・点数がそろって f 倍になる汚れ（途中までしか入らない・2回足し込み）は、汚れのない比に log f を足して、見つけられる割合を出した（f＝0.2〜3）。
- **B. 汚れを入れて8つのチェックを全部流す**：480か月それぞれに、10種類の汚れを1つずつ、別の店（1年前の参照がそろう店）・ランダムな日に入れた（4,800個）。汚れが触れた店×日に1つでもチェックが鳴れば「見つけた」とした。
- **比べる相手**：決めた範囲だけのチェック（売上 50万〜2,000万円、客数 100〜6,000、点数 1,000〜6万、人時 30〜1,500時間、廃棄 1万〜100万円、空も含む）。この会社の店×日の値がふだん入る幅を広めにとった。
- **C. F247 の mart（確定）にそのまま流す**：24か月で何が鳴るか。
- **D. 速報**：締め 1・3・5・10日の速報に流し、行の欠け（未着）と部門の合計の不一致を数えた。各月に「本当に欠けた行」を1つ入れ、速報と確定で見分けられるかを見た。
- **SQL**：Q01〜Q05・Q08 と Q06（参照 a だけ）を `sql/dq_checks.sql` に書き、DuckDB で流して pandas と同じ店×日×チェックが出るかを確かめた（汚れを入れた60か月）。書き方は SQL Server に寄せたが（`MEDIAN`→`PERCENTILE_CONT`、`LN`→`LOG` などの書き換えが要る）、SQL Server では動かしていない。

### 入れた汚れ（`src/sim_common.py` の `inject`）

| 汚れ | 中身 |
|---|---|
| 欠測：行がない | 店×日の行が1〜3日続けてない（部門の行もない） |
| 欠測：空の値 | 人時・廃棄・点数のどれか1つが空 |
| 欠測：0で入る | POS が止まり、売上・客数・点数・会員の客数・粗利が0で入る（部門も0） |
| 欠測：途中までしか入らない | 送信が途中で切れ、POS の値（店・部門とも）が 0.3〜0.7 倍 |
| 桁ずれ：廃棄を千円で入力（1か月） | 1店の1か月の廃棄がすべて 1/1000（F247 の19店と同じ形） |
| 桁ずれ：人時が10倍 | 小数点の打ち忘れで人時・人件費が10倍 |
| 桁ずれ：店の売上だけ10倍 | 店の売上の列だけが10倍（部門・客数・点数はそのまま） |
| 重複：同じ行が2回 | 同じ店×日の行がもう1行ある |
| 重複：前の日の写し | ある日の値が、前の日の値と全く同じ（前の日のファイルの送り直し） |
| 重複：2回足し込み | 再送を足してしまい、POS の値（店・部門とも）が2倍 |

## 結果
- **8つのチェックで、4,800個の汚れの 97.9% を見つけた**（種ごとに 96.3〜100%）。10種類のうち8種類は 100%。
  - 見つけにくかったのは「途中までしか入らない」（81.7%）と「2回足し込み」（97.7%）。どちらも売上・客数・点数がそろって動くので、列どうしの関係（Q07）や部門の合計（Q08）は崩れず、ふだんとの比（Q06）だけが頼り。
  - それぞれの汚れを拾ったチェックは、ほぼ1つに決まる（図1）。行がない→Q02、空→Q03、0→Q04、同じ行が2回→Q01、前の日の写し→Q05。桁ずれは Q06 と Q07 の両方、店の売上だけ10倍は Q06・Q07・Q08 の3つで拾った。
  - 見つけた汚れのうち、8種類（途中まで・2回足し込みを除く）はすべて重さ A になった。途中まで・2回足し込みは B（店に確かめる）。
- **決めた範囲だけのチェックは 49.0%**。空・0・桁ずれ（人時10倍・廃棄千円）は見つかるが、行の欠け・重複・前の日の写し・2回足し込み・途中まではどれも 0%、店の売上だけ10倍は 89.6%（小さい店は10倍でも2,000万円を超えない）。誤報は0。
- **汚れのない月の誤報**：既定（参照 abc、T 1.5・廃棄 2.0）で、1か月平均 0.32 店×日（Q06 が 0.92 件、Q07 が 0.002 件、ほかの6つは0）。480か月の 91% は1件も鳴らず、最大は6店×日。
  - **誤報はほぼ12月だけ**（12月の平均 3.8 店×日、ほかの月は 0〜0.05）。年末（12/28〜31）のにぎわいを「ふだんと違う」と読む。
  - 参照を a だけ（前の8週の同じ曜日）にすると、売上・客数・点数で 1か月 6.2 店×日、12月は 74.6 店×日。a・b で 1.9、a・b・c で 0.31（約20分の1）。
  - 線を 1.3倍に下げると、a・b・c でも 1か月 2.2 店×日（a だけなら 18.0）。廃棄は 1.5倍にすると 2.5 件（2倍で 0.04 件）。人時は 1.3 倍以上なら0。
- **売上・客数・点数がそろって f 倍になる汚れを見つける割合**（a・b・c、T 1.5）：2倍 97.3%、半分 96.1%、1.75倍 80.4%、0.6倍 65.6%、1.5倍 26.5%、0.7倍 14.8%、1.3倍 1.6%。**2〜3割の欠けや増えは、日単位のチェックではほとんど見えない**。線を 1.3倍にすると 1.3倍で 26.5%・0.7倍で 62.1% まで上がるが、誤報は約7倍になる（0.31→2.2）。
- **参照を増やすと見逃しも少し増える**：2倍を見つける割合は a だけ 99.98%、a・b 99.7%、a・b・c 97.3%。参照のどれかがたまたま近い値だと鳴らないため。
- **F247 の mart（確定）にそのまま流すと**、24か月のうち22か月は何も鳴らず、鳴ったのは 2024年12月（08店の年末、4店×日）と 2025年12月（16店の年末、3店×日）だけ。どちらも開店から1年たっておらず、1年前の参照がない店（前の8週だけで判定）。
- **速報（FY2025）**：行の欠け（未着）は1か月平均、締め1日 4.5、3日 3.7、5日 3.0、10日 1.5 店×日で、確定ではすべて届いて0。部門の合計の不一致は、どの締めでも0（店と部門の POS は一緒に届く設定）。本当に欠けた行を1つ入れると、速報（5日）では未着の 3.0 件に混ざって 4.0 件になり見分けられないが、確定ではその1件だけが残った。
- **見本（2025年12月、汚れを5つ入れた確定）**：A 5件（行の欠け・前の日の写し・廃棄の千円・人時10倍・廃棄率）、B 9件。B のうち3件は2回足し込み（11店の12/16、売上 2.15倍）、6件は16店の年末（開店1年未満）の誤報。入れた5つはすべて見つかった。
- **SQL と pandas**：汚れを入れた60か月で、3,799件の店×日×チェックが完全に一致した。

## 頑健性
1. **乱数の種 20通り**：見つけた割合は種ごとに 96.3〜100%。汚れのない月の誤報は、種×月の 91% で0。
2. **線と参照の組み合わせ**：T 1.2〜5倍 × 参照5通り（`results/A_false_alarms_by_T_mode.csv`・`B_detect_by_factor.csv`）。どの組み合わせでも、3倍以上の線では誤報0、2倍の汚れは見えない。
3. **参照 a の週数**（4・8・13週、種 0〜4）：a・b・c の誤報は 1か月 0.25・0.28・0.32、2倍を見つける割合は 97.1・97.2・97.3%。週数ではほとんど変わらない。a だけのときの誤報は 5.4・6.2・6.6。
4. **比べる相手（決めた範囲だけ）**：上の結果。
5. **F247 の mart（確定）そのもの**：24か月で鳴ったのは開店1年未満の店の年末だけ（上の結果）。
6. **SQL と pandas の照合**：60か月で一致。

## 言えないこと
- **数字は架空の会社の合成データ**。汚れの種類・大きさ・入れ方は筆者が置いたもの。実在のスーパーで、どの汚れがどれだけ起きるかを示すものではない。
- **見つけた割合は、汚れの大きさしだい**。ここでは「途中まで」を 0.3〜0.7 倍に置いたが、0.9 倍の欠け（1割の取りこぼし）なら日単位ではほぼ見つからない（f＝0.9 で 0%）。小さな取りこぼしは、会計との照合（F247 の T08）や月の合計で見るしかない。
- **誤報の少なさは、合成データの揺れの小ささに助けられている**。この会社の店×日の売上は、ふだんの値から 1割ほどしか揺れない（参照 a との比の標準偏差 約0.11）。台風・停電・競合の開店・大きな販促など、本当のできごとで動く日は合成データに入っていないので、実務では B がもっと鳴る（推測）。
- **汚れは「1つの店×日」か「1つの店×1か月」に置いた**。全店で同時に起きる汚れ（システムの切り替えで全店の単位が変わるなど）は入れていない。切り替えた月は各店のふだんの値と比べて鳴るはずだが、翌月からは参照もずれた値になり鳴らなくなる（推測）。切り替えの予定を送り元と前もって共有し、会計との照合（F247 の T08）でも見る必要がある。
- 開店1年未満の店は1年前の参照がなく、年末に誤報が出る。開店8週未満の店は Q06・Q07 で判定していない。
- 線（1.5倍・2倍・5倍）は、この合成データの結果を見てから決めた。別の会社・別の粒度では決め直しが要る。
- SQL は SQL Server に寄せた書き方にしたが、実行したのは DuckDB。

## F69・F242・F247・F248 との関係
- **F69**（公的データの点検）：0・欠測・秘匿の見分け方、桁ずれ（3倍・3分の1）、合計の一致を、公的統計の表で確かめた。この回はそれを会社の毎月のデータに置き換え、汚れを入れて見つける割合と誤報を数えた。
- **F242**（毎日の KPI の「いつもと違う」を知らせる）：本当の変化を知らせる警報のルールを比べた回。この回の Q06 も同じ「ふだんとの比」だが、狙うのは本当の変化ではなくデータの壊れで、壊れは大きい（10倍・千分の1・0・欠け）ことが多いので、線を高めに置ける。小さな壊れ（2〜3割）は F242 の警報と区別できない。
- **F247**（データを整える）：入っている汚れを知ってテストを書いた。この回は汚れを知らずに書いたチェックで、F247 の9つのテスト（T01〜T09）のうち、T01 キーの重複・T05 欠けた日・T06 空・T07 部門と店の合計・T09 値の範囲に当たるものを含む。T08 会計との照合は、この回では使っていない。
- **F248**（月次レポートの型）：A の店×日はレポートの「載せなかったもの」に入れ、速報の未着は F248 と同じく「保留」として確定でもう一度チェックする。
