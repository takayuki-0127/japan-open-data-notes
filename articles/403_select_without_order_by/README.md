# 403 ORDER BY のない SELECT の並びに頼ると、結果はどれだけ再現しないのか（実務の型）

`SELECT … LIMIT 1` や `ROW_NUMBER() OVER ()` のように、並びを決めずに「先頭」や「連番」を使う処理が、実行のたびにどれだけ違う答えを返すかを数えたフォルダです。架空の明細100万行を DuckDB に入れ、8つの処理を、スレッドの数（1・2・4・8）と「入れた順を保つ」設定（する・しない）を変えて100回ずつ実行しました。SQLite では、索引の有無と表の作り直しで「先頭の1件」が変わるかを見ました。359（累計と同じ日付の行）・360（上位3件と同点）に対し、ここでは ORDER BY がまったくない場合を扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A403 | 並びを決めない処理は、100回のうち何回、違う答えを返すか。何を変えると答えが変わるか | DuckDB 1.5（2コアの機械）で8処理×8条件×100回。SQLite は6つの表の状態で同じ SELECT を20回ずつ。ORDER BY を足した書き方も100回ずつ | `src/a403_no_order_by.py` |

## 主な結果（回数は、流すたびに少し変わります）
- **スレッド1つでは、8つの処理すべてが100回とも同じ答え**（入れた順どおり）
- **既定の設定（入れた順を保つ）でスレッド2つ以上**：
  - 先頭の1件（LIMIT 1）、条件つきの先頭の1件、`ROW_NUMBER() OVER ()` の連番は、100回とも入れた順どおり
  - つないだ後の先頭の10件は、100回中19〜42回が、いちばん多い答えと違った
  - 顧客ごとの最初の1件（`first`）は41〜51回が違い、「いちばん小さい id」だったのは44〜59回
  - 重なりを除いた後の先頭の5件は40〜77回が違った
  - 文字をつなぐ `string_agg` は、id の小さい順になったのが100回中0〜1回。答えは19〜32通り
- **「入れた順を保つ」をしない設定**にすると、先頭の1件でも100回中1〜22回が違う答えになった
- **SQLite（20万行）**：同じ状態なら20回とも同じ答え。ただし「顧客7の先頭の1件」は、索引なしで id 3955、索引（顧客, 金額）で 67043、索引（顧客, 日）で 141410。表を日の順に作り直しても変わった。5つの状態のうち3つで、索引なしのときと違う答え
- **ORDER BY（や MIN）を足した書き方**は、スレッド8・入れた順を保たない設定でも、6つの処理すべてが100回とも同じ答え

## 動かし方
```
pip install -r requirements.txt
cd src && python a403_no_order_by.py     # 2コアで30秒ほど
```

## 確かめたこと
- 空のフォルダで流し直し、data と、決まった答えになる結果（`sqlite_first_rows.csv`・`duckdb_with_order_by.csv`・`main.json`・SQLite の図）が一致した
- **`results/duckdb_runs_varies_each_run.csv` と、それを描いた図2枚は、流すたびに少し変わります**。実行ごとに答えが変わること自体が結果だからです。本文の回数は、このフォルダに置いた1回分の値です

## 未検証
- SQL Server では動かしていません。SQL Server でも、ORDER BY のない SELECT の並びは決まっていません（並列の実行、索引の選び方、ページの並びで変わりえます）が、どの処理が何回変わるかは確かめていません
- DuckDB の結果は、版（1.5.6）・機械のコア数（2）・表の大きさで変わります

## データ

## 注意（言えないこと）
- 「100回とも同じ」は、同じにならないことがない、という意味ではありません。版や設定、データの大きさが変われば変わりえます
- 8つの処理は作成者が選びました。割合は、処理の選び方では読めません
- 2コアの機械でスレッド4・8を指定しています。コアの多い機械では、回数が変わるはずです（推測）
