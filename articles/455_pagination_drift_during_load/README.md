# 455 1ページずつ順に取り込むと、途中で行が増減したとき、何行が重なり、何行が抜けるのか（実務の型）

架空の一覧10万行を1,000行ずつ取り込む間に、追加と削除が起きる場面を作り、ページの送り方3つ（何行目から／キーの続きから／開始時点で固定）で、重なった行と抜けた行を数えたフォルダです。330（2回取り込んでも二重にならない形）・402（集計済みの表のずれ）・403（ORDER BY なし）とは別に、ページ送りの取り込みだけを扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A455 | 取り込みの途中で行が増減すると、送り方によって何行が重なり、何行が抜けるか。件数の照合で気づけるか | 取り込み中の追加と削除を乱数で作るシミュレーション（30回の平均）。追加・削除の割合とページの大きさを変える。同じ手順を SQLite の SQL でも流して、数が一致することを確かめる | `src/a455_pagination.py`、`src/01_paging_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
基本の場面：10万行、1ページ1,000行、取り込みの間に追加1%・削除1%（最初の行数に対する割合）。キーは作られた順の番号

| 送り方 | 重なった行 | 抜けた行 | 取り込んだ行数 − 終わりの行数 |
|---|---|---|---|
| 何行目から（古い順） | 0 | 495 | 0 |
| 何行目から（新しい順） | 540 | 43 | 0 |
| キーの続きから（古い順） | 0 | 0 | +507 |
| キーの続きから（新しい順） | 0 | 0 | −493 |
| 開始時点で固定（古い順） | 0 | 0 | −491 |

- 「抜けた行」は、取り込みの最初から最後まであったのに、1回も取り込まれなかった行。「重なった行」は、2回以上取り込んだ行
- **件数の照合**：「何行目から」は、取り込んだ行数が終わりの時点の行数と30回すべてで一致した（差0）。重なりと抜けがあっても、件数では分からない。「キーの続きから」は重なりも抜けも0だが、取り込んだあとに消えた行（約500行）や、開始後に増えて取り込まなかった行（約990行）の分だけ、件数に差が出る
- **追加・削除の割合（何行目から）**：

| 追加・削除 | 古い順：重なり／抜け | 新しい順：重なり／抜け |
|---|---|---|
| 0.1%・0.1% | 0／48 | 75／23 |
| 1%・0% | 0／0 | 1,004／0 |
| 0%・1% | 0／492 | 0／492 |
| 1%・1% | 0／495 | 540／43 |
| 5%・5% | 0／2,228 | 2,507／45 |
| 5%・1% | 0／482 | 4,677／0 |

  古い順は、削除の分の約半分が抜ける。新しい順は、追加の分がほぼそのまま重なる（削除があると打ち消される）
- **ページの大きさ（何行目から、追加1%・削除1%）**：古い順の抜けは 1,000行で495、5,000行で465、20,000行で400、50,000行で248。新しい順の重なりは 540・488・388・252。ページを大きくすると減るが、2ページに分けただけでも残る
- **SQLite**：5,000行・1ページ100行・追加2%・削除2%で、5つの送り方とも、SQL で流した結果がシミュレーションと一致

## 確かめたこと
- 空のフォルダで流し直し、results・figures が一致した
- SQLite の SQL（LIMIT/OFFSET、キーの続き）で流した結果が、シミュレーションと5つの送り方すべてで一致する（コード内の assert）

## データ
- データのファイルはない。シミュレーションの設定と乱数の種はコードの中にある（seed 455）

## 注意（言えないこと）
- 架空の場面。変化は「1ページ取るごとに、追加と削除が少しずつ起きる」形で、削除される行はどの行も同じ割合。古い行ほど消えやすい・新しい行ほど消えやすい場合は、数が変わる
- キーは作られた順の番号で、追加はいつも最後に入る。名前順のように、追加が途中に入る並びでは、「キーの続きから」でも、通り過ぎた所に入った行は取り込まれない
- 行の中身の更新は扱っていない（増減だけ）
- 取り込みは、行数がページに満たないページが返ったら終わる形
- 「開始時点で固定」は、開始時点の最大のキーまでに限る形。データベースのスナップショットの機能は使っていない
- T-SQL 版（OFFSET … FETCH）は SQL Server 本体では動かしていない（未検証）
