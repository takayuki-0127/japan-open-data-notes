# 303 E2E テストの考え方を、データの処理にも使えるか（実務の型）

架空の注文データを月×地域の表にまとめる処理（pandas）に、不具合を16個と無害な書き換えを2個、1つずつ入れて、5種類のテストがそれぞれ鳴るかを数えたフォルダです。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A303 | 画面の操作を最初から最後まで通して確かめる E2E テストの考え方（決まった入力を入れ、最後の出力を期待と比べる）は、データの処理でどれだけ不具合を見つけるか | 処理は8つの決まり（店コードをそろえる・重複は新しい行・取消を除く・金額の空を除く・税込みにそろえて合計してから四捨五入・日本時間で月を決める・マスタにない店は「不明」・月×地域で集計）。T1 関数ごとのテスト／T2 出力の形の点検／T3 入力と出力の合計の照合／T4 手で作った24行での通しテスト（期待する出力は DuckDB の SQL で別に計算）／T5 本番に似せた2万行から抜いた入力での通しテスト（正しい版の出力を控える） | `src/pipeline.py`・`src/a303_tests.py` |

## 主な結果
- 16個の不具合のうち見つけた数：T1 関数ごと 8、T2 出力の形 0、T3 合計の照合 11、T1〜T3 のどれか 13、**T4 手で作った24行の通し 16**、T5 似せた500行の通し 13
- T1〜T3 のどれも鳴らず、T4 だけが見つけたのは3個：月を UTC で決める、月の境目が1時間ずれる、顧客を延べで数える
- **無害な書き換え2個（列の順・行の順）には、通しテスト（T4・T5）だけが鳴った**（2/2）。比べ方を「列と行の順は問わない」に変えると、T4 は不具合16個すべてを見つけたまま、無害な2個には鳴らなかった
- T5 は入力の行数で変わる：50行で平均6.1個、200行で9.9個、500行で12.3個、2,000行で15.5個、10,000行で16個（30通りの抜き方の平均）。手で作った24行と同じ16個に届くのは、1万行だった
- 正しい版の出力は、手で作った24行でも2万行でも、SQL で別に書いた仕様の出力と一致した（テストの土台の確認）

## 動かし方
```
pip install -r requirements.txt
cd src && python a303_tests.py
```

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した

## 注意（言えないこと）
- 不具合もテストも作成者が書いたものです。どの不具合を入れるかを知ったうえで手の24行を作ったので、T4 の「16個すべて」は有利な条件での数字です。関数ごとのテスト（T1）は「仕様の文をそのまま確かめる1〜2個」にとどめたので、境目の値まで書けば見つける数は増えます
- データも処理も架空で、処理は1本だけです。処理の作りが違えば、テストごとの数は変わります
- 通しテストは「どこが壊れたか」は教えません。鳴ったあとは、関数ごとのテストや合計の照合で場所を探す必要があります
- 入力ファイルそのものの壊れ（型・範囲）を止める検査は 260、合計が合わないときの調べ方は 233 で扱いました。この記事は処理のコードの不具合に絞っています
