# 482 ポイントの失効を「月末に一括」と「付与日から1年」にすると、失効額はどれだけ違うのか（実務の型）

同じ会員・同じ購入の履歴に、ポイントの失効の決まりを3通り当てて、月ごとの失効額・年の失効率・月末の残高を比べたフォルダです。付与ごとの失効額を SQL のウィンドウ関数（累計の「それまでの最大値」）で出す方法も載せ、シミュレーションと突き合わせています。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A482 | 失効の決まりで、失効額・失効の日・残高はどれだけ変わるか | 架空の会員3,000人・4年分（2023〜2026年、購入21.6万回）。会員ごとに日付順に「失効→利用（古い付与から）→付与」を再現。A：付与日から1年、B：付与月の1年後の月末に一括、C（参考）：最後の付与・利用から1年。A・B は DuckDB の SQL でも失効額を出し、付与1件ずつ一致を assert | `src/a482_points.py`、`src/01_expiry_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
2023年は助走（失効がまだ出そろわない）として、2025〜2026年の2年で比べています。
- **2年の失効額**：A（付与日から1年）31.4万pt、B（月末に一括）30.1万pt（Aより4.2%少ない）。付与は2年で594.8万pt、失効率はAが5.3%、Bが5.1%
- **年の失効率**：2025年 A 5.5%・B 5.2%、2026年 A 5.1%・B 4.9%
- **月ごとの差**：同じ月で比べたBとAの差は平均1,362pt（Aの月の失効額の10.5%）、最大3,060pt。24か月のうち、Aが多い月16、Bが多い月8
- **失効の日**：Aは失効が毎日少しずつ出る（2024〜2026年の1,095日すべて）。Bは月に1日（翌月1日）にまとめて出る（35日）
- **月末の残高**（2026年12月末）：A 63.2万pt、B 64.4万pt（+1.9%）。C は 78.3万pt（+24%）で、失効率は0.5〜0.9%
- **SQL の確かめ**：付与ごとの失効額をウィンドウ関数で出すと、シミュレーションと付与1件ずつ一致した（A 22,159件、B 21,686件）

## データ
- `data/fictional_purchases.csv`：架空の購入とポイントの付与（seed 482）。利用の量は失効の決まりで変わるので、コードの中で決まりごとに再現する

## 注意（言えないこと）
- 架空の会員と購入。利用の仕方（使う確率・使う量）は置いた値で、失効が近いことを知らせて使ってもらう、といった動きは入れていない
- 会員は失効の決まりを知らずに同じように買い・使う、と置いた。実際は決まりによって使い方が変わりうる
- ウィンドウ関数の式は、失効の順番が付与の順番と同じ（A・B）ときに成り立つ。C には使えない
- 会計処理（引当など）の助言ではない
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。SQL は DuckDB で実行した
