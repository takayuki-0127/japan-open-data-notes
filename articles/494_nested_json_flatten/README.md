# 494 入れ子の JSON を平らにすると、行は何倍になり、合計はどれだけずれるのか（実務の型）

1件の注文に明細の配列とクーポンの配列が入った架空の注文 JSON（2万件）を、よく見る6通りで表に平らにし、行の数と、明細の金額・クーポンの金額・送料・注文の合計の4つを素朴に SUM したときのずれを数えたフォルダです。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A494 | 平らにし方で、行の数と4つの合計はどれだけ変わるか | ①pandas の json_normalize（明細を行に、注文の項目は meta）②明細とクーポンを順に explode ③SQL で明細・クーポンをそれぞれ LATERAL で結合 ④DuckDB の同じ SELECT で2つを UNNEST ⑤明細を行に、クーポンは注文ごとの合計を列に ⑥注文・明細・クーポンの3つの表に分けて、それぞれで合計。クーポンの付く注文の割合を0〜80%に変えてくり返す | `src/a494_json_flatten.py`、`src/01_openjson_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
- **データ**（seed 494）：注文2万件、明細44,627行（平均2.23行）、クーポン16,060枚（40%の注文に1〜3枚）
- **①明細ごとの行**：44,627行（注文の2.23倍）。明細の金額は正しいが、各行にくり返された送料は +34%、注文の合計は +231%
- **②順に explode・③SQL でそれぞれ結合**：どちらも62,401行（3.12倍）。明細×クーポンの組み合わせになり、明細の金額 +40%、クーポン +122%、送料 +89%、注文の合計 +355%
- **④同じ SELECT で2つを UNNEST（DuckDB）**：48,863行（2.44倍）。DuckDB は2つの配列を長いほうに合わせて横に並べるので、明細とクーポンの合計はどちらも正しい。ただし送料 +67%、注文の合計 +241%で、明細とクーポンの組み合わせには意味がない
- **⑤明細を行に、クーポンは合計を列に**：明細は正しく、クーポンの合計列 +122%、送料 +34%、注文の合計 +231%
- **⑥3つの表に分けてそれぞれで合計**：4つとも0%。行は20,000＋44,627＋16,060
- **クーポンの割合を変えると**：②の明細の金額の水増しは、クーポンの付く注文が10%で+10%、40%で+42%、80%で+81%

## 確かめたこと
- 空のフォルダで流し直し、results・figures が一致した
- ⑥の4つの合計が、JSON から直接足した正しい値と一致すること（コード内の assert）

## 注意（言えないこと）
- 架空の注文。ずれの大きさは、置いた明細の数・クーポンの割合・送料の決め方で決まる
- ④の結果は DuckDB 1.5 での動き。ほかのデータベースで同じ SELECT に2つの UNNEST を書いたときの動きは同じとは限らない
- T-SQL 版（OPENJSON と CROSS APPLY）は SQL Server 本体では動かしていない（未検証）
- 表をつないで行が増える話は 311、小計の二重計上は 452 で扱った。ここは JSON のほどき方に絞った
