# F255 1年の分析業務を振り返る ― 架空のスーパー「サンプルマート（架空）」の9本を、数字で点検する

看板記事 F255（③ 業務の再現：架空の会社で、F246〜F255 の10本目・最後）。架空の食品スーパー「サンプルマート（架空）」で1年分の分析業務として作った F246〜F254 を振り返る。「何を作り、何が役に立ち、何が役に立たなかったか」を感想で書かずに、各回の結果ファイルから数字を集め、コードも点検して確かめた。

- **会社・数字は架空（合成データ）。実在の会社とは関係がない。顧客（クライアント）のデータは使っていない。**
- note：（公開後に記入）
- 成果物：1枚の振り返りの報告 `reports/振り返りの報告.{md,html}`（図6はその画像）、各回から集めた数字の表 `data/processed/numbers.csv`（63個、どのファイルのどこから取ったかつき）

## 問い
架空の会社で1年分の分析業務（KPI・データの整え方・月次レポート・ダッシュボード・悪い月の説明・販促の効果・予算・データの品質・引き継ぎ）をやってみた。その中で、どのやり方が実際に役に立ち、どれが役に立たなかったのか。来年もう一度やるなら、何を最初に変えるべきか。それを、各回で残した結果の数字とコードから答える。

## データ
- **各回の結果ファイル**：F246〜F253 の `results/`（main.json・summary.json と一部の CSV）、F254 の `results/A_audit*`。`src/f255_01_取得.py` が隣のフォルダ（なければ GitHub の main）から `data/in/` に写し、md5 を `data/in/manifest.csv` に残す。
- **各回のコード**：F246〜F253 の `src/*.py`・`requirements.txt`・`README.md`（コードの点検用）。
- 公開データの新しい取得はなし。`data/in/` はリポジトリに入れていない（01 で作り直せる）。

## 手法
- **A. 素朴なやり方と採用したやり方**（`results/A_before_after.csv`）：6つの回（F247・F248・F249・F251・F252・F253）で、それぞれの回が比べていた「素朴なやり方」と「採用したやり方」の結果を、同じものさし（%）で並べた。どちらの値も、その回の結果ファイルから読んだ。
- **B. 偶然の幅を何度測ったか**（`results/B_noise_bands.csv`）：「全社・月の売上の前年比」と「1店・月の売上の前年比」の偶然の幅（本当の変化がないときのぶれ）を、4つの回がそれぞれ測っていた。90% で書いた回（F250）は ×1.96/1.645 で 95% に直し、そろっているかを見た。
- **C. コードの点検**（`results/C_code_audit.csv`）：F246〜F253 の src をそのまま読み、スクリプトの数と行数、F246 の合成データ・F247 のデータマートを使っているか（フォルダ名で数える方法と、コミット・関数名で数える方法の2通り）、合成データを作り直すか、偶然の幅を自分で計算するか（1.96 などの文字を探す）、requirements の版を固定しているか（`==`）を数えた。F254（引き継ぎ）の点検結果も読んだ。
- **D. 予算の答え合わせ**（`results/D_budget_check_rank.csv`）：F252 の答え合わせ（2026年4〜8月）の差を、モデルごとに過去の外れ（1年合計の MAPE）の順位と並べた。
- **E. 頑健性**：比べる相手を変えたとき（`results/E_alt_choices.csv`）、数字が GitHub に公開されたファイルと同じか（`results/F_github_check.csv`）、新しいフォルダでの再実行。

## 結果
- **1年で作ったもの**：F246〜F253 の8回で、スクリプト47本・7,166行。F246 の合成データは後の7回すべてが、F247 のデータマートは後の6回すべてがコードで使っていた（2つの数え方は一致）。
- **素朴なやり方 → 採用したやり方**（すべて架空の会社・こちらで入れた答えに対して）
  - F247 データを整える：全店売上の正解とのずれ 97%（どの手当てもしない）→ 0%（8つの手当て）
  - F248 月次レポート：店の例外のうち本当に差がある割合 6%（前年比の上下5店）→ 78%（今月3σか3か月続けて1σ）
  - F249 ダッシュボード：差のない店×月に色がつく割合 37%（決めた線 ±3pt）→ 5%（偶然の幅 95%）
  - F251 販促の効果：黒字の販促が赤字に見えた割合 35%（前年比の差、20通り中7通り）→ 5%（合成対照、1通り）
  - F252 予算：80% の幅に実際が入った割合 20%（ETS の区間）→ 83%（業界の外れ＋自社の揺れ）
  - F253 データの品質：入れた汚れを見つけた割合 49%（決めた範囲だけ）→ 98%（ありえない形8つ）
- **6つのうち4つ（F248・F249・F252・F253）は、「偶然の幅」か「ふだんのぶれ」を先に測ったことで良くなった**。残る2つは、データの汚れの手当て（F247）と、比べる相手の作り方（F251）。
- **偶然の幅は4つの回で測り直していた**。全社・月の売上の前年比は ±1.33（F246）・±1.42（F248）・±1.35（F249）・±1.34（F250、90% の ±1.12 を直した値）で、最大÷最小は 1.07倍。1店・月は ±6.23〜6.54 で 1.05倍。値はそろっていたが、F250 だけ 90% で書いていて、同じ量に2つの書き方が混ざっていた。コードで偶然の幅を計算していた回は8回中6回。
- **役に立たなかったもの**
  - 1店・月の営業利益：偶然の幅 ±205%。KPI にできなかった（F246）
  - モデルが出す予測の区間：80% のはずが ETS 20%・SARIMA 57%（F252）
  - 前年比の上下5店（6%）、決めた線 ±3pt（37%）
  - 日ごとの品質チェックでは、売上・客数・点数がそろって1.3倍になる汚れを 1.6% しか見つけられない（F253）
  - Power BI の .pbix は作れず、DAX は Power BI で一度も動かしていない（F249）
- **予算の答え合わせ（1回）**：2026年4〜8月の売上累計は予算より −2.66%、見直しの線（−1.89〜+1.92%）の外。業界（スーパー）の前年比が +4.1% から +1.4% に鈍った時期と重なる。過去の外れでいちばん悪かった季節ナイーブ（MAPE 2.52%、4位）が今回はいちばん近く（−0.06%）、いちばん良かった SARIMA（1.14%、1位）は3位だった。1回の答え合わせでは、モデルの良し悪しは分からない。
- **コードの点検**：requirements の41行のうち、版を固定（`==`）した行は0。合成データを作る・作り直す回は8回中7回。F254 の点検では、「既存店」の決まりが4か所に書かれ、書き方が2通りあった（いまのデータでは同じ答え）。

## 頑健性
1. **比べる相手を変える**（`results/E_alt_choices.csv`）：F248 で「今月3σだけ」（本当に差がある 93%、ただし見つける割合は 51%）や「今月1.96σ」（61%）にしても、上下5店（6%）より良い。F249 で幅を 90%（11%）・99%（0.8%）にしても、決めた線（37%）より少ない。F251 で合成対照の代わりに差の差でも 5%。F252 で SARIMA の区間でも 57% で 80% に届かない。F253 で線を 1.3倍に下げると誤報は1か月 2.2件（決めた範囲だけは誤報0だが見つけるのは49%）。どれも「採用したやり方の方が良い」という向きは変わらない。
2. **偶然の幅の直し方**：90% → 95% の換算は正規分布の倍率（1.96/1.645）を使った。F250 の 90% の値をそのまま比べても、全社・月は ±1.12〜1.42 の範囲。
3. **依存の数え方2通り**：フォルダ名で数えても、コミット・関数名で数えても、F246 に依存する回7・F247 に依存する回6で一致。
4. **公開ファイルとの照合**：写した結果ファイル14個のうち、GitHub（main）に公開済みの12個は md5 がすべて一致（残る2個は同時に作っていた F254 の回で、この時点で未公開）。
5. **再実行**：新しいフォルダで 01〜05 を流し直し、data/processed・results・reports・図が一致することを確かめた（下の再現手順）。

## 言えないこと
- **数字はすべて架空の会社の合成データと、筆者が入れた答え**に対するもの。採用したやり方が良く見えるのは、筆者が置いた設定（地域の流れ・店×月の揺れ・汚れの種類）の上での話で、実在の会社で同じだけ良くなるとは限らない。素朴なやり方と採用したやり方は、同じ筆者が同じ設定を知ったうえで選んでいる（推測：実務では採用したやり方の差はもっと小さく見える）。
- 6つの比べ方は、ものさしが回ごとに違う（%でそろえただけ）。どの改善がいちばん大きいかを順位づけするものではない。
- コードの点検は、文字（フォルダ名・関数名・1.96 など）を探して数えた。書き方が違えば数え漏れがありうる。
- 予算の答え合わせは1回（5か月）だけ。
- F254（引き継ぎ）はこの回と同時に作っていたため、その点検結果は途中の版を読んでいる。
