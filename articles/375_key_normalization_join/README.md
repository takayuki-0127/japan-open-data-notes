# 375 全角と半角、前後の空白で、キーはどれだけつながらないのか（実務の型）

請求データを取引先マスタに「取引先名」でつなぐとき、表記のゆれ（全角と半角、空白、大文字小文字、（株）と株式会社）でつながらない行がどれだけ出るか、正規化（書き方をそろえること）でどこまで直るか、正規化のせいで別の取引先につながる行がどれだけ出るかを数えたフォルダです。架空の取引先マスタ（3,000社）と請求データ（30,000行）を使い、結合は DuckDB の SQL で行いました。T-SQL 版は `src/02_join_tsql.sql` に置きましたが、**SQL Server 本体では動かしていません（未検証）。照合順序（Japanese_CI_AS など）の動きも試していません**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A375 | そのままつなぐと何%がつながらないか。正規化を足すとどう変わるか。誤ってつながる行は何行か | 請求の18.7%の行に、6種類のゆれを入れる。マスタには、大文字小文字だけ・中黒の有無だけ・前株と後株だけが違う別々の取引先を20組ずつ入れておく。正規化を1段ずつ足しながら LEFT JOIN し、つながらない行と、正しい取引先と違う取引先につながった行を数える。取引先コードでも同じことをする | `src/a375_key_normalization.py`、`src/*.sql` |

## 主な結果（請求30,000行、取引先名でつなぐ）
| 正規化（上から順に足す） | つながらない行 | 別の取引先につながった行 | 増えた行 |
|---|---|---|---|
| 0 そのまま | 5,580（18.6%） | 2 | 0 |
| 1 前後の空白を取る | 4,308（14.4%） | 3 | 0 |
| 2 全角と半角をそろえる（NFKC） | 3,290（11.0%） | 4 | 0 |
| 3 大文字にそろえる | 3,192（10.6%） | 360（1.2%） | 360 |
| 4 間の空白を取る | 2,331（7.8%） | 368（1.2%） | 368 |
| 5 （株）を株式会社にそろえる | 0 | 396（1.3%） | 396 |
| 6 中黒・ハイフンを取る（やりすぎの例） | 0 | 776（2.6%） | 776 |
| 7 「株式会社」を取る（やりすぎの例） | 0 | 4,519（15.1%） | 4,519 |

- **そのままでは18.6%（金額で18.4%）がつながらない**。5段目まで足すと0になる
- **3段目（大文字にそろえる）から、別の取引先につながる行が出る**。大文字小文字だけが違う取引先20組（40社）のキーが重なるためで、その取引先あての請求は2つの取引先につながり、行が増える。5段目で396行（1.3%）、請求金額の合計は1.3%多く出る
- 6段目で中黒だけが違う20組も重なり、776行（2.6%）。7段目では前株と後株だけが違う取引先が重なり、4,519行（15.1%）
- ゆれの種類ごとに、効く段が違う：前後の空白は1段目、全角の英字と半角カナは2段目、大文字小文字は3段目、間の空白は4段目、法人格の書き方は5段目
- **取引先コードでつなぐ**と、つながらない行は 4.0% → 3.0% → 1.0% → 0%（3段目）で、別の取引先につながる行は0だった

## 動かし方
```
pip install -r requirements.txt
cd src && python a375_key_normalization.py
```
乱数の種を固定してあるので、実行のたびに同じ `data/`・`results/`・`figures/` を出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- SQL（DuckDB）で数えた結合後の行数とつながらない行数は、pandas の merge で数えた値と一致した（コード内の assert）

## データ
- `data/customers_master.csv`（3,000社）・`data/invoices.csv`（30,000行。入れたゆれの種類と正しい取引先の番号つき）：架空（seed 375）。実在の会社名ではありません
- `results/steps.csv`：正規化の段ごとの結果。`results/unmatched_by_variation.csv`：ゆれの種類ごとの、つながらない割合

## 注意（言えないこと）
- すべて架空です。つながらない割合は、入れたゆれの割合（18.7%）でほぼ決まります。別の取引先につながる行の数は、「正規化するとぶつかる取引先」を何組入れたかで決まります
- 7段目の15.1%は、名前の作り方（少ない部品の組み合わせ）のせいで大きく出ています。実際の取引先マスタでの割合ではありません
- 旧字体と新字体（髙と高）、「ヶ」と「ケ」、長音とハイフンの取り違え、略称（東和と東和物産）、誤字は入れていません
- 正規化は Python で行いました（DuckDB には NFKC の関数がないため）。SQL Server の照合順序に任せる書き方は試していません
