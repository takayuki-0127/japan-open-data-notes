# 461 区分ごとのユニーク人数を足すと、全体の人数より何%多くなるのか（実務の型）

架空の購買ログ（顧客×日×店×部門、1か月分）で、日ごと・店ごと・部門ごとに数えた「買った人の数」を足した数と、全体で数え直した人数を比べたフォルダです。344（アクティブな顧客の定義）・389（通過率の数え方）とは別に、「足せない数を足す」ことだけを扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A461 | 区分ごとのユニーク人数を足すと、本当の人数の何倍になるか。複数の店を使う人の割合や来店の多さでどう変わるか。合計の照合で気づけるか | COUNT(DISTINCT) を区分ごとに出して足す／全体で数え直す／先に「人×区分」の表を作ってから数える。SQL は DuckDB で実行し、pandas の値と一致することを確かめる | `src/a461_distinct.py`、`src/01_distinct_tsql.sql`（T-SQL 版、未検証） |

## 主な結果
基本の場面：顧客2万人のうち月に1回以上買った15,196人、128,162行、30日・8店・6部門。ふだんの店以外で買う来店が1割

| 数え方 | 足した数 | 本当の人数 | 倍率 |
|---|---|---|---|
| 日ごとを足す | 69,667 | 15,196 | 4.58倍 |
| 週ごとを足す | 40,913 | 15,196 | 2.69倍 |
| 店ごとを足す | 22,280 | 15,196 | 1.47倍（+47%） |
| 部門ごとを足す | 53,512 | 15,196 | 3.52倍 |
| 店×部門ごとを足す | 63,264 | 15,196 | 4.16倍 |

- 倍率は「1人が使った区分の数の平均」とぴったり同じになる（店1.47、部門3.52、日4.58）。2つ以上の店を使った人は34.2%、2つ以上の部門を使った人は87.0%
- **合計の照合**：行数と金額は、店ごとを足した数と全体が一致する（差0）。人数だけが合わない。金額の照合が通っても、人数が正しいとは言えない
- **そこから作る指標**：1人あたりの金額は、本当の人数で割ると12,112円。店ごとを足した数で割ると8,261円（−32%）、部門ごとで3,439円（−72%）、日ごとで2,642円（−78%）。部門ごとの「利用した人の割合」を足すと352%になる
- **複数の店を使う人の割合**（各20回の平均）：2店以上を使った人が0%なら上振れ0、21%で+25%、34%で+47%、57%で+107%、72%で+183%
- **来店の多さ**（各20回の平均）：月の来店回数の平均が1回なら日ごとを足した数は2.0倍、4回で4.6倍、16回で11.0倍
- **月の比べ**：来店の回数だけが3割多い月を作ると、本当の人数は+5.0%なのに、日ごとを足した数は+25.1%に見える
- **直し方**：全体で数え直す。または先に「人×店」の表（1人1店1行）を作り、そこから数える。どちらも本当の人数と一致した

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- SQL（DuckDB）で出した数が、pandas で出した数と一致する（コード内の assert）
- 倍率が「1人が使った区分の数の平均」と一致する（コード内の assert）

## データ
- `data/purchase_log_sample.csv`：架空の購買ログの最初の2,000行（全体はコードで作り直す。seed 461）

## 注意（言えないこと）
- 架空のデータ。倍率は、来店の回数、複数の店・部門を使う割合の置き方で決まる
- 「何倍になるか」は、足し方の誤りの大きさを示すもの。日ごとの人数（延べ人数）そのものが悪い指標だと言うものではない。延べ人数として使うなら正しい
- 近似の数え方（HyperLogLog など）は扱っていない
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。SQL は DuckDB で実行した
