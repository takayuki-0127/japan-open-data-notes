# 329 金額を小数（FLOAT）で持つと、合計はどれだけずれるのか（実務の型）

小数第2位まである架空の金額100万行を、4バイトの浮動小数（REAL）・8バイトの浮動小数（FLOAT・DOUBLE）・10進の型（DECIMAL）で持ち、合計・等号の判定・足す順番を比べたフォルダです。DuckDB と NumPy で計算しました。T-SQL 版は `sql/01_float_money_tsql.sql`（**SQL Server 本体では未検証**）。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A329 | 金額の型によって、合計のずれ・等号の判定・足す順番の影響はどれだけ違うか | 金額は1/100単位の整数で正しい値を持ち（合計5,564,456,719.37）、3つの型に入れて比べる。合計は1,000〜100万行で。等号は、2〜100個の金額の和を、正しい和と `=` で比べる（10万回ずつ）。足す順番は100通りに並べ替える | `src/a329_float_money.py`、`sql/01_float_money_tsql.sql` |

## 主な結果
- **10進の型（DECIMAL）**：どの行数でも合計の差は0。`0.1 + 0.2 = 0.3` も成り立つ
- **8バイトの浮動小数**：100万行を上から順に足した合計の差は−0.0001。金額としては見えない大きさ。ただし
  - 100通りの並びで足すと、合計は93種類の違う値になり、正しい合計とぴったり同じになった並びは0
  - 店ごと（200店）の合計を正しい合計と `=` で比べると、一致したのは8店だけ。小数第2位に丸めてから比べると200店すべて一致
  - 2個の金額の和でも、21%で「和 = 正しい合計」が外れた。10個で41%、100個で79%。小数第2位に丸めてから比べると0%
  - 店ごとの合計を足し直した値と、全体の合計は `=` で一致しなかった（DECIMAL は一致）
- **4バイトの浮動小数**：4バイトのまま上から順に足すと、1,000行で+0.27、1万行で+16.40、10万行で+1,178、**100万行で−107,791**。合計が約1,678万（2の24乗）を超えると、1より細かい桁を持てなくなるため
  - DuckDB の `sum` は4バイトの列を8バイトで足すので、差は−0.08にとどまった（残るのは、1件ずつの値が4バイトに入りきらない分）。店ごとの合計を丸めて比べても、一致は200店中30店
- DuckDB で `0.1 + 0.2 = 0.3` を型ごとに流すと、DOUBLE は成り立たず、DECIMAL は成り立った。REAL は成り立った（4バイトではたまたま同じ値に丸まるため）

## 動かし方
```
pip install -r requirements.txt
cd src && python a329_float_money.py
```
100万行のデータは実行時に作ります（`data/` には先頭1,000行だけ置いています）。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- DuckDB はスレッドを1つにして実行しています。2つのスレッドで流すと、DOUBLE の合計の最後の桁が実行ごとに変わりました（−0.00009 と −0.00004）。これも「足す順番で答えが変わる」の一例です

## 注意（言えないこと）
- SQL Server 本体では動かしていません。SQL Server の `SUM` が REAL の列を何バイトで足すかは確かめていません
- 金額は「小数第2位まである値」を想定しました。円の整数だけなら、8バイトの浮動小数は約9,007兆（2の53乗）まで、4バイトは約1,678万（2の24乗）まで正確に持てます
- ずれの大きさは、金額の大きさと行数で変わります。ここの数字は、平均約6,900・最大約178万の金額100万行での値です
- 掛け算・割り算（税率、按分）をはさむ場合のずれは扱っていません（丸めについては 327・328）
