# 585 個・箱・ケースの単位が混ざった出荷明細を換算せずに足すと、品目別の数量はどれだけずれるのか（実務の型・入数の換算）

出荷明細の数量の列は、行によって「個」「箱」「ケース」と単位が違うことがあります。単位の列を見ずに数量を足すと、品目別の出荷数はまったく違う数字になります。**ここでは、架空の300品目・1年分の出荷明細（80,000行）で、換算せずに足した数量・入数マスタで換算した個数・入数の履歴まで使った個数を、本当の個数と比べました。** あわせて、入数マスタの行が漏れている場合と、入数が途中で変わったのにマスタが今の値しか持っていない場合のずれも数えました。単位の混ざり方・入数・マスタの漏れは作成者が置いたもので、数字はその仮定で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A585 | 単位を換算せずに足すと、品目別の数量と順位がどれだけずれるか | 本当の個数（出荷日の入数で換算）を正とし、①換算せずに足す、②入数マスタ（今の値）で換算、③入数の履歴（有効期間つき）も使って換算、の3通りと比べる。品目別のずれの分布、上位20品目の重なり、順位相関、マスタに行がない明細の件数。マスタでの換算を DuckDB（1スレッド）の SQL と Python で突き合わせ。seed 585 | `src/a585_unit_conversion.py`、`src/02_convert_duckdb.sql`、`src/01_convert_tsql.sql`（未検証） |

## 主な結果
- 明細の単位：個 49.6%・箱 33.2%・ケース 17.1%
- **換算せずに足す**：全体で本当の個数の 12.4%（644,197 対 5,197,119）。品目別では本当の 2.4%〜79.1%（中央値 14.7%）で、300品目中281品目が半分以下
- **品目の並び**：順位相関 0.73、上位20品目のうち同じだったのは11品目。125品目で順位が50位以上動いた
- **入数マスタの漏れ**：ケースの行がない12品目で、770行（本当の個数で103,692個、全体の2.0%）が換算できない。LEFT JOIN で空のまま足すと、その12品目は本当より 3.3%〜92.7%少ない（中央値 32.6%）。INNER JOIN だと、その行は件数ごと消える
- **入数の変更**：7月に箱の入数が12個から10個に変わった8品目は、マスタの今の値（10個）で換算すると 6.1%〜10.5%少ない（中央値 7.6%）。有効期間つきの履歴で換算すると、ずれは0になる

## 動かし方
```
pip install -r requirements.txt
cd src && python a585_unit_conversion.py
```
数秒で終わります。`data/shipments.csv`（line_id・shipped_on・item・unit・qty）、`data/unit_master.csv`（item・unit・pcs_per_unit）、`data/box_size_history.csv`（item・valid_from・valid_to・pcs_per_box）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 品目別の「換算せずに足した数」「マスタで換算した個数」と、換算できなかった明細の数（770行）が、Python と DuckDB の SQL（`02_convert_duckdb.sql`）で一致した
- 履歴を使った換算で、マスタの漏れがない品目は本当の個数と完全に一致した
- T-SQL 版（`01_convert_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- 品目300。箱の入数は 6・10・12・20・24個、ケースは 4〜12箱。品目ごとに、個・箱・ケースのどれで出やすいかを変えた
- 出荷明細80,000行（2025年）。個は1〜24、箱は1〜8、ケースは1〜3
- 入数マスタは今の値だけを持つ。12品目はケースの行が漏れている
- 8品目は2025年7月1日から箱の入数が12個→10個（それまでの明細は12個入り）

## 注意（言えないこと）
- 架空のデータ。実際の会社の出荷数ではない
- ずれの大きさは、箱・ケースで出る明細の割合と入数で決まる
- 重さや容積など、個数以外の単位への換算は扱っていない
- 在庫の評価や会計上の扱いは扱っていない
