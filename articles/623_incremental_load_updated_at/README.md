# 623 差分の取り込みを「更新日時が前回より後」で行うと、何件が取りこぼされるのか（実務の型）

元の表から変わった行だけを取り込むとき、「updated_at が前回取り込んだ最大値より後」という条件はよく使われます。ただ、updated_at には更新を始めた時刻が入り、書き込みが確定（コミット）するのはその数秒あと、ということがあります。**ここでは、架空の元の表（2万キー、1日約10万回の更新、updated_at は秒単位）を5分ごとに取り込む場面で、条件4通り（＞、≧、60秒重ねる、コミット順の連番）について、一度も読まれなかった更新、二重に読んだ更新、1日の終わりに値が元と違うキーを数えました。** 確定が10〜90秒遅れる更新の割合を0〜10%と変えています。12時の回の件数は SQL（DuckDB）でも出し、Python と一致することを確かめています。数字は置いた確定の遅れで決まります。

## 主な結果
- **確定の遅れが短いだけ（0〜数秒）でも**：updated_at ＞ 前回の最大で 99,965件のうち 175件を取りこぼし、日の終わりに 34キーの値が違った。≧ にすると 68件・9キー（同じ秒の行を二重に読んだのは 409件）
- **確定が10〜90秒遅れる更新が 5% のとき**：＞ で **957件**（1.0%）を取りこぼし、193キーが違った。≧ で 840件・179キー。60秒重ねて取ると 73件・19キーで、二重に読んだのは 19,759件。コミット順の連番では取りこぼし・二重・ずれとも 0
- **10% のとき**：＞ で 1,792件・381キー、60秒重ねて 156件・35キー、連番は 0
- **重ねる幅（遅れ 5%）**：0秒 840件、10秒 627件、30秒 331件、60秒 73件、120秒 0件。二重に読む件数は 405件から 39,536件に増える
- 取りこぼしは、確定が遅れて「前回の最大値」より古い updated_at で後から見えるようになった行と、前回の最大値と同じ秒に後から確定した行で起きる
