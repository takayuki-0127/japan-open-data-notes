# 1096 変更の多いファイルほどバグが多いのは、変更のせいか、ファイルの大きさのせいか？（テストとバグ）

アプリのソースのファイルを並べると、よく変更されるファイルほど、見つかったバグが多いことがよくあります。ここから「変更が多いとバグが増える」と読みたくなります。けれども、この見え方には少なくとも3つのしくみが混ざります。大きいファイルほど変更も多く、バグも多いこと（大きさの分）。見つかったバグを直す変更そのものが「変更の回数」に数えられること（直しの分）。そして、変更そのものがバグを持ちこむこと（変更の分）です。変更を減らせばバグが減るのは、3つ目だけです。**ここでは、作成者が乱数で作った架空のアプリのソースのファイル500本（ファイルの本当の大きさ、1年の機能の変更の回数、大きさの分のバグと変更1回あたりのバグを作成者が置いたもの）で、「変更が1回ふえるとバグが何件ふえるか」（傾き）を5つの数え方で出し、置いた本当の値とどれだけずれるかを数えました。変更1回あたりのバグを0と0.05に置いた2通りを各300回、確かめに本当の値・大きさと変更の結びつき・行数の記録のずれを変えた27通りを各100回作りました。**

例は架空のアプリのファイルで、実在のテストの道具・開発のサービスの名前は使っていません。

関連する記事：選ばれ方や別の原因が混ざって、見かけの効果が出るしくみは、839「投稿の時刻の効果は、時刻の効果か、内容の効果か？」（力作ほど夜に出す）、1035「道のりの長い日ほど、1kmあたりの時間は短いのか？」（3つのしくみの切り分け）、953「出店した場所の売上が高いのは、場所のおかげか？」、1082「似た人どうしがつながっているのは、影響しあったからか、もとから似ていたからか？」でも扱いました。同じ企画の1092「千行あたりのバグ数で、チームどうしを比べてよいのか？」は、行数で割る物差しそのものがチームの書き方やテストの厚さでずれる話で、この記事で使った「千行あたり」の読み方の注意にあたります。1100「テストを先に書いた機能にバグが少ないのは、書き方の効果か、機能の選ばれ方か？」は、機能の大きさ・難しさと公開からの日数が、テストを先に書いたかどうかとバグの見かけの関係に混ざる話で、この記事と同じ形です。この記事は、ファイルの大きさと、直しの変更を数に入れることの2つが混ざる場合に絞ります。

## 主な結果

### 変更1回あたりのバグを0と置いたとき（変更ではバグが増えない、300回、`results/describe_base.csv`）
| 物差し | 値 |
|---|---|
| 記録の変更の回数とバグの数の順位の相関 | 0.5861 |
| 機能の変更の回数とバグの数の順位の相関 | 0.4529 |
| 行数と機能の変更の回数の順位の相関 | 0.6567 |
| 機能の変更の多い上位20%のファイルが持つバグの割合 | 45.83% |
| 同じ上位20%のファイルが持つ行数の割合 | 45.58% |
| 千行あたりのバグ（上位20%／それ以外） | 3.0141件／2.9838件 |

- **変更ではバグが増えないと置いても、変更の多いファイルほどバグが多かった**（順位の相関0.5861）。変更の多い上位20%のファイルにバグの45.83%が集まった
- ただし、その上位20%のファイルは行数でも45.58%を占め、千行あたりのバグは3.0141件とそれ以外（2.9838件）とほぼ同じだった。バグが多いのは大きいからだった（作りどおり）
- 変更1回あたりのバグを0.05と置くと、千行あたりのバグは上位20%で4.4577件、それ以外で3.8433件と差が出た

### 5つの数え方の「変更1回あたりのバグ」（300回の平均と10〜90%、`results/estimates_base.csv`）
| 数え方 | 本当の値0のとき | 本当の値0.05のとき |
|---|---|---|
| ① 記録の変更（直しも入る）の傾き | 0.0939（0.0757〜0.1149） | 0.1316（0.1167〜0.148） |
| ② 直しを除いた変更の傾き | **0.0887**（0.0703〜0.1112） | **0.1353**（0.1171〜0.1555） |
| ③ ②に行数もいっしょに入れる | **−0.0003**（−0.0127〜0.0121） | **0.0506**（0.0368〜0.0659） |
| ④ 行数の10の組の中で | 0.0345（0.009〜0.0613） | 0.0803（0.0551〜0.1072） |
| ⑤ ①に行数もいっしょに入れる | 0.0125（0.0005〜0.0246） | 0.0635（0.051〜0.0777） |

- 変更の回数とバグの数の傾き（①②）は、本当の値0でも0.09前後、0.05でも0.13前後と、大きさの分が上乗せされた
- **行数もいっしょに入れた③は、置いた本当の値に近かった（−0.0003と0.0506）**。バグを「大きさの分＋変更の分」の足し算で作り、記録の行数を本当の大きさと同じに置いたためで、作りどおり
- 行数の10の組に分けた④は、ずれが0.0345・0.0303残った。組の中にも大きさの違いが残るため（いちばん大きい組は行数の幅が広い）
- 直しの変更を数に入れたままの⑤は、行数もいっしょに入れても0.0125・0.0135上にずれた。バグの多いファイルほど直しの変更が増え、変更の回数がバグを追いかけて増えるため

### 確かめ：27通りの置き方（各100回、`results/grid.csv`）
| 記録の行数のずれ τ | ② 直しを除いた変更のずれ | ③ 行数もいっしょに入れたずれ | ④ 組の中のずれ | ⑤ 直しも入れて行数を入れたずれ |
|---|---|---|---|---|
| 0（本当の大きさと同じ） | 0.0523〜0.1009 | **−0.002〜0.0017** | 0.0218〜0.0371 | −0.0025〜0.0225 |
| 0.3 | 0.0525〜0.1042 | 0.0118〜0.0198 | 0.0293〜0.0398 | 0.0079〜0.0437 |
| 0.6 | 0.0508〜0.1047 | **0.031〜0.0493** | 0.0358〜0.0546 | 0.0226〜0.0754 |

（ずれ＝数え方の値−置いた本当の値。各 τ で、本当の値3通り×α 3通りの9通りの範囲）
- 27通りすべてで、変更の回数だけの傾き（②）は置いた値より0.0508〜0.1047大きかった。本当の値0の9通りでも0.0532〜0.1042だった
- **③が当たるのは、記録の行数が本当の大きさをそのまま表すとき（τ=0）だけだった**。行数の記録がずれると（τ=0.6）、③にも0.031〜0.0493のずれが残り、置いた本当の値0.05と同じくらいの大きさになった。行数が本当の大きさ（バグの出やすさを決めるもの）を表しきれないと、その分が変更の傾きに残るため
- α（大きいファイルほど変更が多い度合い）が小さいほど、②のずれは大きかった（τ=0、本当の値0で α=0.5 のとき0.1009、α=1.1 のとき0.0537。`results/grid.csv` の bias_m2_feature_changes）。大きさで変更があまり増えないときは、変更の回数の差1回が大きさの大きな差にあたるためと考えられる（推測）

## 注意（言えないこと）
- 架空のデータです。ファイルの大きさの分布、変更の回数の決まり方、大きさの分のバグ、変更1回あたりのバグ、直しの変更の入り方は作成者が置いたもので、結果はこれで決まります。とくに③が当たるのは、バグを「大きさの分＋変更の分」の足し算で作り、記録の行数を本当の大きさと同じに置いたためで、作りどおりです
- 実際のファイルでは、行数のほかにも、込み入り具合・古さ・担当の入れかわりなど、変更の回数とバグの両方に関わるものがありえます。この記事では大きさだけを置きました。行数の記録のずれ（τ）は、そうした「行数で表しきれない分」の代わりとして置いたものです
- 変更がバグを持ちこむかどうかは、この記事のような記録の比べだけでは決めきれません。決めるのに何が要るかも、この記事では数えていません
- 実在のアプリのファイルの変更やバグの数を表すものではありません
