# F92 電力需要の「上振れ」はどこまで見込めばよいか？ 分位点予測とカバー率

## 問い

翌日の電力需要（1日のピーク）を予測するとき、外れたときに困るのは「実績が予測より上に出る」ほうである。では、予測に何%を上乗せしておけば、「95%の日はその範囲に収まる」と言えるのか。分位点を直接予測する方法（分位点回帰・LightGBM の分位点損失）と、点予測の外れ方から上乗せを決める方法（分割コンフォーマル）を、**実際に狙いどおりの割合で収まったか（カバー率）**で比べる。

## データ

- 東京エリアの日ごとのピーク需要（MW）：東京電力パワーグリッド「エリア需給実績」の1時間値から作成（F22・F67 と同じ）。2016年4月〜2026年9月、3,827日
- 関西エリア（頑健性用）：関西電力送配電「エリア需給実績」。2024年4月〜2026年9月、905日
- 気温・湿度：気象庁「過去の気象データ」（東京・大阪の日別値）
- `src/01_取得.py` は F67 のフォルダに置いた日別データを取ってくる（元の取得手順は F22・F67 の README）

## 手法

- 予測するもの：翌日のピーク需要（MW）。説明変数は当日の気温（平均・最高・最低）、湿度、冷房・暖房度日、曜日・休日・お盆・年末年始・GW、季節（年周期）、トレンド、前日と1週間前のピーク
- 比べる方法
  1. **点予測＋残差の分位点**（分割コンフォーマル）：LightGBM の点予測に、学習期間の最後の1年で測った外れ（実績−予測）の分位点を足す
  2. **線形の分位点回帰**：statsmodels の QuantReg（気温の2乗、休日との交差項を入れる）
  3. **LightGBM の分位点**：`objective="quantile"`
  4. 参考：点予測に一律3・5・8%を足す
- 狙う水準：0.5・0.8・0.9・0.95・0.975・0.99
- 評価：年度ごとの拡張ウィンドウ（2020年度〜2026年度上期の7回、計2,374日）。カバー率（実績が上限以下だった割合）、pinball 損失、点予測からの上乗せ幅、季節別、上の分位点が下の分位点を下回る「交差」

## 結果

| 方法 | 90% | 95% | 99% | 99%の上乗せ（中央から） | pinball(99%) |
|---|---|---|---|---|---|
| 点予測＋残差の分位点 | 89.4% | 95.0% | 99.2% | +10.2% | 44 MW |
| 線形の分位点回帰 | 89.1% | 93.4% | 96.9% | +9.0% | 58 MW |
| LightGBM の分位点 | 87.5% | 91.9% | 94.4% | +12.8% | 96 MW |

（点予測の平均の外れ MAPE は 2.5%）

1. **全体では「点予測＋残差の分位点」がほぼ狙いどおり**（95%→95.0%、99%→99.2%）。分位点を直接学習する2つは高い水準ほど足りなくなり、LightGBM の 99% は 94.4% しか収まらなかった。外れの多い日が少なく、木のモデルが端の分位点をうまく学べないためと考えられる（推測）
2. **季節で分けると、夏と冬は狙いより外れやすい**。95%の上限に収まったのは、点予測＋残差の分位点で夏 92.7%・冬 90.4%・その他 98.3%。全体の 95% は「穏やかな季節の余裕」で夏冬の不足を埋めた結果。最高気温35℃以上の113日では 84.1% だった
3. **一律の上乗せでも大差はない**。点予測に一律5%を足すと 96.4%、8%で 99.2% 収まり、点予測＋残差の分位点（95%で平均+4.8%）と同じくらいの効率だった（図4）。ただし一律の％が何%の安全度に当たるかは、こうして後から確かめないと分からない
4. **分位点の交差**：線形の分位点回帰とLightGBM の分位点は、別々に学習するため上下が入れ替わる日がかなりあった（隣り合う水準の組で延べ 2,346回・1,493回）。並べ替えで直すと、LightGBM の 99% は 96.3% まで上がる
5. **年度ごとのぶれ**：点予測＋残差の分位点の95%カバー率は年度によって 90.7%（2020年度）〜99.5%（2026年度上期）

## 頑健性

| 設定 | 点予測＋残差 95% / 99% | 線形QR 95% / 99% | LightGBM分位点 95% / 99% |
|---|---|---|---|
| 基本 | 95.0 / 99.2 | 93.4 / 96.9 | 91.9 / 94.4 |
| 交差を並べ替えで直す | 95.0 / 99.2 | 93.5 / 98.3 | 92.0 / 96.3 |
| 較正を季節別にする | 94.3 / 98.8 | — | — |
| 学習を直近3年に限る | 95.2 / 99.5 | 94.5 / 97.3 | 90.3 / 94.5 |
| **気温に誤差 σ=2℃ を足す** | **85.1 / 94.8** | **85.0 / 93.0** | **84.5 / 89.8** |
| 2020年度を評価から除く | 95.8 / 99.5 | 93.5 / 96.9 | 92.5 / 95.0 |
| 関西（評価183日・学習2年） | 97.3 / 100.0 | 100.0 / 98.4 | 83.6 / 94.0 |

- 方法の並び（点予測＋残差 ≧ 線形QR ＞ LightGBM 分位点）は、どの設定でもおおむね同じ
- いちばん効くのは**気温の誤差**。実績の気温を使った「理想の条件」でちょうど95%でも、予報くらいの誤差（σ=2℃）が入ると85%前後に落ちる。実際の運用では、上乗せをもっと大きくとる必要がある
- 季節別に較正しても全体のカバー率はほとんど変わらなかった（較正用の1年では夏・冬の日数が少ない）
- 関西は評価が半年だけで、線形QRの90%の上乗せが0%近くになるなど不安定。参考程度

## 言えないこと

- 気温は**実績値**を使っている（翌日の予報ではない）。実際の運用の外れはこれより大きく、頑健性のとおり 95% の上限でも 85% 前後しか収まらない可能性がある
- ピークは1時間値の最大で、需給の逼迫を決める 30分値・予備率・供給側の事情は見ていない。「この上乗せで停電を防げる」とは言えない
- 99% のような端の水準は、評価期間に外れが18日しかなく、カバー率の±1ポイントは偶然でも動く
- 関西は期間が短く、東京の結果を他のエリアに広げてよいかは確かめきれていない
- LightGBM の分位点の弱さは、今回の設定（木の数・葉の数）での結果で、調整すれば改善する余地がある
