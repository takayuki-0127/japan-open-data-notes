# 233 集計の合計が会計の数字と合わないとき、SQL のどこから疑うか（実務の型）

「3月の売上（税込）」のレポートの合計が、会計の数字と合わない。そんなときに SQL のどこから疑うかの順番を、架空の通販会社の注文データ（乱数で作成、seed 固定）で試したフォルダです。よくある原因5つ（結合で行が増える、期間の端、取消の注文、NULL のキー、丸め）をわざと入れたレポートを、点検クエリで1つずつ見つけて直しました。SQL は SQL Server（T-SQL）の書き方で書き、DuckDB で動かしています。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A233 | 集計が合わないとき、どんな順番で何を確かめればよいか。原因が打ち消し合うと何が起きるか | 結合の前後の件数、キーの重複、期間の最初と最後、状態ごとの件数、NULL のキー、丸め方の点検クエリ。原因を1つずつ直したときの差（ウォーターフォール）と、直す順番を全120通り変えたときの各原因の大きさ | `sql/01_report_before.sql`〜`04_report_after.sql`、`src/a233_make_data.py`・`a233_reconcile.py` |

## 主な結果
- 直す前のレポートは1億668万円で、会計の数字（1億1,095万円）より427万円（3.8%）少なかった
- 原因を点検の順に直すと、①住所の重複を直して−780万円、②期間の端（31日の0時以降が落ちていた）で+305万円、③取消の注文を除いて−401万円、④店が NULL の注文（ネット注文）を LEFT JOIN で戻して+1,304万円、⑤税の丸めを注文ごとに変えて−7,197円。直したあとのレポートは会計の数字と1円も違わず一致した
- 差の大きさは、5つの原因を足し引きした結果だった。①と③で多すぎ、②と④で少なすぎて打ち消し合い、直す前の差（3.8%）は、個々の原因（最大1,300万円台）よりずっと小さく見えていた
- 件数の点検（①）だけで、2つの原因が見えた。住所の表を結合すると行が35,718→38,469に増え（注文の数は11,963のまま）、店の表を結合すると注文の数が11,963→10,494に減った
- 直す順番を全120通り変えても、各原因の大きさの見積もりは同じ向きで、幅は「店が NULL」で1,266万〜1,453万円など。1つずつ直した分の大きさは、順番によって少し変わる

## 動かし方
```
pip install -r requirements.txt
cd src && python a233_make_data.py && python a233_reconcile.py
```
`src/common.py` の `tsql_to_duckdb()` が、T-SQL の `N'…'`・`CAST(… AS FLOAT)` などを DuckDB の書き方に置き換えてから実行します。

## データ
- `data/*.csv`：架空の通販会社のデータ（顧客6,000人、注文24,000件、明細71,814行、2026年2月15日〜4月15日）。`a233_make_data.py` が乱数（seed=233）で作ります。実在の会社・業務とは関係ありません
- `results/waterfall.csv`：原因を1つずつ直したときの合計
- `results/c1_counts.csv`〜`c5_nullkey.csv`：点検クエリの結果
- `results/order_dependence.csv`：直す順番を全120通り変えたときの、各原因の大きさの最小・最大・平均
- `results/summary.json`：まとめの数字

## 注意
- 架空のデータに、わざと原因を入れて作った例です。実際の業務では、原因がこの5つとは限りません。点検の順番は、筆者が手間の小さいものから並べた一つの型です（推測）
- SQL Server そのものでは動かしていません（未検証）。`BETWEEN` と日時の扱い、`FLOOR` と DECIMAL の計算は、SQL Server でも同じ結果になるはずです（推測）。税率の列は SQL Server の `DECIMAL(4,2)` を想定し、DuckDB でも DECIMAL で読んでいます
- 「会計の数字」は、注文ごと・税率ごとに円未満を切り捨てる、と決めた架空のルールです
