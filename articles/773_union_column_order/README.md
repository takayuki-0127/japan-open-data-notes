# 773 列の順番が違う2つの表を UNION ALL でつなぐと、何行の値が別の列に入るのか（実務の型）

UNION ALL は、列の名前ではなく列の位置で2つの表を合わせます。`SELECT * FROM a UNION ALL SELECT * FROM b` と書いたとき、b の表の列の順番が a と違うと、値は別の列に入ります。型が同じなら、エラーにはなりません。**ここでは、作成者が乱数で作った架空の2店の売上表（B 店だけ「金額・数量」の順）で、SELECT * でつないだ場合と、列名を書いてつないだ場合・UNION ALL BY NAME の場合を比べました。**

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A773 | 列の順番が違うと、何行の値が入れ替わり、合計はどうなるか | 架空の A 店3,000行（日付・店・品目・数量・金額）と B 店2,400行（日付・店・品目・金額・数量）。SELECT * の UNION ALL・列名を書いた UNION ALL・UNION ALL BY NAME を DuckDB（1スレッド）で実行し、正しい合計と一致するかを確認。seed 773 | `src/a773_union_order.py`、`src/02_union_duckdb.sql`、`src/01_union_tsql.sql` |

## 主な結果

| | 正しい（列名を書く・BY NAME） | SELECT * でつなぐ |
|---|---|---|
| 入れ替わった行 | 0行 | **2,400行（全体の44%）** |
| B 店の数量 | 7,196 | **2,608,080** |
| B 店の売上 | 2,608,080円 | **7,196円** |
| B 店の平均単価 | 362円 | **0.003円** |
| 2店の売上の合計 | 5,827,060円 | **3,226,176円（55%）** |

- B 店の2,400行（全体の44%）で、数量と金額が入れ替わった。どちらも整数なので、エラーは出なかった
- 2店の売上の合計は、正しい値の55%になった。残ったのは A 店の売上と、B 店の数量の合計だけ
- 列名を書いたつなぎ方と UNION ALL BY NAME は、どちらも正しい合計と一致した

## 動かし方
```
pip install -r requirements.txt
cd src && python a773_union_order.py
```
数秒で終わります。`data/store_a.csv`・`data/store_b.csv` もこのとき作ります。

## 確かめたこと
- 空のフォルダで流し直し、results・figures・data が一致した
- 列名を書いたつなぎ方と UNION ALL BY NAME で、店ごとの数量・金額が、元の表の合計と一致すること（assert）

## データ
- `data/store_a.csv`：架空の A 店の売上（sale_date・store・item・qty・amount）
- `data/store_b.csv`：架空の B 店の売上（sale_date・store・item・amount・qty。列の順番が違う）

## 注意（言えないこと）
- 架空のデータです。品目と単価は作成者が置いたもので、ずれの大きさはこれで決まります
- UNION ALL BY NAME は DuckDB の書き方です。SQL Server にはないので、T-SQL 版では列名を書いてつなぎます（T-SQL 版は未検証）
- 型の違う列が入れ替わる場合（日付と文字など）は、エラーになるか、暗黙の型変換で通るかが変わります。ここでは扱っていない
