# 295 集計をストアドプロシージャにまとめると、何がうれしいのか（実務の型）

同じ売上の集計を「呼び出し側で SQL の文字列をつないで作る形」と「引数の型と検査を持つストアドプロシージャ」の2つで書き、架空の依頼1,000件を通して結果を比べたフォルダです。プロシージャ本体は T-SQL で `sql/sp_sales_summary.sql` に置きましたが、**SQL Server 本体では試していません（未検証）**。DuckDB にはプロシージャがないので、同じ検査を Python の関数とパラメータ付きの文で再現して数えました（`src/a295_run.py` の `proc()`）。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A295 | 集計をプロシージャにまとめると、入力の誤りをどこまで止められるか | 架空の注文20万行（50店・2年）、架空の依頼1,000件（85%は正しい入力、15%はよくある入力の誤り6種類）、2つの形の答えを正解と照合 | `src/a295_run.py`・`a295_figs.py`、`sql/sp_sales_summary.sql`・`adhoc_concat.sql` |

## 主な結果
- 正しい入力の847件は、2つの形とも全件、正解と同じ答えだった
- 入力の誤り153件の行き先
  - **文字列をつなぐ形**：83件（54%）が**エラーにならずに数字を返した**。期間の逆転（27件）・全角の店コード（26件）・存在しない店コード（18件）は「0件・0円」、引用符入りの文字（12件）は誤った数字。止まったのは、ありえない日付（40件）と空欄（30件）の70件だけ
  - **プロシージャ**：153件すべてが集計の前に止まった（店コードなし44・日付の形40・必須30・期間の逆転27・長さ12）
- 引用符入りの例：店コード `S017' OR '1'='1` で2025年4月を頼むと、文字列をつなぐ形は「全店の4月＋その店の全期間」を1店の数字として返した。正しい値の88.4倍（46万円のはずが4,078万円、架空）
- 検査は5行ほど。`@store_code` を `VARCHAR(4)` で受けるだけだと、長すぎる文字は SQL Server では**黙って4文字に切り詰められる**ので、広めに受けて `LEN()` で長さを検査する形にした


## 確かめたこと

## 注意（言えないこと）
- 依頼の誤りの種類と割合（15%）は架空の置き方です。言えるのは「文字列をつなぐ形では、入力の誤りの一部がエラーにならずに数字として出ていく。型と検査を持つプロシージャなら集計の前に止められる」という向きまでです
- 文字列をつなぐ形でも、呼び出し側でパラメータ付きの文（`?` や `@p`）を使えば引用符の問題はなくなります。プロシージャの利点は、検査と集計の決まりを1か所に置き、どこから呼んでも同じ答えと同じ止まり方になることです（推測）
- 「存在しない店コードは0を返してよい」という考え方もあります。どちらにするかは使う人と決めることで、この記事では止める側にしました
- プロシージャのほかの利点（権限を集計だけに絞る、実行計画の再利用）は数えていません
- 定義の変更を1か所で直せる話は F275（コピペ型と共通ビュー型）で扱いました
