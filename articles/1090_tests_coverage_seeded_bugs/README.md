# 1090 カバレッジ80%のテストで、埋めこんだバグはどれだけ見つかるのか？（テストとバグ）

カバレッジは、テストを流したときにコードの何%の行を通ったかの割合です。「カバレッジ80%」は、テストが一度も通らない行が2割あるという意味で、通った8割の行にあるバグが見つかるという意味ではありません。バグは、その行を通ったうえで、テストの入力でおかしな結果が表に出て、テストがその結果を確かめたときにだけ見つかります。また、テストの強さを確かめるために、作成者がわざとバグを埋めこみ、何%見つかるかを数えることがありますが、埋めこむ場所と本当のバグが入りやすい場所が違えば、本当のバグの見つかり方とずれます。**ここでは、作成者が乱数で作った架空のアプリのコード（300の関数×30行＝9,000行。1つの関数は、ふだん通る行24行と、めったに通らない分かれ道2行×3つからなる）とテストで、カバレッジが50〜90%になったときに、行に一様に埋めこんだバグと、分かれ道に多く入ると置いた本当のバグが、それぞれ何%見つかるかを数えました。置き方を変えた27通りの確かめも行いました。**

例のアプリとテストは架空のもので、実在のテストの道具・開発のサービスの名前は使っていません。

関連する記事：同じ企画の 1089「見つかったバグが減ったのは、品質が上がったからか、テストが減ったからか？」は、テストの量と見つかる数の関係を、1091「ときどき落ちるテストを再実行で通すと、本当の不具合を何%見逃すのか？」は、テストが落ちたあとの扱いで見逃しが増えることを扱います。914「全数検査なら、不良はゼロになるのか？」は、工場の検査で、見つけにくい不良は検査をくり返しても残ることを数えていて、この記事の「行は通ったが見つからない」バグと同じしくみです。この記事は、ソフトウェアのテストに固有の「通った行の割合」と、わざと埋めこんだバグの見つかる割合の読み方に絞ります。

## 主な結果

### カバレッジと見つかったバグの割合（100回の平均、`results/by_coverage.csv`）
| カバレッジ | テストの本数 | ふだん通る行の通った割合 | 分かれ道の行の通った割合 | 埋めこんだバグ | 本当のバグ |
|---|---|---|---|---|---|
| 50% | 453.14本 | 59.49% | 12.63% | 13.35% | 8.75% |
| 60% | 705.4本 | 70.6% | 18.22% | 18.84% | 12.17% |
| 70% | 1,138.42本 | 81.07% | 26.23% | 25.61% | 17.6% |
| **80%** | 2,049.9本 | 90.38% | 38.99% | **35.25%** | **25.15%** |
| 90% | 4,761.74本 | 97.5% | 60.34% | 52.37% | 38.82% |

- **カバレッジ80%で見つかったのは、行に一様に埋めこんだバグの35.25%（10〜90%の範囲は28.9〜43.1%）、分かれ道に多いと置いた本当のバグの25.15%（18.33〜33.33%）だった**。埋めこんだバグの見つかる割合は、本当のバグより10.1ポイント高く出た
- カバレッジ80%のとき、ふだん通る行は90.38%通ったが、分かれ道の行は38.99%しか通らなかった。80%は「ふだん通る行をほぼ通り、分かれ道の多くを通らない」80%だった
- カバレッジが80%から90%に上がるまでに、テストの本数は2,049.9本から4,761.74本に増えた。残りの行の多くは、めったに通らない分かれ道だった

### カバレッジ80%のときの内訳（100回の平均）
| | 見つかった | 行は通ったが見つからない | 行を通らなかった | 行を通ったうち見つかった |
|---|---|---|---|---|
| 埋めこんだバグ | 35.25% | 45.53% | 19.22% | 43.64% |
| 本当のバグ | 25.15% | 39.0% | **35.85%** | 39.2% |

- 本当のバグは、半分ほど（50.9%）が分かれ道にあり、35.85%はテストが一度も通らない行にあった。埋めこんだバグで通らなかったのは19.22%で、ほぼ通らない行の割合（20%）どおりだった
- **行を通ったバグでも、見つかったのは4割ほど（埋めこんだバグ43.64%、本当のバグ39.2%）**。1本のテストが通ったときに見つかる確率は、表に出る確率の平均0.25×確かめる確率0.6＝0.15（式どおり）で、よく選ばれる関数は何本ものテストが通るので、0.15より高くなった。「カバレッジ80%×1本のテストで見つかる確率0.15＝12%」（式）と読むと、本当のバグの25.15%よりも低く見積もることになる

### 確かめる確率だけを変えた3つのテスト（どれもカバレッジ80.08%、`results/by_check.csv`）
| 確かめる確率 | 埋めこんだバグ | 本当のバグ |
|---|---|---|
| 0.3 | 24.05% | 16.88% |
| 0.6 | 36.25% | 24.87% |
| 0.9 | 43.4% | 30.63% |

- この3つは、上の表とは別の乱数で作ったテストとバグで数えた（そのため確かめる確率0.6の行は、上の表の35.25%・25.15%と少し違う）
- 同じカバレッジ80.08%でも、テストが結果を確かめる確率で、見つかる本当のバグは16.88〜30.63%と変わった。カバレッジの数字には、確かめているかどうかは出てこない

### 確かめ：置き方27通り（カバレッジ80%、各40回、`results/grid27.csv`）
- **本当のバグの見つかった割合は、27通りで5.92〜59.88%と動いた**。埋めこんだバグは11.57〜60.0%
- **埋めこんだバグから本当のバグを引いた差は、分かれ道のバグの入りやすさを4倍・8倍にした18通りすべてで正（+3.7〜+23.33ポイント）**で、1倍（本当のバグも一様）の9通りでは−0.87〜+2.68ポイントと、ほぼ同じだった（作りどおり）。差が正だったのは27通り中23通り
- 本当のバグが通らない行にあった割合は、入りやすさで19.08〜45.29%と動き、埋めこんだバグは18.93〜20.88%でほぼ変わらなかった
- 関数の選ばれやすさの偏りや、分かれ道に入る確率を変えても、差は+6.02〜+12.13ポイントだった（`results/extra.csv`）。分かれ道に入る確率を0.2にすると、80%に届くテストの本数は1,599.5本と少なくなり、分かれ道の行の通った割合は50.51%に上がって、差は+6.02ポイントに縮んだ

## 注意（言えないこと）
- 架空のデータです。コードの形（ふだん通る行と分かれ道）、テストの作り方、分かれ道へのバグの入りやすさ、表に出る確率、確かめる確率は作成者が置いたもので、結果はこれで決まります。カバレッジ80%で見つかる本当のバグは、置き方で5.92〜59.88%と動きました
- 「本当のバグは分かれ道に多い」は作成者の置き方です。埋めこんだバグとの差は、この置き方からそのまま出ます（入りやすさを同じにすると差は消えます）。実際のコードでどこにバグが多いかは、この記事では言えません
- 埋めこんだバグは、本当のバグと同じ「表に出る確率」の分布で置きました。実際にわざと埋めこむバグは、本当のバグより表に出やすいことも出にくいこともありえますが、入れていません
- 行を通ったかどうかだけを数えました。分かれ道のどちらに進んだか、入力の組み合わせをどれだけ試したかは数えていません
- 実在のアプリ・テストのカバレッジや見つかる割合を表すものではありません
