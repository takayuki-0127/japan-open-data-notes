# 1059 サーバーごとの99パーセンタイルを平均すると、全体の99パーセンタイルになるのか？（処理の速さ）

応答時間の遅い側を見るときは、99パーセンタイル（99%点。速い順に並べて99%の位置の値で、100件のうち99件はそれより速く終わる時間）がよく使われます。サーバーが何台もあると、台ごとの99%点は出ていても、全体の99%点は出ていないことがあります。そこで台ごとの99%点を平均したくなりますが、99%点は平均どうしのように足して割ることができません。**ここでは、作成者が置いた分布からの乱数で作った架空のアプリ（サーバー8台、1台だけ遅い側の裾が長い）の1時間分の応答時間で、台ごとの99%点の平均・件数で重みを付けた平均・中央値・最大と、全部の処理を合わせて数えた99%点を比べ、平均した値より遅い処理が本当は何%あるかを数えました。1分ごとの99%点を60分平均したときと、置き方を変えた27通りでも確かめました。処理時間はすべて作成者が置いた分布からの乱数で、実機の計測はしていません。**

平均どうしの平均（件数の違う平均をそのまま平均するずれ）は 345、割合の平均とまとめた割合の違いは 900 で扱っています。この記事はパーセンタイルどうしを平均するずれに絞ります。同じ企画の1058は99%点が何件測れば落ち着くかを扱う問いで、この記事では基本の置き方で1台あたりの件数を約1.2万件と多くして、件数の少なさによるずれがあまりまざらないようにしました（`results/per_server_one_hour.csv` の count）。平均が速くなっても遅い側が遅くなる場合は同じ企画の 1060、平均の待ち時間と長く待つ人の割合の違いは 873 で扱っています。

## 主な結果

### まとめ方ごとの値（基本、200時間の平均、`results/methods_200hours.csv`）
| まとめ方 | 値 | 本当の99%点（196.96ms）に対する比 | その値より遅い処理の割合（本当は1%） |
|---|---|---|---|
| ①台ごとの99%点の平均 | 158.13ms | **0.8028** | **1.63%** |
| ②件数で重みを付けた平均 | 158.07ms | 0.8026 | 1.63% |
| ③台ごとの99%点の中央値 | 118.24ms | 0.6003 | 3.31% |
| ④台ごとの99%点の最大 | 447.49ms | 2.272 | 0.12% |
| ⑤全部の処理を合わせて数える | 196.94ms | 0.9999 | 1.0% |
| ⑥区切りごとの件数を足し合わせる | 196.86ms | 0.9995 | 1.0% |

- **台ごとの99%点を平均すると、本当の全体の99%点より19.72%低く出た**。その値より遅い処理は1%ではなく1.63%あった。200時間の5〜95%の範囲でも0.7882〜0.8171倍で、毎回低く出た
- このずれは、置いた8台の分布から式で決まる値（台ごとの99%点の式の平均157.99ms、その値より遅い処理1.63%）と合った（式どおり）。乱数の揺れで出たずれではない
- 基本の置き方は8台に同じ割合で振り分けたので、②件数の重みを付けても①とほぼ同じ（−19.74%）だった
- 全体の99%点より遅い処理の96.82%は H の処理だった（1時間分）。全体の99%点は「いちばん遅い1%」を決める値なので、裾の長い1台がほとんどを決める。平均では H は8分の1の重みしか持たない
- ⑤全部を合わせて数えるか、⑥台ごとに同じ区切りで件数を数えて足し合わせれば、本当の値とほぼ同じ（1.0%）になった。⑥は台ごとの生の値を集めなくても、区切りの件数だけ送ればよい
- 確かめ：8台がまったく同じ分布なら、①の平均は本当の99%点の0.9997倍（50回の平均）で、ずれはほぼなかった（本当の値116.8msは式の値116.8msと一致、式どおり）。ずれは、台どうしの分布の違いから生まれる

### 1分ごとの99%点を60分平均すると（1台、200回、`results/minutes_200hours.csv`）
| まとめ方 | 本当の1時間の99%点（142.54ms）に対する差 | その値より遅い処理の割合 |
|---|---|---|
| 1分ごとの99%点の平均 | **−18.89%** | **2.83%** |
| 1分ごとの99%点の件数で重みを付けた平均 | −10.06% | 1.73% |
| 1分ごとの99%点の最大 | 本当の1.2828倍 | 0.23% |
| 1時間を合わせて数える | 本当の1.0002倍 | 1.0% |

- 1台の中でも、1分ごとの99%点を60分平均すると1時間の99%点より18.89%低く、その値より遅い処理は2.83%あった。混む分は件数が多く遅いのに、平均では1分が同じ重みになるため。件数で重みを付けても−10.06%残った

### 置き方を変えた27通り（各20回、`results/grid.csv`）
- ①台ごとの99%点の平均は、本当の99%点の**0.3886〜1.4933倍**だった。27通りのうち9通りで本当より2%以上高く、18通りで2%以上低く出た。**H の処理の量が少ない（ほかの1台の1/4倍）ときは高く、多いときは低く出て、向きまで変わった**
- その値より遅い処理の割合は0.39〜4.7%（本当は1%）
- ②件数で重みを付けた平均も0.6849〜1.0201倍（その値より遅い処理0.92〜1.94%）で、重みを付けても直らなかった
- ⑥区切りの件数を足し合わせる方法は、27通りすべてで0.9946〜1.0053倍に収まった
- ①の比は、どの通りでも置いた分布からの式の値と0.0194以内で合った（式どおり）。つまり、どちらにどれだけずれるかは、台どうしの分布の違い（作成者が置いたもの）で決まる

## 注意（言えないこと）
- 架空のデータです。台ごとの分布の形（対数正規分布）、中央値、裾の長さ、処理の振り分け方は作成者が置いたもので、結果はこれで決まります。①のずれは置き方で本当の0.3886〜1.4933倍と向きまで動きました。実在のソフトやサーバーの速さを表すものではありません
- 図1は1時間分の値（①156.15ms・⑤191.35ms、図の中では整数に丸めた）で、本文の表は200時間の平均（158.13ms・196.94ms）です
- 基本の置き方では1台あたりの件数を多くしたので、件数が少ないときに99%点が揺れる・偏る話はまざっていません（同じ企画の1058の問い）。件数の少ない台や1分では、ずれはさらに変わると考えています（推測）
- ⑥の区切りの方法は、区切りの幅（ここでは約2.3%）だけの誤差が残ります。区切りを粗くすると誤差は大きくなります（推測）
- どの監視の道具を使うべきかの助言ではなく、パーセンタイルどうしを平均したときのずれを数えただけです
