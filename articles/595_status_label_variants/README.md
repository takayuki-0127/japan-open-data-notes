# 595 「完了」「済」「済み」のように表記の揺れたステータス列をそのまま GROUP BY すると、何%の行が別のグループに分かれるのか（実務の型・表記ゆれ）

案件や申込みの表のステータス列には、同じ意味なのに表記が違う値がよく混ざります。「完了」「済」「済み」「完了済み」、末尾に空白の入った「完了 」、半角カナの「ｷｬﾝｾﾙ」などです。**ここでは、架空の案件表（2024〜2025年の24,000件、本当のステータスは5種類）で、①そのまま、②前後の空白を除く、③全角・半角をそろえる（NFKC）、④対応表で同じ意味の表記をまとめる、の4段階で GROUP BY し、グループの数・正規の名前でない行の割合・完了率を比べました。** 表記の混ざり方は作成者が置いたもので、数字はその仮定で決まります。文字コードの違い（文字化け）は扱わず、「同じ意味の別表記」だけを扱います。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A595 | 表記ゆれをそろえずに数えると、何%の行が別のグループに分かれ、完了率はどれだけ違うか | ステータスを4段階でそろえ、段階ごとにグループ数、正規の5種類（未着手・対応中・保留・完了・取消）に入らない行の割合、完了率を出す。登録月ごとの完了率も比べる。②と④を DuckDB（1スレッド）の SQL と Python で突き合わせ。seed 595 | `src/a595_status_variants.py`、`src/02_status_duckdb.sql`、`src/01_status_tsql.sql`（未検証） |

## 主な結果
- **そのまま**：22グループ。正規の5種類に入らない行は **22.3%**。完了率 **47.4%**（本当は62.8%）
- **空白を除く**：17グループ、入らない行17.9%、完了率50.6%（「完了 」455行・「完了　」307行が戻る）
- **全角・半角をそろえる**：16グループ（「ｷｬﾝｾﾙ」が「キャンセル」とまとまる）。完了率は変わらない
- **対応表で同じ意味をまとめる**：5グループ、完了率62.8%
- 「完了」の意味の表記は6通り。「完了」11,383行のほか、「済」1,773行・「完了済み」591行・「済み」560行・「完了 」455行・「完了　」307行
- **登録月ごとの完了率**：「完了」とぴったり同じ行だけを数えると、2025年6月の43.9%が7月に12.0%へ急に下がる（そろえた値は51.1%→47.5%）。7月に入力画面が変わり「済」が増えた、という置き方。本当の完了率との差は、6月まで平均9.8ポイント、7月から平均31.6ポイント

## 動かし方
```
pip install -r requirements.txt
cd src && python a595_status_variants.py
```
数秒で終わります。`data/tasks.csv`（task_id・created_on・status）と、表記の対応表 `data/status_map.csv`（variant・canonical）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- グループ数（そのまま22・空白を除いて17・対応表で5）と完了率が、Python と DuckDB の SQL（`02_status_duckdb.sql`）で一致した。対応表に無い表記は0行
- T-SQL 版（`01_status_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）。SQL Server の既定の照合順序では、末尾の半角空白や全角・半角を同じとみなす場合があり、グループ数が DuckDB や Python と変わりうる

## データ
- 案件24,000件。登録日は2024年1月〜2025年12月。古い案件ほど完了している
- 本当のステータスは5種類。それぞれに2〜6通りの表記を、決めた割合で混ぜた
- 2025年7月以降の登録分は、完了の表記の割合を変えた（「完了」86%→25%、「済」3%→55%）

## 注意（言えないこと）
- 架空のデータ。実際の会社の案件表ではない
- 分かれる行の割合は、表記の混ざり方で決まる
- 対応表は作成者が全部の表記を知っている前提で作った。実際のデータでは、まず出てくる表記の一覧（DISTINCT）を見て、対応表を作る必要がある
- 文字コードの違い（文字化け）は扱っていない
