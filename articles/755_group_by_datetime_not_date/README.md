# 755 時刻つきの日時のまま GROUP BY すると、日ごとの集計は何行に分かれてしまうのか（実務の型・SQL の日付）

注文の日時の列には、店舗の注文のように日付だけ（時刻 00:00:00）のものと、EC の注文のように秒まで入ったものが混ざることがあります。この列のまま `GROUP BY ordered_at` すると、日ごとではなく時刻ごとに行が分かれます。日付のカレンダー表と `ON ordered_at = d` で結ぶと、00:00:00 ちょうどの注文しか結びつきません。**ここでは、架空の1か月（2025年10月）の注文（店舗は日付だけ、EC は秒まで）を、5つの書き方で日別に集計しました。** 店舗と EC の割合や時刻の分布は作成者が置いたもので、数字はその置き方で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A755 | 時刻つきの日時のまま日別に集計すると、何行に分かれ、何件が落ちるか | A 日時のまま GROUP BY、B カレンダー表と「=」で結合、C 日付に直して GROUP BY、D 文字の先頭10桁、E 期間（d 以上 d+1 未満）で結合。DuckDB（1スレッド）と pandas で一致を確認。seed 755 | `src/a755_datetime.py`、`src/02_datetime_duckdb.sql`、`src/01_datetime_tsql.sql`（未検証） |

## 主な結果
- **A 日時のまま**：31日の注文13,264件が5,231行に分かれた（1日あたり168.7行）。行の99.3%は1件だけ。合計は合う
- **A の読み違い**：日付ごとの先頭の行だけ見ると、1日の注文数は平均260.0件（店舗の注文だけ）。本当は427.9件
- **B「=」で結合**：行は31行で見た目は正しいが、EC の注文5,205件（39.2%、売上の46.6%）がまるごと落ちた。00:00:00 ちょうどの EC の注文は0件だった
- **C・D・E は同じ答え**：日付に直す、文字の先頭10桁、期間で結合のどれでも31行・13,264件

## 動かし方
```
pip install -r requirements.txt
cd src && python a755_datetime.py
```
数秒で終わります。`data/orders.csv` に注文を、`results/daily_counts.csv` に日ごとの件数（正しい件数・「=」で結合した件数・A の行数）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 5つの書き方の結果が、pandas の groupby・normalize・isin と一致した
- T-SQL 版（`01_datetime_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- `data/orders.csv`：order_id・channel（店舗・EC）・ordered_at・amount
- 仮定：1日に店舗約240件、EC 約160件（土日は多い）。店舗の注文は日付だけ、EC は夜に多い時刻を秒まで入れた

## 注意（言えないこと）
- 架空のデータ。B で落ちる割合は、時刻つきの注文の割合で決まる
- 文字の先頭10桁（D）は、日時を `YYYY-MM-DD hh:mm:ss` の形で文字にしたときだけ使える。形が違うと別の結果になる
- タイムゾーンの違い（UTC で入った日時を日本の日付にする話）は扱っていない
- 実在の店の数字ではない
