# 1089 見つかったバグが減ったのは、品質が上がったからか、テストが減ったからか？（テストとバグ）

開発チームでは「今期はリリース前に見つかったバグが3割減った」と報告することがあります。けれども、見つかったバグの数は、入ったバグの数（品質）と、テストでどれだけ見つけられたか（テストの量）の掛け算です。品質が上がっても、テストを減らしても、同じように減ります。**ここでは、作成者が乱数で作った架空のアプリの開発チームのリリース（2週間ごと、前の12回と後の12回。リリースごとに入るバグの数と、テストの時間、バグ1つごとの見つけやすさを作成者が置いたもの）で、見つかったバグの数が同じ3割減になる3つの場合（A 入るバグが3割減った・B テストの時間を減らした・C 両方を半分ずつ）を作り、見つかった数・テスト1時間あたりの数・リリース後90日の報告を足した数で見分けられるかを数えました。置き方を変えた27通りの確かめも行いました。**

例のチームとアプリは架空のもので、実在の会社・テストの道具・開発のサービスの名前は使っていません。チームの人どうしを比べることはしていません。

関連する記事：同じ企画の 1090「カバレッジ80%のテストで、埋めこんだバグはどれだけ見つかるのか？」は、テストがどれだけのバグを見つけられるかそのものを、1091「ときどき落ちるテストを再実行で通すと、本当の不具合を何%見逃すのか？」は、テストの結果の扱い方で見逃しが増えることを扱います。914「全数検査なら、不良はゼロになるのか？」は、工場の検査で、見つけやすさが不良ごとに違うと検査をくり返しても見つけにくい不良が残ることを数えていて、この記事の「テストの時間を増やしても見つかる数が比例して増えない」と同じしくみです。1093「バグの見つかり方の曲線から、残りのバグの数はどこまで読めるのか？」は、見つかりやすさがバグごとに違うと残りを少なく見込むことと、テストの量が減った週は曲線が頭打ちに見えることを扱っていて、この記事の B（テストを減らすと見つかる数が減る）と同じ向きのずれです。919「改善の前後で不良率を比べるとき、何か月見ればよいのか？」は前後の比べ方の期間を、837「反応率の分母（フォロワー・表示・再生）で、良い投稿は入れ替わるのか？」は割る数で読み方が変わることを扱っています。同じ企画の 1095「リリースを細かく分けると、1回あたりの障害は減って見えるのか？」は、品質が同じでもリリースの回数（割る数）が変わるだけで1回あたりの障害が減って見える話で、この記事の「1時間あたり」と同じく、割る数の側の変化を品質の変化と取り違える形です。この記事は、見つかった数の減り方を、品質とテストの量に分けられるかに絞ります。

## 主な結果

### 見つかった数が同じ3割減になる3つの場合（前の12回から後の12回への変化、200回の平均、`results/scenarios.csv`）
| | 変化なし | A 入るバグが3割減った | B テストの時間を減らした | C 両方を半分ずつ |
|---|---|---|---|---|
| リリース前に見つかった数 | +0.92% | **−29.07%** | **−29.5%** | **−29.79%** |
| テスト1時間あたりの数 | +0.92% | −29.07% | **+59.37%**（式 +58.22%） | +14.05%（式 +13.7%） |
| ＋リリース後90日の報告を足した数 | +0.93% | **−29.74%**（式 −30%） | **−9.25%**（式 −9.55%） | −19.42%（式 −19.77%） |
| 入ったバグ（本当の数、作成者だけが知る） | +0.88% | −29.85% | +0.24% | −14.57% |
| リリース前に見つかった割合（足した数のうち、前→後） | 79.49%→79.43% | 79.24%→79.95% | 79.67%→**61.85%** | 79.45%→69.21% |

- **見つかった数だけでは、3つの場合は見分けられなかった**。10〜90%の範囲は、A が −36.39〜−21.88%、B が −37.16〜−21.85% でほぼ重なり、同じ回の A と B で A のほうが大きく減ったのは45%（半々）だった。見つかった数が20%以上減った回は、A 93.5%・B 92.5%・C 95.5%（変化なしは0%）
- **テスト1時間あたりで割ると、B（品質は変わっていない）は+59.37%と、品質が悪くなったように見えた**。テストの時間を半分にしても、見つけやすいバグは短い時間でも見つかるので、見つかる数は半分まで減らない（見つかる数はテストの時間に比例しない）。品質が15%上がった C も+14.05%と増えて見えた。値は見つかる確率の式どおり（B は式 +58.22%、C は式 +13.7%）
- **リリース後90日の報告を足すと、A は−29.74%（式どおり−30%）、B は−9.25%で、見分けがついた**。それでも B は0%にはならなかった。テストで見逃したバグのうち、90日で報告されるのは平均60%と置いたので、見逃しが増えた分の一部が数えられないため（式では−9.55%）
- 足した数が15%以上減った回を「品質が上がった」と読むと、A 100%・C 78.5%・B 17%・変化なし0%だった

### 確かめ：置き方27通り（各40回、`results/grid27.csv`）
| 見つけやすさのばらつき | 80時間で見つかる割合 | B で見つかる数を3割減らすテストの時間の減らし方 | B：1時間あたり | B：90日を足した数 | A：90日を足した数 |
|---|---|---|---|---|---|
| 0.5 | 50% | 39.93%減 | +18.67% | −7.72% | −31.33% |
| 0.5 | 90% | 62.82%減 | +90.94% | −11.0% | −31.22% |
| 1.0 | 70%（基本） | 55.76%減 | +61.29% | −9.38% | −31.07% |
| 1.5 | 50% | 52.74%減 | +42.14% | −9.02% | −29.36% |
| 1.5 | 90% | 82.21%減 | +288.43% | −11.72% | −29.51% |

（表は見つかる数の減り方30%の9通りのうち5通り。27通りすべては `results/grid27.csv`）

- **B のテスト1時間あたりの数は、27通りすべてで増えた（+7.68〜+571.69%）**。減り方30%の9通りでは+18.67〜+288.43%。もとの見つかる割合が高いほど、見つけやすさのばらつきが大きいほど、テストの時間を大きく減らさないと見つかる数が3割減らず、1時間あたりは大きく増えた
- 品質が上がった C でも、1時間あたりの数は27通り中20通りで増えた
- **90日の報告を足した数は、B が27通りで−19.97〜−3.16%（減り方30%では−11.72〜−7.72%）、A は減り方どおり（−50.74〜−13.4%）で、27通りすべてで A のほうが大きく減った（差は5.37〜38.69ポイント）**
- 使う人が90日で見つける割合を40%にすると、B の足した数は−15.36%と A（−29.38%）に近づき、80%にすると−3.55%（A −29.97%）だった。リリース後の報告が少ないほど、見分けにくくなった
- 前後6回ずつでは、変化なしでも見つかった数は10〜90%で−13.2〜+14.87%動いた（24回ずつでは−5.85〜+6.94%）。同じ回で A と B のどちらが大きく減ったかは、6〜24回ずつ・報告の割合を変えた4通りで43〜54%と、半々のままだった

## 動かし方
```
pip install -r requirements.txt
cd src && python a1089_fewer_bugs.py
```
15秒ほどで終わります。`data/releases_one_run.csv` もこのとき作ります。

## 確かめたこと
- 空のフォルダ（/tmp に `src` と `requirements.txt` だけを写したもの）で流し直し、results・figures・data の8ファイルがバイト単位で一致した（cmp、約15秒）
- 見つかった数・1時間あたり・足した数の平均を、見つけやすさの分布から出した式の値と並べた（`scenarios.csv` の `_formula` 列、`grid27.csv` の `_formula` 列）。1時間あたりの値の式との差は、27通りで最大6.55ポイントだった
- `data/releases_one_run.csv` の B（1回目）から数えた変化（見つかった数−28.29%、1時間あたり+62.11%）を `a1089_main.json` の `data_check` に書き、主な結果の範囲に入ることを確かめた
- 図3枚を開き、日本語・重なり・軸（棒は0から）を確かめた。図の値のラベルは results と同じ小数2けたにした（−の記号もそろえた）

## データ
- `data/releases_one_run.csv`：1回目の A・B・C のリリース24回ずつ。scenario・release・period（before／after）・test_hours（テストの時間）・bugs_in（入ったバグ。作成者だけが知る本当の数）・found_before_release（リリース前に見つかった数）・reported_90d（リリース後90日の報告）・not_found_90d（90日たっても見つからない数）
- `results/a1089_main.json`：主な結果すべて（置き方を変えた範囲も入れた）
- `results/scenarios.csv`：4つの場合ごとの変化の平均・10%・90%・式の値
- `results/grid27.csv`：27通りの確かめ
- `results/extra.csv`：報告の割合とリリースの回数を変えた確かめ

## 注意（言えないこと）
- 架空のデータです。入るバグの数、見つけやすさの分布、テストの時間と見つかる確率の関係（1−exp(−時間×見つけやすさ)）、使う人の報告の割合は作成者が置いたもので、結果はこれで決まります。B で1時間あたりが増える大きさは、置き方で+7.68〜+571.69%と動きました
- 主な値の多くは、置いた確率の式どおりです。新しく数えたのは、12回ずつのリリースでのぶれと、置き方を変えたときの幅です
- テストの時間は、ちょうど記録されていると置きました。テストの中身（どこを確かめるか）の違い、バグの重さ、テストで見つけやすいバグと使う人が見つけやすいバグの関係（ここでは別々に置いた）は入れていません
- リリース後の報告は90日分をすべて待ってから数えました。実際には、直近のリリースの報告はまだそろっていません
- 実在のチーム・アプリの品質を表すものではありません
