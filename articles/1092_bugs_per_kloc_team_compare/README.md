# 1092 千行あたりのバグ数で、チームどうしを比べてよいのか？（テストとバグ）

開発のチームごとに「見つかったバグの数÷千行」（千行あたりのバグ数）を並べ、少ないチームほど作りが確かだと読むことがあります。けれども、この数は3つのものが掛け合わさってできています。作りこまれたバグの多さ（知りたいもの）、テストでバグが見つかる確率（テストの厚さ）、同じ機能を何行で書くか（書き方）です。同じ機能を短く書くチームは、行数が少ないぶん千行あたりの数が大きく出ます。テストが薄いチームは、見つかる数が少ないぶん小さく出ます。**ここでは、作成者が乱数で作った架空のアプリの8つのチーム（担当する機能の数・1機能を書く行数・1機能あたりに作りこまれるバグ・テストで見つかる確率を作成者が置いたもの）で、4つの物差しで並べたとき、作成者が置いた「1機能あたりの作りこまれたバグ」の順をどれだけ当てるかを1000回数えました。行数の書き方の差・見つかる確率の差・機能の数を変えた27通りの確かめも行いました。**

例のアプリとチームは架空のもので、チームはA〜Hの記号だけです。人や人の属性を比べるものではありません。比べるのは、作成者が置いた「チームの担当部分の作りの確かさ」だけです。

関連する記事：1050「小さな町の数字を大きな町に当てはめると、規模の違いでどれだけずれるのか？」は1人あたりの値が規模で変わるときのずれを、1086「人数が倍になると、つながりの密度はどう変わるのか？」は割る数（ありうる組の数）が増えるだけで密度が下がることを、913「不良率の月ごとの上下は、工程の変化か偶然か？」は件数が少ないときのたまたまの上下を扱います。同じ企画の 1097「ストーリーポイントで数えた「速さ」は、チームどうしで比べられるのか？」は、チームごとに物差し（ポイントの付け方）が違う数でチームを比べる話で、この記事の書き方の違いと同じ形です。1098「直したあとに別の所が壊れる率は、何で割るかでどう変わるのか？」は、千行あたりを含む6つの割り方で修正の壊れの率を比べ、千行あたりが当たるかどうかも置いた大きさの効き方で変わることを、1096「変更の多いファイルほどバグが多いのは、変更のせいか、ファイルの大きさのせいか？」は、ファイルの行数という大きさがバグの数に混ざる話を扱います。この記事は、千行あたりという割り方そのものと、見つかった数で数えることのずれに絞ります。

## 主な結果

### 1回分の8チーム（`data/teams_one_draw.csv`）
- 置いた確かさでいちばん確かなのはGだったが、①千行あたりでいちばん少なかったのはEだった。8チームの①の順と正しい答えの順の順位相関は0.0だった
- Gは1機能を短く書くチーム（書き方の係数0.5819）で、行数が少ないぶん①が1.36と大きく出て3番目になった
- Eは1機能あたりのバグが多い（0.6709、少ないほうから7番目）が、見つかる確率が56.64%と低く、①は1.14でいちばん少なかった

### 4つの物差しの当たり（基本の置き方、8チーム×1000回、`results/measures_base.csv`）
| 物差し | いちばん確かなチームを当てた割合 | 順位相関 | 2チームの上下が合った割合 |
|---|---|---|---|
| ① 見つかったバグ÷千行 | **37.4%** | 0.517 | 70.2% |
| ② 作りこまれたバグ÷千行 | 39.3% | 0.5581 | 72% |
| ③ 見つかったバグ÷機能の数 | 44.35% | 0.6513 | 76.14% |
| ④ 作りこまれたバグ÷機能の数 | 52.8% | 0.7461 | 80.87% |

- でたらめに選んだときの当たりは12.5%（8チームの1つ）。①は37.4%で、④（すべてのバグが分かり、機能の数で割る、実際にはできない比べ方）の52.8%より低かった
- ②（すべてのバグが分かっても千行で割る）は39.3%で、①とあまり変わらなかった。基本の置き方では、①が外れる分のうち、千行で割ることによる分が大きかった
- ④でも52.8%なのは、作りこまれたバグの数そのものが乱数で上下するため
- ①のチームどうしの比は、期待値では「1機能あたりのバグの比×見つかる確率の比÷書き方の係数の比」になる（式どおり）。機能の数を2万にしてたまたまの上下を小さくすると、2000組で式との差は対数で中央値0.0123、最大0.074だった

### 作りの確かさを全チーム同じに置くと
| | 値 |
|---|---|
| ①の最多÷最少（1000回の中央値） | **3.27倍**（10〜90%：2.2〜5.38倍） |
| ①の最多÷最少が1.5倍以上になった回 | 99.9% |
| ④の最多÷最少（中央値） | 1.82倍 |

- 確かさに差がまったくなくても、①ではチームの間に中央値で3.27倍の差が出た。書き方と見つかる確率の差、たまたまの上下が重なった分

### 確かめ：置き方27通り（各400回、`results/grid.csv`）
| 物差し | いちばん確かなチームの当たり | 順位相関 |
|---|---|---|
| ① 見つかったバグ÷千行 | 24.04〜69% | 0.3283〜0.8613 |
| ③ 見つかったバグ÷機能の数 | 25.08〜69% | 0.4125〜0.8613 |
| ④ 作りこまれたバグ÷機能の数 | 30.21〜75.88% | 0.5133〜0.8982 |

- **書き方の差を置いた18通りすべてで、①の順位相関は③を下回った**。書き方の差を0にした9通りでは、行数が機能の数に比例するので①と③は同じ値になる（作りどおり）
- 書き方の差を0.5にすると、①の順位相関は機能の数を15から240に増やしても0.3283〜0.4329にとどまった（機能の数を増やすと縮むのはたまたまの上下だけで、書き方の差による片寄りは残る）
- 見つかる確率の差を広げる（0.4〜1.0）と、③も④から離れた（機能の数240で③0.6302〜0.648、④0.8866〜0.8982）

## 注意（言えないこと）
- 架空のデータです。機能の数、書き方の差、1機能あたりのバグの差、見つかる確率の差は作成者が置いたもので、結果はこれで決まります。①の当たりは、置き方27通りで24.04〜69%と動きました
- 「機能の数」は、誤差なく数えられると置きました。実際には機能の数え方にも決まりと誤差があり、③は今回より外れます（推測）
- バグの数は機能の数に比例すると置きました。大きな担当部分ほど1機能あたりのバグが増える（または減る）ことは入れていません。バグの重さ（深刻度）の違いも入れていません
- 実在のチーム・会社・開発のやり方を表すものではありません。チームや人の良し悪しを決めるものでもなく、千行あたりのバグ数が何を混ぜて数えているかを数えただけです
