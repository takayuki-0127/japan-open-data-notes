# 571 UTCで保存した時刻を日本時間に直さずに日付で集計すると、何件が前日に入るのか（実務の型・タイムゾーンと日付の集計）

システムによっては、注文の時刻を UTC（協定世界時）で保存しています。日本時間は UTC より9時間進んでいるので、UTC の時刻をそのまま日付にすると、日本時間の0時〜8時59分の注文が前日の日付に入ります。**ここでは、架空の注文（2025年の1年分、59,881件）を、3通り（正 日本時間に直してから日付にする・UTCのまま日付にする・2回直す（すでに日本時間の値にさらに9時間足す））で日別・曜日別・月別に集計して比べました。** 時刻の分布と11月1日0時開始のセールは作成者が置いたもので、数字はその仮定で決まります。

|---|---|---|---|
| A571 | 日付の切り方で、日別・曜日別・月別の件数と売上がどれだけ変わるか | 注文時刻（UTC）に +9時間 して日付にしたものを正とし、UTCのまま・+18時間 と比べる。日別の売上のずれ（%）の分布、曜日別の構成比、月別の合計、年の境目に落ちる件数。日本時間と UTC のままの日別件数を Python と SQL（DuckDB、1スレッド）で突き合わせ。seed 571 | `src/a571_utc_date.py`、`src/02_date_duckdb.sql`、`src/01_date_tsql.sql`（未検証） |

## 主な結果
- **UTCのままだと前日に入る注文**：9,590件（全体の16.0%、売上でも16.0%）。日本時間の0〜8時台の注文がすべて前日になる
- **日別の売上のずれ**：絶対値の中央値 3.7%、上位10%の日で 9.4%以上。5%を超える日が129日、10%を超える日が31日
- **0時開始のセール**：11月1日の売上 546万円が、UTCのままだと 85万円になり、10月31日が 84万円から 545万円になる。月別でも10月が +18.8%、11月が −15.6%
- **曜日**：金曜の構成比が 14.7% → 16.3%、土曜が 17.4% → 15.8% になる（土曜0時台の注文が金曜に入る）
- **年の境目**：2025年1月1日の注文のうち19件が、2024年12月31日の日付になる
- **2回直すと**：日本時間の15時以降の注文（55.8%）が翌日に入る。直していないのか、二重に直しているのかは、深夜と昼の件数の比で見分けがつく

## 動かし方
```
pip install -r requirements.txt
cd src && python a571_utc_date.py
```
数秒で終わります。`data/orders_utc.csv`（order_id・ordered_at_utc・amount）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 日本時間の日付と UTC のままの日付の日別件数が、Python と DuckDB の SQL で一致した
- T-SQL 版（`01_date_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- 2025年1月1日〜12月31日（日本時間）の注文。1日あたり平均160件（曜日で ±10%程度）、時刻は夜に山がある分布
- 11月1日は0時開始のセールとして、0〜2時台に約900件を足した
- 金額は対数正規分布（中央値 約4,200円）

## 注意（言えないこと）
- 架空のデータ。実際の店の数字ではない
- 前日に入る割合は、深夜〜朝の注文の多さで決まる。夜の注文が少ない業種では小さくなる
- 夏時間のある地域の時刻は扱っていない（日本時間は年中 UTC+9）
- 時刻の列が UTC か日本時間かは、データの定義書や、深夜の件数の多さで確かめる必要がある
