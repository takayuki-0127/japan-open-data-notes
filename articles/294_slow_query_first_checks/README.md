# 294 SQL のクエリが遅いとき、まず何を見るか（実務の型）

架空の注文データ100万行を SQLite に置き、「遅いクエリ」でよくある5つの場面を、実行プランと実行時間で比べたフォルダです。SQL Server 用の手順（T-SQL）も `sql/` に置きましたが、**SQL Server 本体では試していません（未検証）**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A294 | クエリが遅いとき、実行プランのどこを見て、何を直すと速くなるか。索引はいつでも速いのか | SQLite の `EXPLAIN QUERY PLAN`、索引の有無・列の順番・カバリング索引・`INDEXED BY`／`NOT INDEXED` で強制した比較、5回の中央値の時間 | `src/a294_make_data.py`・`a294_cases.py`・`a294_figs.py`、`sql/01_first_checks_sqlite.sql`・`01_first_checks_tsql.sql` |

## 主な結果（100万行、この環境での時間。倍率を見る）
| 場面 | 直す前 → 直した後の実行プラン | 時間 |
|---|---|---|
| 1 絞り込む列に索引がない | SCAN（全部読む）→ SEARCH（索引で絞る） | 31ms → 0.01ms（約3,000倍） |
| 2 列に関数をかけている（`strftime('%Y-%m', 日付)`） | 索引があっても SCAN → 範囲の条件に書き直すと SEARCH | 175ms → 29ms（6倍） |
| 3 複合索引の列の順番が（日付, 店） | 期間内を全部なめる → （店, 日付）にすると等号と範囲の両方で絞れる | 9.4ms → 1.0ms（約10倍） |
| 4 索引に金額がなく、本体へ取りに戻る | SEARCH → SEARCH COVERING INDEX（索引だけで答える） | 116ms → 3.3ms（35倍） |
| 5 9割の行が当てはまる条件で索引をたどる | 索引 → 全部読む（SCAN） | 79ms → 52ms（1.5倍） |

- **索引はいつでも速いわけではない**：当てはまる行の割合を1〜100%で変えると、索引をたどるほうが速いのは1〜2%まで、5%で同じくらい、それより多いと全部読むほうが速かった（100%では索引が14倍遅い）
- SQLite の自動の判断（ANALYZE 済み）は、この列では当てはまる割合が100%でも索引を選んだ。オプティマイザの判断が外れることがあるので、時間を測って確かめる
- 5つとも、直す前と後で答え（件数・合計）が同じことを確かめた
- 実行プランの読み方：「SCAN か SEARCH か」「どの列で絞れているか（`customer_id=?` など）」「COVERING か（本体へ戻らないか）」の3つ。SQL Server では Table Scan／Index Seek／Key Lookup に当たる

## 確かめたこと
- 空のフォルダで作り直すと、`orders.sqlite` はバイト単位で同じ、5つの実行プランはすべて同じ、時間は±1割以内（倍率の向きと大きさは同じ）
- 時間はこの作業環境（2コア）の値で、機械や混み具合で変わる。比べるのは倍率

## 注意（言えないこと）
- SQLite（行の形で保存する組み込みのデータベース）での結果です。SQL Server でも考え方（Scan と Seek、関数で索引が使えない、複合索引の列の順番、INCLUDE、統計情報）は同じですが、時間・境目の割合・オプティマイザの判断は違います（推測）。列の形で保存するデータベース（DuckDB など）では、索引がなくても集計は速く、話が変わります
- 境目の「5%前後」は、この表の行の大きさ・並び（注文番号順で、条件の列はばらばらに散っている）での値です。条件に当てはまる行が表の中でまとまっていれば、索引が速い範囲は広がります（推測）
- 遅さの原因は索引と書き方だけではありません（ロックの待ち、統計情報の古さ、パラメータの値で計画が変わる問題、ネットワーク）。この記事は「まず実行プランを見る」場面だけを扱いました
