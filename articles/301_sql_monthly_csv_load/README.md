# 301 公的統計の CSV を、SQL Server に毎月取り込む形はどう作るか（実務の型）

毎月届く統計の CSV を表に取り込む「形」を4つ作り、同じ25か月分の届き方（前月の値の直し＝確報、同じファイルの2回流し、桁区切りのコンマと「-」、途中の失敗、2か月前のファイルの直した版）を流して、どこで数字がずれるかを数えたフォルダです。取り込みの SQL は T-SQL 版を `sql/01_load_tsql.sql` に置きました（**SQL Server 本体では動かしていません＝未検証**。`BULK INSERT` は T-SQL だけの命令で、同じ流れを DuckDB で動かして確かめました）。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A301 | 毎月の CSV の取り込みは、どの形にすると、流し直しや値の直しがあっても数字がずれないか | 商業動態統計の6業態の月次販売額をもとに、25回分の届け（当月の速報＋前月の確報）を作る。A＝型つきの表にそのまま追記／B＝ステージング表で型を確かめて追記し「最後に入れた行」を選ぶビューで読む／C＝ステージング＋型の確認＋キーで入れ替え＋取り込みの記録（1つのトランザクション）／D＝C＋届けの新しさを比べて、新しい版だけ入れ替える。取り込みのたびに「その時点の正しい姿」と突き合わせる | `src/a301_load_designs.py`、`sql/01_load_tsql.sql` |

## 主な結果
- 届いたファイルは26個（毎月25個＋直した版1個）、取り込みは形ごとに29回。突き合わせたキー（業態×月）は150個
- **A そのまま追記**：速報と確報が両方残り、150キーのうち144キーが確報と違った。年の合計は2024年が+116%、2025年が+128%。コンマ入りのファイルは型が合わず、ファイル全体が失敗した
- **B 追記＋最後の行を選ぶビュー**：ビューを通せば、2024-10 の取り込みまでは正しい姿と一致。ただし 2024-11 に「2024-09 のファイルの直した版」を流すと、9月の6キーが確報から速報に戻り、そのあと15回の取り込みのあいだずっと残った（最後まで6キー）。ビューを通さずに表を直接集計すると144キーが違う。「-」の1行は黙って落ちた
- **C キーで入れ替え＋記録**：同じファイルの2回目は中身のハッシュで飛ばし（2回）、途中の失敗は元に戻り、「-」の1行ははじいて記録した（1行）。それでも B と同じく、直した版で9月の6キーが速報に戻った
- **D C＋新しい版だけ入れ替える**：25回の取り込みのどの時点でも、ずれは0。直した版の9月の6行は「すでに新しい届けの行がある」ので入れ替えなかった
- 表に残った行（2023-12 以降）：A 324行、B 335行、C・D 150行

## 動かし方
```
pip install -r requirements.txt
cd src && python a301_load_designs.py
```
`data/incoming/` に届くファイル26個を作り（実行時に作るので GitHub には置いていません）、4つの形で取り込み、`results/`・`figures/` を出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures が一致した
- 「その時点の正しい姿」は、取り込みの処理とは別に、届いたファイルから Python の辞書で作った（いちばん新しい届けの値。同じ届けなら後に届いたほう）

## 注意（言えないこと）
- T-SQL 版（`BULK INSERT`・`TRY_CONVERT`・`DELETE … JOIN`）は SQL Server 本体では動かしていません。DuckDB では `read_csv(all_varchar=true)`・`TRY_CAST` で同じ流れを試しました
- 届き方（速報のずれ0.4%、起きることの月）は作成者が決めたものです。実際の商業動態統計の速報・確報の差ではありません
- 「届けの新しさ」はファイル名の年月から取りました。ファイル名に年月がない、同じ年月で何度も直る、といった場合は、版の番号や公表日を別に持つ必要があります
- A・B で「6行ずつ確定する」としたのは、`BULK INSERT` に `BATCHSIZE` を付けた場合に当たります（付けなければ1つのトランザクションです）
- 入力の検査（型・範囲・列どうし）そのものは 260、取り直したファイルの変化の見つけ方は 259 で扱いました。この記事は「入れ方」に絞っています
