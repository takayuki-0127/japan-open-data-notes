# 305 DAX の CALCULATE は、何をしているのか（実務の型）

Power BI のメジャーでつまずきやすい `CALCULATE` の動きを、架空の売上表で確かめたフォルダです。**DAX そのものは実行していません（Power BI がないため未検証）。** DAX の決まりどおりに読んだときの値を、(1) 絞り込みの入れ替えを模した小さな Python の関数と、(2) 1本ずつ手で書いた SQL（DuckDB で実行）の2通りで出し、12本とも一致することを確かめました。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A305 | `CALCULATE` の条件は、いまの絞り込みに「足される」のか「入れ替わる」のか | 架空の売上 13,897行（12店・4カテゴリ・2年）。12本のメジャーを、決まりどおりの読みと2つの単純な読み（足すだけ／いつも入れ替える）で計算して比べる | `src/a305_run.py`・`a305_figs.py`、`dax/measures.dax`、`sql/measures.sql` |

## 主な結果
評価する場所は、スライサーが「年=2025・地域=関東」、行が「日用品」のセルです。
- **「条件は WHERE に AND で足すだけ」と読むと、12本中7本で違う数字になった**（M02・M04・M05・M06・M07・M08・M12）
  - `CALCULATE([売上], Product[category] = "食品")` は、行の「日用品」を「食品」に**入れ替える**ので 1,196万円。足すだけと読むと「日用品かつ食品」で空
  - `ALL(Product[category])` は絞り込みを**外す**（3,967万円）。構成比の分母に使うと 18.9%
  - `AVERAGEX(Store, SUM(Sales[amount]))` は行ごとに絞られず、749万円（そのセルの合計）のまま。`AVERAGEX(Store, [売上])` と書くと店ごとに絞られて 125万円（6店の平均）
- **「条件はいつも入れ替える」と読むと、12本中3本で違った**（M03・M09・M10）
  - `KEEPFILTERS` をつけると重なる（日用品かつ食品＝空）
  - `FILTER(Sales, …)` は、いまの絞り込みの中の行を絞る（98万円）。入れ替えると読むと 3,499万円
  - スライサーが「店=S02」のとき `Store[region] = "関西"` を足すと、**列が違うので店の絞り込みは残り**、空になる
- まとめると「同じ列の絞り込みは入れ替える、違う列は重なる、`ALL` は外す、`KEEPFILTERS` は重ねる、メジャーを参照すると行が絞り込みに変わる」

## データ
- `data/sales.csv`（年・月・店・カテゴリ・金額、13,897行）、`data/stores.csv`（店と地域、12行）。作成者が乱数で作った架空のデータ（seed 305）。実在の会社の数字ではありません
- `results/measures.csv`：12本の DAX・決まりどおりの値・2つの単純な読みの値・照合に使った SQL とその値
- `results/share_by_category.csv`：構成比の分母を `ALL(列)` にした場合と `ALL(表)` にした場合

## 確かめたこと
- 決まりどおりの値は、Python の関数と手で書いた SQL の2通りで12本とも一致
- 空のフォルダで流し直し、data・results・figures・dax・sql の10ファイルがバイト単位で一致

## 注意
- **DAX は実行していません。** 決まりは Microsoft の公開ドキュメント（CALCULATE・KEEPFILTERS・ALL・コンテキスト遷移）の説明に沿って読んだものです。関係の向き（店・商品・日付の表から売上の表へ1方向）と、スライサーが年の列だけにかかっていることを前提にしています。日付の表を「日付テーブルとしてマーク」した場合や双方向の関係では、動きが変わることがあります
- 「単純な読み」は説明のために置いた2つの読み方で、実際に何割の人がそう読むかは調べていません
- 12本は作成者が選んだ例です。7本・3本という本数は、例の選び方で変わります
