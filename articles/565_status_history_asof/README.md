# 565 状態が何度も変わる申込みで、過去のある日の状態を履歴からどう戻すのか。今の状態で数えると何件ずれるか（実務の型・状態の履歴と as-of）

申込みの状態（受付・審査中・保留・承認…）は何度も変わります。「去年の12月末に審査中だった件数」を出すには、今の状態ではなく、履歴からその日の状態を戻す必要があります。**ここでは、架空の申込み（2024年1月〜2025年12月、15,000件）と状態の履歴57,201行（うち3,322行はあとから入力）で、24か月の月末ごとの状態別の件数を、3通り（正 有効日で戻す・当 記録日で戻す・今 今の状態で数える）で出して比べました。** 状態の変わり方と入力の遅れは作成者が置いたもので、数字はその仮定で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A565 | 戻し方で、月末の状態別の件数がどれだけ違うか | 有効期間つき履歴（valid_from、valid_to は次の履歴の valid_from）。正：valid_from ≦ 月末 < valid_to。当：月末までに記録された履歴（recorded_on ≦ 月末）だけで同じことをする。今：月末までに受けた申込みを、2025年末の状態で数える。月末ごとに「正」と状態が違う申込みの数も数える。「正」の24か月分を Python と SQL（DuckDB、1スレッド）で突き合わせ。seed 565 | `src/a565_status_asof.py`、`src/02_asof_duckdb.sql`、`src/01_asof_tsql.sql`（未検証） |

## 主な結果
- **今の状態で数えると**：過去の月末の「審査中・保留」は、ほぼ0件になる（「正」との差は平均 −542件、24か月平均で −93.9%）。そのぶん承認・否認・取下げ・解約が多く出る（承認は平均 +160.6件、最大 +289件）
- **2024年12月末の例**：正では審査中 345件・保留 213件・承認 3,835件・解約 252件。今の状態で数えると審査中 0件・保留 0件・承認 3,913件・解約 542件
- **状態が「正」と違う申込み**：今の状態で数えると、24か月平均で 17.7%（2024年1月末は 74%、月が新しいほど小さい）。2024年12月末は 7,412件中 872件
- **記録日で戻すと（当時見えていた数）**：「正」との違いは小さいが、ゼロではない。審査中・保留は平均 +9.3件（−6〜+23件）、承認は平均 −14.0件。状態が違う申込みは平均 1.3%。あとから入力される履歴（全体の5.81%）のぶん、当時の数は少し古い状態のまま
- 「正」と「当」のどちらを使うかは目的による。今わかっている正しい状態で過去を見るなら「正」、当時の報告を再現するなら「当」

## 動かし方
```
pip install -r requirements.txt
cd src && python a565_status_asof.py
```
数秒で終わります。`data/status_history.csv`（app_id・seq・status・valid_from・recorded_on）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- 24か月の月末の「正」の状態別件数が、Python と DuckDB の SQL で一致した
- T-SQL 版（`01_asof_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）

## データ
- 受付から1〜5日で審査中。30%の確率で保留に回り（2〜14日後）、5〜39日後に審査中に戻る（くり返すこともある）。審査中から3〜29日で、承認60%・否認25%・取下げ15%。承認の12%は30〜299日後に解約
- 2番目以降の履歴の8%は、有効日より3〜30日遅れて記録される（データ全体では5.81%）
- 2025年12月31日より後に有効になる履歴は入れていない

## 注意（言えないこと）
- 架空のデータ。実際の申込みの数字ではない
- 差の大きさは、状態が変わる速さと、入力の遅れ方で決まる
- 同じ日に状態が2回変わる場合は扱っていない（seq で順番を決める形にはしてある）
