# 1167 消したはずの分が実際に空くまでに時間がかかると、空き容量の見込みはどれだけずれるのか？（データ量の見込み）

保存の場所の空きを見込むとき、「消したものの分はその日に空く」と数えることがあります。けれども、消したものをしばらく戻せるように残しておく決まりや、消したものを片付ける処理が1日に空けられる量の上限があると、消した分が実際に空くのは後になります。とくに、古い置き場をまとめて消した日には、見込みの空きはその日に大きく増えますが、実際の空きはなかなか増えません。**ここでは、作成者が置いた架空のアプリの保存領域（毎日の書き込み・90日たったら消す決まり・消してから戻せるように残す日数・片付けの速さを置き、乱数で作ったもの）で、「消したらすぐ空く」と見た見込みの空きと実際の空きの差を、ふだんの日と、3,000GBをまとめて消した日のあとで数えました。残す日数・片付けの速さ・書き込みのばらつきを変えた24通りで確かめました。**

ふだんのずれは「残す日数×1日に消す量」で、まとめて消したあとに空きが見込みに追いつくまでの日数は「残す日数＋3,000GB÷片付けの余力（片付けの速さ−ふだん1日に消す量）」で、どちらもほぼ決まります（式どおり）。この記事で数えて新しく分かったのは、まとめて消した3,000GBそのものが空き終わっても、そのあいだに待たされたふだんの消した分のために、実際の空きが見込みに追いつくのはさらに後になる、という日数の開きです。

関連する記事：883「開店直後の行列は、何分で解消するのか？」は、行列が減る速さは会計の速さではなく、会計の速さから来る速さを引いた「余力」で決まる、という形を扱っています。この記事のまとめて消した分の片付けも同じ形です。874「利用が8割を超えると、待ち時間はなぜ急に伸びるのか？」は、処理の速さが来る量に近いと待ちが伸びる形です。514「入庫と出庫の記録が遅れて届くと、在庫が一時的にマイナスになる日は何日あるのか？」は、記録の遅れで見かけの在庫が本当の在庫からずれる形を扱っています。この記事は、消した記録と実際に空く時期のずれに絞ります。同じ企画の 1166「古いものを消す決まりを入れると、量の伸びはどこで止まり、そこまで何日かかるのか？」は、同じ「90日たったら消す」決まりで、消した分がすぐ空くと置いたときに量が止まる高さと日数を扱っています。1170「空きが何%を切ったら足すと決めるとき、増え方のばらつきで、足りなくなる日の何日前に気づけるのか？」は、空きが正しく数えられるときに、増え方の振れで気づく日がどれだけ散らばるかを扱っています。この記事のずれがあると、見込みの空きで気づく日はさらに遅れると考えられます（推測）。

## 主な結果

### ふだんのずれ（`results/a1167_main.json` の `base_steady`・`base_hold_only`）
| | 片付けの上限あり（1日150GB） | 上限なし（残す7日だけ） |
|---|---|---|
| 消したのに空いていない量の平均 | **701.7GB** | 699.9GB |
| その95%点 | 841.0GB | 838.2GB |
| 最大 | 1,152.2GB | 1,152.2GB |
| 1日の書き込みの何日分か | 7.02日分 | 7.0日分 |

- ふだんの日は、見込みの空き（平均3,001.2GB）が実際の空き（平均2,299.5GB）を上回り、見込み÷実際は平均1.3119倍だった。ずれは容量の4.68%にあたる
- ずれの平均は「残す日数7日×1日に消す量の平均100GB＝700GB」にほぼ同じだった（式どおり）。片付けの上限による上乗せは1.8GBだけだった

### 3,000GBをまとめて消した日のあと（500回、`results/a1167_main.json` の `base_event`、`results/event_gain_by_day.csv`）
| まとめて消した日からの日数 | 見込みの空きの増え | 実際の空きの増え（平均） | 3,000GBに対する割合 | 古い置き場そのものが空いた割合 |
|---|---|---|---|---|
| 0日（その日） | 3,000.0GB | 0.0GB | 0% | 0% |
| 7日 | 3,000.0GB | 49.0GB | 1.63% | 4.95% |
| 14日 | 3,000.0GB | 402.4GB | 13.41% | 39.95% |
| 30日 | 3,000.0GB | 1,193.8GB | **39.79%** | **100%** |
| 60日 | 3,000.0GB | 2,686.4GB | 89.55% | 100% |
| 90日 | 3,000.0GB | 3,000.0GB | 100% | 100% |

- 見込みの空きはまとめて消した日に3,000GB増えた（中央値で6,012.2GBに）。実際の空きは、その後30日の最も少ない日で中央値2,235.9GBのままだった
- **古い置き場の3,000GBそのものは中央値26.0日で空き終わった（目安の式：残す7日＋3,000÷150＝27日）。けれども実際の空きが見込みに追いつく（3,000GBの99%に届く）までは中央値66.0日（10〜90%で60〜72日）かかった（目安の式：残す7日＋3,000÷余力50＝67日）**
- 30日目には古い置き場は空き終わっていたのに、実際の空きの増えは3,000GBの39.79%だった。古い置き場を片付けているあいだ、ふだんの消した分が後回しになり、そのたまった分を余力の1日50GBで片付けるからである

### 確かめ：24通り（各200回、`results/grid.csv`）
| 片付けの速さ（ふだん消す量の何倍か） | 片付けの上限による上乗せ（ふだん） | 古い置き場が空き終わるまで（中央値） | 実際の空きが見込みに追いつくまで（中央値） | 30日目の実際の空きの増え |
|---|---|---|---|---|
| 1.2倍 | 12.2〜74.2GB | 24〜39日 | **147〜161.5日** | 10.51〜20.28% |
| 1.5倍（基本） | 1.7〜22.5GB | 19〜33日 | 59〜73日 | 26.77〜51.26% |
| 3倍 | 0〜3.3GB | 9〜23日 | 14〜28日 | 99.71〜100% |

（どの行も、残す日数4通り×書き込みのばらつき2通りの8通りの幅）

- **実際の空きが見込みに追いつくまでの日数は、24通りで14〜161.5日と大きく動いた**。動かしたのはおもに片付けの余力で、余力が小さい（1.2倍）と、古い置き場は24〜39日で空き終わっても、追いつくまでは147〜161.5日かかった
- 追いつくまでの日数の中央値は、24通りすべてで目安の式（残す日数＋3,000÷余力）との差が3日以内だった（式どおり）
- ふだんのずれの平均は24通りで0〜1,474.2GB（容量の0〜9.83%）で、ほぼ残す日数で決まった（残す0日では片付けの上限による分だけ）。書き込みのばらつきを0.6にすると、片付けの上限による上乗せは大きくなった（1.2倍で最大74.2GB）

## 注意（言えないこと）
- 架空のデータです。書き込みの量、90日で消す決まり、残す日数、片付けの速さ、まとめて消す量は作成者が置いたもので、ずれの大きさはこれで決まります。主な値は「残す日数×1日に消す量」「残す日数＋まとめて消す量÷余力」の式でほぼ決まります（式どおり）。実在のアプリや保存の仕組みを表すものではありません
- 片付けは消した順に、1日に決まった量まで空けると置きました。消した順と違う順で空ける仕組み、時間帯や混み具合で片付けの速さが変わる仕組みは入れていません
- 書き込みの量は日によって散らばるだけで、増えていく傾きは入れていません
- 容量をどれだけ用意すべきかや、その費用は扱っていません。残す日数や片付けの速さをどう決めるべきかも言えません
