# 701 「2024/1/5」のように0を埋めない日付を文字列のまま並べ替えると、何行が順番を間違えるのか（実務の型・SQL と表の扱い）

日付を「2024/1/5」のように月や日の0を埋めない文字列で持っている表は、ORDER BY・MIN・MAX・BETWEEN を文字列のまま使うと、文字の順（「1」「10」「11」「12」「2」…）で比べてしまいます。**ここでは、架空の注文6,000件（2024/1/1〜2025/12/31）の日付を0なしの文字列で持たせ、文字列のまま並べた場合と日付に直して並べた場合を比べました。** 件数と期間は作成者が置いたもので、数字はその置き方で決まります。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A701 | 文字列のまま並べると、行の順番・最初と最後の日・「最新N件」・期間の絞り込みはどれだけずれるか | 文字列の ORDER BY・MIN/MAX・BETWEEN と、strptime で日付に直したもの。DuckDB（1スレッド）と pandas で一致を確認。seed 701 | `src/a701_string_date.py`、`src/02_sort_duckdb.sql`、`src/01_sort_tsql.sql`（未検証） |

## 主な結果
- **並べた順番**：文字列のまま並べると、6,000行のうち **5,987行（99.8%）** が、日付で並べたときと違う日付の位置に入った。月か日が1桁の行は80.9%
- **最初と最後の日**：文字列の MIN は 2024/1/1 で正しいが、**MAX は 2025/9/9**（本当は 2025/12/31）
- **「最新N件」**：文字列で降順にした最新10〜500件は、本当の最新と **0%** 重なった（すべて2025年9月の注文）。1,000件で9.4%
- **期間の絞り込み**：文字列で '2025/1/1'〜'2025/3/31' を絞ると **1,614件**（本当は760件）。10〜12月の906件が混ざり、3月4日〜9日の52件が落ちた

## 動かし方
```
pip install -r requirements.txt
cd src && python a701_string_date.py
```
数秒で終わります。`data/orders.csv` に注文（日付は文字列）を書き出します。

## 確かめたこと
- 空のフォルダで流し直し、data・results・figures がバイト単位で一致した（DuckDB は `SET threads=1`）
- DuckDB の ROW_NUMBER（文字列の順・strptime の順）と MIN/MAX が、pandas の結果と一致した
- T-SQL 版（`01_sort_tsql.sql`）は書いたが、SQL Server では動かしていない（**未検証**）。CONVERT のスタイル 111 で 0 なしの日付が読めるかも確かめていない

## データ
- `data/orders.csv`：order_id・order_date_txt（例 2024/1/5）・amount
- 仮定：注文日は2年間に一様より少し後ろ寄り（後ろほど1.6倍まで多い）。金額は対数正規分布

## 注意（言えないこと）
- 架空のデータ。ずれの件数は期間と件数の置き方で変わる。0を埋めた「2024/01/05」や「2024-01-05」なら文字列でも正しく並ぶ
- 列が日付型なら起きない。ここは CSV や表計算から文字列のまま取り込んだ場合
- 同じ日の中の順番は注文番号で決めている
