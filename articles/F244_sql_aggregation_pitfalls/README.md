# F244 集計の SQL は、どう書けば間違えにくいか？

シリーズ「実務に近い分析」の14本目。集計の SQL でよく起きる誤りを21個、わざと書いて動かし、「合計がどれだけずれるか」と「どんなテストなら見つかるか」を数えました。公開データ（経済産業省「商業動態統計」）を DB に入れた6個と、架空のネット書店「あおば書店（架空）」の注文データ（シミュレーション）での15個です。

## 問い
- JOIN の行の増え方、NULL、DISTINCT、日付と時間帯、ウィンドウ関数の範囲、整数の割り算。それぞれの誤りで、集計の数字はどれだけずれるのか。
- 照合・粒度・NULL・期間・小さなデータでの答え合わせ・値の範囲・エンジン間の一致、の7つのテストのうち、どれが誤りを見つけるのか。

## 結論
- **ずれは「少し」では済まない。** 21個のうち、合計のずれが10%を超えたのは13個。例：品目の合計行まで足すと +145%（A1）、明細の行を人数として数えると +232%（B7）、値引きの NULL を引くと −71%（B3）、NOT IN と NULL で結果が0件（B5）。
- **一方で、ずれが小さく見落としやすい誤りもある。** 12/31 を BETWEEN で落とすと 12月の売上が −2.5%（B9）、行のない日を飛ばした7日移動平均は合計で +1.7%（B11）、年度を暦年で切ると −0.8%（A5）、UTC のまま月に分けると年の合計は 0.0% のまま月の値だけ動く（B8）。
- **7つのテストを合わせると21個すべて見つかった**（乱数の種3通りでも21個）。正しい SQL では7つのテストに引っかかるものはなかった。
- **いちばん効いたのは「小さなデータでの答え合わせ」（T5）で21個。** これを外すと16個に落ち、平均値引きの NULL（B4）、NOT IN と NULL（B5）、人数の数え方（B6・B7）、率の平均（B13）の5つは T5 でしか見つからなかった。
- **ただし答え合わせ用のデータに「境目のケース」がないと、T5 は21個中15個しか見つけない。** 分割払い・2回の発送・クーポンなし（NULL）・明細の返品がないデータでは、JOIN の増え方や NULL の誤りが表に出ない。
- **照合（T1）は足し上げられる指標でしか使えない。** 使えた11個のうち10個を見つけたが、人数・率・平均には使えない。UTC で月を切る誤り（B8）は年の合計が変わらないので照合を通ってしまい、期間・キーの網羅（T4）で見つかった。
- **結果に NULL が出るかを見るテスト（T3）は1つも見つけなかった。** SUM や AVG は NULL を黙って飛ばすので、NULL の誤りは「NULL のない、間違った数字」として出てくる。
- **整数の割り算はエンジンで結果が変わる。** SQLite（と SQL Server）では切り捨てになり、購入率がすべて0（B12）、前年比が整数に丸まる（A4）。DuckDB では正しく割れるので、DuckDB だけで確かめると見つからない（エンジン間の一致 T7 で見つかった）。

## データ
| データ | 中身 | 期間 |
|---|---|---|
| 経済産業省「商業動態統計」（F135 で取得、F232 で整えたものを再利用） | 全国・月次の業態別・品目別の販売額（百万円）。百貨店・スーパー・コンビニ・ドラッグストア・ホームセンター・家電大型専門店 | 2014年1月〜2026年8月 |
| 国民の祝日（内閣府「国民の祝日」に基づき、F233 で jpholiday から作成） | 祝日の日付 | 2014〜2026年 |
| あおば書店（架空）の注文データ（シミュレーション） | 顧客8,000人、注文59,737件、明細149,592行、支払い・発送・返品・日ごとの訪問数 | 2025年1〜12月（日本時間） |

- 注文の時刻は UTC の文字列で持たせ、日本時間 = UTC + 9 時間とした。クーポンを使わない注文の値引きは 0 ではなく NULL、紹介者がいない顧客の紹介者 ID も NULL にした。
- 12% の注文は支払いが2回（ポイント＋カード）、8% は発送が2回、明細の 4% に返品、注文の 4% はキャンセル。3/15・3/16・7/8・11/20 はシステム停止で注文が1件もない日（行がない日）にした。
- **あおば書店は架空の会社で、数字はすべてシミュレーション。** 実在の会社のデータは使っていない。

## 手法
1. 同じ表を DuckDB 1.5 と SQLite 3.45 の両方に入れ、21個の集計それぞれに「誤り版」と「正しい版」の SQL を書いて両方で流した（`sql/queries_duckdb.sql`、`sql/queries_sqlite.sql`）。
2. 正しい値は、SQL とは別に pandas で計算した。正しい版の SQL が pandas と一致すること（21個×2エンジン）を確かめてから比べている。
3. テストは7種類。
   - T1 照合：結果の合計を、元の表から別に計算した合計（公表の合計行など）と比べる。足し上げられる指標だけ。公開データは公表の丸めがあるので 0.01% まで許した
   - T2 粒度：結果のキー（月・顧客など）が重複していないか
   - T3 NULL：結果に NULL がないか
   - T4 期間・キーの網羅：出てくるべき月・日・顧客がそろっていて、余計なものがないか
   - T5 小さなデータで答え合わせ：40人・約800注文の小さなデータ（公開データは3業態・2020〜2025年を切り出し）で、pandas の答えと完全に一致するか。境目のケース（分割払い・2回の発送・クーポンなし・返品・キャンセル・元日0〜9時・12/31 23時台・停止日）を必ず入れた
   - T6 値の範囲・型：率が0〜1に入り、すべて整数になっていないか。前年比が整数ばかりでないか
   - T7 エンジン間の一致：同じ SQL を DuckDB と SQLite で流して同じ結果になるか
4. 主の結果は SQLite（整数の割り算が SQL Server と同じ動き）で出した。

## 頑健性
1. **乱数の種を3通りに変える**（`results/E_seeds.csv`）：21個すべてが見つかるのは3通りとも同じ。ずれの大きさも B1 +11.8〜+12.1%、B3 −70.7〜−70.9%、B7 +232〜+235% などほぼ同じ。
2. **主のエンジンを DuckDB にする**（`results/C_catch_matrix_duckdb.csv`）：整数の割り算の2つ（A4・B12）は DuckDB では誤りにならないため、T5 が見つけるのは19個に減る。T7（エンジン間の一致）がこの2つを見つけ、どれか1つで見つかるのは21個のまま。
3. **答え合わせ用のデータから境目のケースを抜く**（`results/D_catch_matrix_plain_fixture.csv`）：T5 が見つけるのは21個中15個に減り、B4（平均値引きの NULL）はどのテストでも見つからなくなった（21個中20個）。
4. **データの条件を変える**（`results/F_parameters.csv`）：分割払いが0%なら支払いの JOIN の誤り（B1）は合計がずれず照合も通る。5%で +5.0%、30%で +29.8%。クーポンを使う注文が10%なら値引き NULL の誤り（B3）は −90%、90%なら −10%。**誤りがあっても、データの中身しだいで「たまたま正しい数字」が出る**ので、照合だけに頼れない。

## 言えないこと
- 21個は「よくある誤り」の一部で、すべてではない。どの誤りが現場でどれくらい起きるかは調べていない。
- 「見つけた数」は、この21個とこのテストの組み合わせでの数。テストの作り方（許すずれの幅、答え合わせ用データの中身）を変えると変わる。
- 答え合わせ（T5）が強いのは、正しい値を SQL とは別の書き方（pandas）で計算しているから。同じ考え違いを両方に書けば、答え合わせも通ってしまう。
- 注文データはシミュレーションで、実際のネット書店のデータではない。誤りの大きさ（%）はデータの作り方（分割払いの割合など）で変わる。
- SQL Server では実行していない。整数の割り算・日付の扱いは SQL Server のルールに合わせて書いたが、細かい動き（照合順序、日付型の変換）は確かめていない。
- B13（日ごとの率の平均）は誤りというより定義の違い。どちらが正しいかは、何を知りたいかで決まる。
