# 513 ログを10件に1件だけ残して10倍すると、小さな区分の件数はどれだけ振れるのか？（実務の型）

架空のイベントログ（100万件、区分1,000、利用者約9万人）を作り、「イベントごとに1/kを残す」と「利用者ごとに1/kの人を選び、その人のイベントをすべて残す」の2通りで間引いて k 倍し、区分ごとの件数とユニーク利用者数を本当の値と比べたフォルダです（k＝2・10・100、各200回）。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A513 | 間引いて戻した件数は、区分の大きさによってどれだけ振れるか。0件になる区分はどれだけあるか。ユニーク利用者は正しく戻るか | 区分の大きさに大小（ジップ型）のある架空ログを作り、2通りの抜き取りを200回くり返して、相対誤差（二乗平均）・0件になる割合・ユニーク利用者の偏りを区分の大きさ別に集計。DuckDB の `USING SAMPLE` と ID のハッシュで1回分を確認 | `src/a513_log_sampling.py`、`src/02_sampling_duckdb.sql`、`src/01_sampling_tsql.sql`（T-SQL 版、未検証） |

## 主な結果（区分の大きさ別の中央値）
- **10件に1件（×10）の件数の相対誤差**：100件未満の区分35%、100〜1,000件21%、1,000〜1万件6.7%、1万件以上2.1%
- **100件に1件（×100）**：100件未満113%、100〜1,000件71%、1,000〜1万件22%、1万件以上6.1%。2件に1件でも100件未満の区分は12%振れる
- 振れ幅はほぼ √((k−1)/本当の件数) で決まる（100〜1,000件の区分で式は2件に1件7.2%・10件に1件21%・100件に1件71%、実測7.1%・21%・71%）
- **0件になる割合**：100件に1件にすると、100件未満の区分の47%、100〜1,000件の区分の15%が0件になった。10件に1件では0.1%以下
- **利用者ごとに間引いても**、件数の振れはほぼ同じか少し大きい（1万件以上の区分で10件に1件2.7%、イベントごと2.1%）。同じ人のイベントがまとめて入るか抜けるかするため
- **ユニーク利用者数**：イベントごとに間引いて「残った人数×10」とすると、1万件以上の区分で+30%、1,000〜1万件で+4%多く出た（何度も来る人は1件でも残れば数えられるため）。利用者ごとに間引けば偏りはほぼ0（±0.2%以内）
- **DuckDB の1回分**：10%抜き取り×10の合計はイベントごと999,750件、利用者ごと（ハッシュ）983,680件（本当は100万件）

## 動かし方
```
pip install -r requirements.txt
cd src && python a513_log_sampling.py
```
`results/` に区分の大きさ別の表（`by_size.csv`）、まとめ（`a513_main.json`）、DuckDB の1回分（`duckdb_once.csv`）が出ます。ログは毎回スクリプトで作り直すので、`data/` は置いていません。

## 注意（言えないこと）
- 架空のデータ。区分の大きさの分布（ジップ型、指数1.2）と利用者の来訪の偏り（対数正規）は置いた値。実際のログでは区分の分かれ方や、人ごとの偏りが違う
- 相対誤差は抜き取りの偶然による振れだけ。ログの欠けや重複、時間帯で抜き取り率を変える仕組みなどは入れていない
- 利用者ごとの抜き取りは「同じ人のイベントがそろう」利点があるが、件数の振れは小さくならない。利用者数の少ない区分ほど振れる
- T-SQL 版は SQL Server 本体では動かしていない（未検証）。`CHECKSUM` や `NEWID()` の偏りも確かめていない
