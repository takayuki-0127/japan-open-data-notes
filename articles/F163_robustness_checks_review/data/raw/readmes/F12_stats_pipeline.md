# F12 e-Stat から自動で更新できる「くらしの指標」パイプライン（DuckDB × dbt × Streamlit）

看板記事 F12。物価・雇用・賃金の公的統計を、**取得 → DuckDB に保存 → dbt で加工とテスト → ダッシュボード**の流れにして、毎月同じコードで更新できるようにしました。

## 問い

物価・賃金・雇用の公的統計を、毎月自動で取り込み、加工し、ダッシュボードとして更新し続けられるか。そのとき、データの異常（欠け・重複・ありえない値）や取得の失敗に、仕組みの側で気づけるか。

## データ（e-Stat の「ファイル」、API キーは使わない）

| 名前 | 統計 | e-Stat の statInfId | 期間 |
|---|---|---|---|
| cpi | 消費者物価指数 2020年基準 長期時系列 中分類指数（全国・月次） | 000032103842 | 1970年1月〜2026年9月 |
| lfs | 労働力調査 長期時系列 表1 a-1 主要項目（季節調整値） | 000031831358 | 1953年1月〜2026年8月 |
| jobs | 一般職業紹介状況 有効求人倍率（実数・季節調整値） | 000040505314（毎月変わる） | 1963年1月〜2026年8月 |
| wage | 毎月勤労統計調査 全国調査 長期時系列 実数・指数累積データ（指数・伸び率） | 000032189777 | 1952年〜2026年8月（調査産業計・5人以上・就業形態計だけ残す） |

- 設計では e-Stat API（appId が必要）を使う予定でしたが、**API キーなしで取れる e-Stat の「ファイル」の公開 URL**（`file-download?statInfId=…`）に変えました。シークレットが要らないので、GitHub Actions で動かすときも鍵の管理がいりません
- 有効求人倍率の表は、毎月の公表ごとに statInfId が変わります。`src/sources.json` の `discover_title` で一覧ページから最新のものを探します
- 今回の実行は 2026-10-26 時点。作業した環境から e-Stat に直接つながらなかったため、ブラウザで同じ URL から取った4ファイルをまとめたもの（`--bundle`）から作りました

## 手法（パイプライン）

| 段 | 中身 | ファイル |
|---|---|---|
| 01 取得 | 公開 URL からダウンロード。失敗したら指数バックオフで最大5回再試行し、それでも駄目なら前回のファイル（キャッシュ）で続行（`--strict` で停止） | `src/01_fetch.py`, `src/sources.json` |
| 02 保存 | 4つの表を縦持ち（month, series, value）で DuckDB の raw テーブルへ。取り込みごとに件数・最新月を `load_log` に、全値を `snapshots` に残し、前回との差分（新しい月・改定・消えた値）を CSV に出す | `src/02_load_duckdb.py` |
| 03 加工とテスト | dbt：source → staging（横持ち、view）→ mart（前年同月比・実質賃金の作り直し、table）。テスト20本 | `dbt/`, `src/03_run_dbt.py` |
| 04 出力 | mart の CSV、図、Streamlit のダッシュボード | `src/04_figures.py`, `app/app.py` |
| 自動化 | 全体を順に流して記録する `run_pipeline.py`。毎月動かす GitHub Actions の例（このリポジトリでは有効にしていない） | `src/run_pipeline.py`, `workflow_example/update_monthly.yml` |

### dbt のテスト（20本）

- 一意・非NULL：各モデルの month
- 値の範囲（自作の generic test `value_between`）：物価指数 10〜200、失業率 0〜15%、求人倍率 0.1〜3倍、実質賃金の前年比 ±20%、物価の前年比 −10〜30%
- `assert_raw_no_duplicates`：生データで同じ月・同じ系列が2行ないか
- `assert_real_wage_rebuilt_matches`：名目賃金指数 ÷ 持家の帰属家賃を除く総合 × 100 で作り直した実質賃金指数が、公表値と 0.15 ポイント以内で一致するか
- `assert_latest_month_is_recent`：最新月が実行日から4か月以上古くないか（取り込みが止まっていないか）

## 主な結果

1. **全体が約32秒で流れ、テスト20本がすべて合格**（`results/run_log.txt`, `results/dbt_results.json`）
2. **実質賃金は、作り直した値と公表値が 1970年1月〜2026年8月の680か月すべてで一致**（差の最大 0.0）。公表の実質賃金は「名目 ÷ 持家の帰属家賃を除く総合」で作られていることを、データで確かめられた
3. 最新の値（mart_indicators_monthly）
   - 物価（総合）の前年同月比：2026年9月 2.2%（生鮮食品及びエネルギーを除く総合 2.3%、エネルギー −0.3%）
   - 完全失業率 2.5%、有効求人倍率 1.18倍（2026年8月、季節調整値）
   - 実質賃金（現金給与総額）の前年同月比：2026年1〜8月は8か月続けてプラス（平均 +2.1%）。2025年は12か月のうちプラスが1か月だけだった
4. **わざと壊して確かめた3つの試験**（`results/robustness.json`, `src/05_checks.py`）
   - 通信が2回失敗する偽の通信 → 3回目で取得（1秒・2秒待って再試行）。5回とも失敗 → キャッシュで続行
   - 先月時点（`--as-of 2026-07`）の取り込みと比べると、新しい月の値が cpi 12・lfs 4・jobs 2・wage 8 行増え、過去の値の改定は0件。同じデータでもう一度流すと差分は0行
   - 壊れたデータ（失業率25%の行・同じ月の重複・総合指数の欠け）を入れると、テスト3本が失敗し、mart は作られずに止まる
5. つまずいたこと：重複した月は、staging で `group by` して横持ちにする段階で `max()` に潰されて見えなくなった。生データの段階で重複を調べるテスト（`assert_raw_no_duplicates`）を足して、初めて止められるようになった

## 動かし方

```bash
pip install -r requirements.txt
python src/run_pipeline.py                 # e-Stat から取得して全部流す
# python src/run_pipeline.py --bundle f12_bundle.json   # ブラウザで取ったバンドルから
python src/05_checks.py                    # 頑健性チェック（再試行・差分・壊れたデータ）
streamlit run app/app.py                   # ダッシュボード
```

- `data/stats.duckdb` と `dbt/target/` は実行すると作られるので置いていません
- 差分の試験を再現するときは、`python src/02_load_duckdb.py --as-of 2026-07` のあとに `python src/02_load_duckdb.py` を実行
- 毎月の自動更新：`workflow_example/update_monthly.yml` を `.github/workflows/` に置くと、毎月26日に実行して結果をコミットします（シークレット不要。dbt のテストが落ちると止まり、GitHub の通知で分かる）

## 言えないこと

- ダッシュボードは数字の記述で、物価・賃金・雇用のあいだの因果は言えない
- 実質賃金の前年比のプラスが続いている理由（賃上げ・ボーナス・物価の落ち着きなど）は、このパイプラインでは分けていない
- 物価の前年同月比は、公表されている指数（小数1桁）から計算したもの。公表の前年比と 0.1 ポイントずれる月がありうる
- 自動更新は例のファイルとして置いただけで、このリポジトリで毎月動かしてはいない。e-Stat の表の形式（列の並び・シート名）が変わると読み込みで止まる（そのときはテストではなく 02 のエラーで気づく）
