# 326 古いシステムから新しいシステムへ移したデータは、何を照合すれば「同じ」と言えるか（実務の型）

架空の顧客・口座・取引の3つの表を作り、新システム側に移行のミスを10種類、1つずつ入れて、5段の照合（件数・合計・キーの有無と重複・列ごとのハッシュ・抜き取り）で見つかるかを数えたフォルダです。照合の SQL は DuckDB で動かしました。T-SQL 版は `sql/01_reconcile_tsql.sql` に置きましたが、**SQL Server 本体では動かしていません（未検証）**。

| # | 問い | 手法 | ファイル |
|---|---|---|---|
| A326 | 移行の前後で、どの照合がどのミスを見つけ、どれを見逃すか | 顧客5,000・口座8,000・取引200,000行の架空データ。ミス10種類（行の欠け、行の重複、端数の切り捨て、符号の逆転、文字の切り詰め、文字の置き換え、日時の9時間ずれ、NULL が 0・空文字に、ひも付けのずれ、相殺する入れ違い）を1つずつ入れ、5段の照合を流す。抜き取りは行数を10〜3,000行に変えて200回ずつ。害のない変換3種類（コードを名前に、全角ハイフンを半角に、行の並び替え）で空振りも数える | `src/a326_reconcile.py`、`sql/01_reconcile_tsql.sql` |

## 主な結果
- 見つけたミスの数（10種類中）：件数 2、合計 4、キーの有無・重複 2、列ごとのハッシュ 10、抜き取り300行 5（200回のうち95%以上で当たったもの）
- **件数・合計・キーの3つを全部やっても、見つかったのは4種類**。文字の切り詰め・文字の置き換え・日時のずれ・NULL の変化・ひも付けのずれ・相殺する入れ違いの6種類は素通りした
- 抜き取り300行は、全部の行が違うミス（端数・日時・NULL・文字）には100%当たったが、数十〜数百行だけのミスには当たりにくい：行の欠け（200行）29%、符号の逆転（300行）40%、相殺する入れ違い（200行）28%。3,000行まで増やすと96〜100%。**行の重複は、何行抜いても0%**（キーで引いて1行目どうしを比べるため）
- 列ごとのハッシュは10種類すべてを見つけた。ただし分かるのは「どの表のどの列が違うか」までで、行は分からない。害のない変換（コードを名前に、全角ハイフンを半角に）でも2つ鳴った
- **ハッシュのまとめ方に落とし穴**：キーと値のハッシュを XOR でまとめる形では、10種類のうち7種類しか見つからなかった。見逃したのは、NULL が 0 に変わる（同じ変化が偶数行）、ひも付けのずれ、相殺する入れ違い（どちらも値の入れ替わり）。キーと値を1つの文字列にしてからハッシュし、足し合わせる形では10種類すべて見つかった
- 全部見つけるのに必要な最小の組み合わせは「列ごとのハッシュ」1つ。ハッシュを使わない4つの組み合わせでは、ひも付けのずれ（抜き取り300行で92%）と相殺する入れ違い（28%）が残る

## 動かし方
```
pip install -r requirements.txt
cd src && python a326_reconcile.py
```
データは実行のたびに同じものを作ります（seed 326）。`results/`・`figures/` を出します。

## 確かめたこと
- 空のフォルダで流し直し、results・figures が一致した
- 抜き取りで「違う行」を数えるところは、照合の SQL とは別に、旧と新をキーでつないで全列を比べて作った

## 注意（言えないこと）
- すべて架空のデータです。「何種類見つけたか」は、入れたミスの選び方と大きさ（0.1%、50行、300行など）で決まります。実際の移行で起きるミスの割合を表すものではありません
- T-SQL 版（`EXCEPT`・`HASHBYTES`・`NEWID()`）は SQL Server 本体では動かしていません。SQL Server の `CHECKSUM_AGG` がどうまとめるかも、ここでは確かめていません
- ハッシュが「同じ」でも、別の値がたまたま同じハッシュになる場合は見逃します（今回の10種類では起きませんでした）
- 害のない変換がある列は、変換の決まりを旧側にも当ててからハッシュを取る必要があります。その手間は測っていません
- 版の違うファイルの比べ方は 259、取り込む前の入力の検査は 260 で扱いました。この記事は、移行の前後の突き合わせに絞っています
